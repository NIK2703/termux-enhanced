## 2. F0 — хвост строки: в `drawTextRun` уходят все `columns` символов

### 2.1 Доказательство

`TerminalRow.clear()` (`TerminalRow.java:216-225`):

```java
public void clear(long style) {
    Arrays.fill(mText, ' ');
    Arrays.fill(mStyle, style);
    mSpaceUsed = (short) mColumns;      // ← не 0
    ...
}
```

`setChar()` меняет `mSpaceUsed` только на **разницу** в числе java-char'ов
(`mSpaceUsed += javaCharDifference`, строка 330), то есть при замене символа той же ширины
не меняет его вовсе. Конструктор вызывает `clear()` (строка 81). Значит для любой строки,
которая хоть раз выделялась или очищалась — а это все строки экрана —
`getSpaceUsed() == mColumns`.

Рендер использует это значение как объём текста строки:

```java
final int charsUsedInLine = lineObject.getSpaceUsed();   // TerminalRenderer.java:426
...
final int charsSinceLastRun = currentCharIndex - lastRunStartIndex;   // :539
addRun(..., charsSinceLastRun, ...);                                  // :545
...
canvas.drawTextRun(text, startCharIndex, runWidthChars, ...);         // :798
```

Цикл `:473` идёт по `column < columns`, поэтому для ASCII-строки `currentCharIndex` доходит
до `columns`, и `runWidthChars == columns - startColumn`. Строка из 11 символов
отрисовывается как 200.

### 2.2 Замер (не оценка)

Стенд: `TerminalRow`/`WcWidth`/`TextStyle` скомпилированы отдельно (`javac`, JDK 21), сценарий —
экран 200×48, строки разной длины:

```
PROBE fresh row      : spaceUsed=200 (columns=200)
PROBE after 'ls -la' : spaceUsed=200 -> drawTextRun chars=200, real content chars=11, wasted=189
PROBE after clear    : spaceUsed=200 -> drawTextRun chars=200
PROBE frame 200x48   : chars handed to drawTextRun=9600, real content=1521, wasted=8079 (84%)
```

**84 % символов полного кадра — пробелы за концом содержимого.** Они проходят itemization,
шейпинг, получение glyph id и раскладку позиций, не давая ни одного пикселя.

Почему это не перехватывается существующими оптимизациями:

* A2/E4 (пустая строка) спасает только строки, где **нет ни одного** непробела. Строка
  `ls -la` — непустая, идёт полным путём.
* Обрезка «по `mSpaceUsed`» не работает ровно потому, что `mSpaceUsed` равен ширине экрана.

### 2.3 Правка

Обрезать хвост рана по последнему непробельному кодпоинту, а раны, целиком состоящие из
пробелов, не рисовать текстом вообще.

В цикле `:473` инкрементально ведём границу содержимого рана:

```java
// на каждый кодпоинт рана
if (codePoint != ' ' || combiningEaten) runContentEnd = currentCharIndex + charsForCodePoint;
```

На закрытии рана (`:516` и `:545`):

```java
int chars = currentCharIndex - lastRunStartIndex;
final int effect = TextStyle.decodeEffect(lastRunStyle);
final boolean decor = (effect & (CHARACTER_ATTRIBUTE_UNDERLINE | CHARACTER_ATTRIBUTE_STRIKETHROUGH)) != 0;
// Обрезка только когда она ничего не меняет на экране:
//  · decor — подчеркивание/зачёркивание рисуются drawTextRun и идут по пробелам;
//  · mismatch — mes считается по измеренной ширине, обрезка исказит масштаб;
//  · combining — комбинирующий знак над пробелом видим.
if (!decor && !lastRunFontWidthMismatch && !runHasCombining && runContentEnd < currentCharIndex) {
    chars = Math.max(0, runContentEnd - lastRunStartIndex);
}
```

В `drawRunText()`: `if (runWidthChars > 0) canvas.drawTextRun(...)`. Прямоугольники курсора и
фона масштабированного рана считаются от **колонок** (`left/right` из `startColumn` и
`runWidthColumns`, строки 696-697), поэтому обрезка на них не влияет.

Условия безопасности (каждое обязательно):

1. **Подчёркивание / зачёркивание** — текстовые декорации, `drawTextRun` рисует их по всем
   клеткам рана включительно с пробелами. Обрезка укоротит линию. Исключить (это ровно та же
   ловушка, что уже учтена в A2).
2. **`fontWidthMismatch`** — масштаб считается как `runWidthColumns / mes`, где `mes` — сумма
   измеренных ширин. Обрезка текста изменит `mes`, но не `runWidthColumns` ⇒ глифы поедут.
   Mismatch-раны не обрезаем (их мало и они короткие).
3. **Комбинирующие символы** — «пробел + combining» видим. Если ран поглотил комбинирующие,
   обрезку отключаем.
4. **Курсор** — прямоугольник курсора рисуется по колонкам и от обрезки не зависит; глиф под
   блок-курсором — пробел, то есть ничего. Обрезка допустима.
5. **Выделение** — подсветка это фон (pass A, по колонкам). Обрезка допустима.

Дополнительный выигрыш того же флага: внутренние раны из одних пробелов (отступы в коде,
разделители колонок в `ls --color`) перестанут рисоваться вообще.

Ожидаемый эффект: на экране 200×48 объём текстовой работы падает в **3–6 раз** на типовом
содержимом; это самая большая доля полного кадра, и правится она без новой структуры данных
и без нового состояния.

## 3. F1 — базовая заливка строки дублирует `drawColor()` на полном кадре

На полном кадре (`dirtyRect == null`) сначала заливается весь канвас:

```java
if (dirtyRect == null) {
    canvas.drawColor(bgColor, PorterDuff.Mode.SRC);   // :347-349
}
```

а затем **для каждой строки** — прямоугольник тем же самым цветом:

```java
canvas.drawRect(fillLeft, rowTop, fillRight, heightOffset, baseFillPaint);   // :414
```

`baseFillPaint` несёт тот же `bgColor` (`:366-375`), а при `dirtyRect == null`
`fillLeft = 0`, `fillRight = columns * mFontWidth`. Это та же площадь, тот же цвет, тот же
режим (SRC при прозрачности, SRC_OVER при непрозрачном фоне над непрозрачным же).

Стоимость: лишний **полный экран заливки на каждый полный кадр** — на 1080×2200 это ~2.3 Мпкс,
то есть 0.1–0.5 мс GPU на кадре, 60 раз в секунду, в самом горячем сценарии (живое дно).

Правка — одна строка:

```java
if (dirtyRect != null) {
    canvas.drawRect(fillLeft, rowTop, fillRight, heightOffset, baseFillPaint);
}
```

На частичном кадре заливка обязательна (стирает предыдущие пиксели строки) и остаётся.

## 4. F2 — E2 сводится к bounding box'у на шаге инвалидации

Буфер хранит **битовое множество** грязных строк, рендер пропускает негрязные строки (`:412`),
`repaintAfterUpdate()` аккуратно собирает `first`/`last` (`:1064-1073`). А затем:

```java
private void invalidateRowRange(int first, int last) {
    ...
    for (int row = first; row <= last; row++) screen.markRowDirty(row);   // :1208
    ...
}
```

Строки между реально изменившимися помечаются грязными **повторно**, и рендер честно рисует
весь band. Разреженность, ради которой делался E2, теряется.

Типичный случай: курсор переехал с строки 40 на строку 3 (TUI перерисовывает статус-строку).
Помечены 2 строки, инвалидируются и рисуются 38.

Комментарий к `:1208` объясняет маркировку страхом, что «damage, который запросил
перерисовку, не будет нарисован». Этот страх уже закрыт другим механизмом — `forceDraw`
в рендерере (`:383-390`): если в клипе **ни одной** грязной строки, рисуются все строки
клипа. А damage, который действительно нужно нарисовать, всегда помечен вызывающей стороной:

* курсор — `markRowDirty(prev)`/`markRowDirty(cur)` в `:1057-1058`;
* полоса скроллбара — `markRowsIntersectingDirty()` в `:1133`;
* содержимое — биты из `setChar`.

Правка: `invalidateRowRange(first, last, boolean markRows)`; из `repaintAfterUpdate()`
передавать `false`. Второй вызывающий (`:1086`) — единственный.

Ожидаемый эффект: `tmux` со статус-баром, `btop`, любые «две строки в кадре» — **2–3 строки
вместо 48**. Это тот выигрыш, который E2 обещал и не дал.

## 5. F3 — «призрак» бегунка скроллбара

`drawScrollbar()` вызывается на каждом кадре (`:2708`) и **безусловно** запоминает позицию:

```java
mLastThumbTop = (int) Math.floor(thumbRect.top);        // :2799
mLastThumbBottom = (int) Math.ceil(thumbRect.bottom);   // :2800
```

Но канвас на частичном кадре обрезан: если клип не накрывает бегунок, `drawRoundRect` ничего
не рисует, а `mLastThumb*` всё равно обновляются. Дальше `invalidateScrollbarBand()` видит
`mLastThumbTop == top && mLastThumbBottom == bottom` (`:1118`) и **возвращается**, считая, что
восстанавливать нечего. Старые пиксели бегунка остаются на экране до следующего полного
кадра — а в follow-text режиме полных кадров нет (E1), то есть надолго.

Правка: записывать `mLastThumb*` только если кадр действительно покрыл бегунок:

```java
if (canvas.getClipBounds(mThumbClipProbe)
        && !Rect.intersects(mThumbClipProbe, thumbPixelRect)) return;  // не рисовали — не запоминаем
```

Альтернативно — сравнивать clip с `thumbRect` до `drawRoundRect` и пропускать весь метод.
Артефакт мал (альфа бегунка 5–12 %), но он ровно из того класса, который потом ловят неделями.

## 6. F4 — `fillLeft/fillRight` из bbox клипа

```java
final float fillLeft  = (dirtyRect == null) ? 0f : (dirtyRect.left  - xOffset);   // :361
final float fillRight = (dirtyRect == null) ? (columns * mFontWidth) : (dirtyRect.right - xOffset);
```

`dirtyRect` — это `canvas.getClipBounds()`, то есть **bounding box** накопленного damage.
Пока damage — один прямоугольник, всё корректно. Если в одном кадре склеились два
прямоугольника разной ширины (узкая полоса скроллбара + band строк; или клип от родителя),
bbox расширяется по горизонтали: грязная строка зальётся фоном во всю ширину, а текст будет
нарисован только внутри реального клипа — **левая часть строки окажется стёртой**.

Правка: заливать строку всегда во всю ширину сетки и доверить обрезку канвасу:

```java
canvas.drawRect(0f, rowTop, columns * mFontWidth, heightOffset, baseFillPaint);
```

Клип всё равно ограничит закрашиваемую площадь, стоимость на GPU не меняется (тот же
отсечённый квад), зато исчезает целый класс «залили, но не перерисовали».

## 7. F5 и F6 — мелкое и отложенное

**F5 (шум).** На каждый кодпоинт: одно деление в `fontWidthMismatch` (`:488`) и второе — в
коэффициенте масштаба (`:503`). Оба операнда константны для (кодпоинт, шрифт, размер):
`bmpMeasures[cp]` и `WcWidth.width(cp)`. Можно заполнять параллельные таблицы
`bmpMismatch[]`/`bmpRatio[]` там же, где лениво заполняется `bmpMeasures` (`:219-234`), и
свести проверку к одному чтению массива. Побочный плюс: коэффициент станет **битово
одинаковым** для всех глифов с одинаковой метрикой, значит A3 (группировка масштабированных
глифов) будет схлопывать раны чаще. Эффект — единицы процентов кадра.

**F6 (B2, не начиналось).** `resize()` (`TerminalBuffer.java:329+`) пересобирает экран через
`setChar` по символу, `blockCopy()`/`copyInterval()` — тоже. При истории 10 000–50 000 строк
это миллионы вызовов на поворот экрана. Быстрый путь для «простых» строк (нет широких,
суррогатных, комбинирующих) — `System.arraycopy` по `mText`/`mStyle`. Единственная из
оставшихся правок с эффектом «сотни мс → десятки».

## 8. Что НЕ предлагается

* **Blit-скролл.** Обоснованно отвергнут во втором аудите (§4.1): прозрачность, контракт
  клипа, overdrag. F0/F1 не меняют этого вывода — они удешевляют полный кадр, а не отменяют
  его.
* **Кэш ранов со сдвигом (A4).** После F0 баланс меняется не в его пользу: A4 экономит
  сканирование (WcWidth + measure + ветвления, ~0.1 мс/кадр), но не экономит `drawTextRun`,
  который и есть основной стоимостью. До замера (§9) не начинать: выигрыш может оказаться
  5 %, а цена — новое состояние с пятью ключами инвалидации (версия строки, курсор,
  выделение, палитра, метрики шрифта).
* **Субглифовый сдвиг, своя физика жеста, свой Choreographer.** Отвергнуто ранее.

## 9. Как мерить (это по-прежнему обязательный шаг)

Микрозамеры здесь неприменимы: вопрос в долях кадра.

1. Разметить `TerminalRenderer.render()` двумя секциями под отладочным флагом:
   «scan» (цикл по колонкам, `:473-546`) и «draw» (pass A + pass B). Это сразу ответит,
   стоит ли браться за A4.
2. `adb shell dumpsys gfxinfo com.termux framestats` — 99-й перцентиль длительности кадра
   (jank), а не среднее, в сценариях: `yes`, fling по истории 2000 строк, `tmux` со
   статус-баром, поворот экрана при истории 10 000.
3. Контроль качества F0: подчеркнутый текст (`printf '\e[4mfoo\e[0m'`) — линия должна идти
   до конца рана; комбинирующие над пробелом; блок-курсор в хвосте строки; `ls --color` —
   выравнивание колонок не поехало; прозрачность 50 %.

## 12. §9.1 — замер scan vs draw на устройстве

Из §8: «до замера (§9) не начинать [A4]» — выигрыш может оказаться 5 %, а цена — новое
состояние с пятью ключами инвалидации. Замер выполнен на устройстве (Poco F5-ish, 1080×2400,
`1080x2400`, Android, флинг по истории `seq 1 50000`). Инструментовка — временная, в `render()`
добавлены два `System.nanoTime()` (один вокруг цикла по колонкам + `addRun`, второй вокруг
pass A + pass B), аккумуляторы в static-полях, дамп в logcat каждые 120 кадров. Удалена после
замера.

Сценарии и результаты (µs/кадр, среднее по 120 кадрам в каждом батче):

| Сценарий | rows/frame | runs/frame | scan | draw | total | scan/total |
|---|---:|---:|---:|---:|---:|---:|
| Запуск (первый кадр с `seq` в буфере) | 60.4 | 198.7 | **660** | 1023 | 1683 | 39 % |
| Запуск (второй батч, прогрелось) | 72.0 | 240.2 | **451** | 1041 | 1492 | 30 % |
| `seq` в буфер (1 ран/строка) | 72.0 | 76.0 | **305** | 282 | 588 | 52 % |
| Флинг по `seq 1..50000` (стационар) | 48.0 | 48.0 | **310–325** | 232–290 | 545–610 | 53–57 % |

**Скан — не 5 %, а 30–57 % кадра.** Документная оценка в §8 (~0.1 мс) была занижена
раза в 3–6. Главные потребители — `WcWidth.width` (BMP-таблица) и `measureCodePoint` (256 КБ
`bmpMeasures`, на телефоне кэш-промахи на длинных хвостах). Цикл по `columns` колонкам с этими
двумя вызовами + `getStyle` + проверкой `fontWidthMismatch` — вот что занимает скан.

**Это меняет решение по A4.** A4 экономит скан, не drawTextRun, и его выигрыш — те же
30–55 % кадра, что и у хвостового рана. Но A4 — новое состояние с пятью ключами инвалидации
(версия строки, курсор, выделение, палитра, метрики шрифта), плюс кэш на каждый ряд. Хвостовой
ран — локальная правка в одном методе без нового состояния. **A4 закрыт как «не начинать»**
(заморожен навсегда, не «до замера»), хвостовой ран — следующая задача.

## 13. T8 — хвостовой ран

### 13.1 Идея

Перед циклом по колонкам найти первую колонку «хвоста» — максимального суффикса пробельных
клеток. Для plain-строк (без широких, суррогатных, комбинирующих; `!mHasNonOneWidthOrSurrogateChars`)
это настоящее посимвольное сравнение: `while (c >= 0 && mText[c] == ' ') c--;`.

В цикле, начиная с этой колонки, включить «хвостовой режим»:

```java
if (inTail) {
    charAtIndex = ' ';
    charIsHighsurrogate = false;
    charsForCodePoint = 1;
    codePoint = ' ';
    codePointWcWidth = 1;
    measuredCodePointWidth = mFontWidth;
} else { /* то же, что было */ }
final boolean fontWidthMismatch = inTail ? false
    : Math.abs(measuredCodePointWidth - codePointWcWidth * mFontWidth) > 0.01f * mFontWidth;
```

Логика разбиения/слияния ранов, F0-обрезка по `runContentEnd`, обработка курсора/выделения/
подчёркивания — без изменений: хвостовой режим только подменяет дорогие per-cell вычисления
константами.

### 13.2 Корректность

* **TUI-фон.** Стиль хвостовой клетки может отличаться от стиля контента. Ран-merge
  (`style != lastRunStyle`) сработает на границе контент↔хвост, хвост станет отдельным раном
  со своим `backColor`. Pass A закрасит его прямоугольником — то же поведение, что и до T8.
* **Курсор в хвосте.** `insideCursor = (cursorX == column)` (WcWidth=1 ⇒ вторая ветвь ложна)
  — отработает на нужной клетке, ран разорвётся, drawRunText нарисует курсор. Совпадает с
  content-режимом.
* **Подчёркивание/зачёркивание в хвосте.** Стиль хвоста может содержать эффект
  `CHARACTER_ATTRIBUTE_UNDERLINE`. Тогда `lastRunNoTrim=true` на старте хвостового рана, F0
  оставит полный `charsSinceLastRun = columns - tailStartCol`, и `drawTextRun` прочертит
  декорацию по хвосту — то же поведение, что и без T8 (F0 это уже умеет).
* **«Измеренная ширина пробела ≠ mFontWidth».** В таком шрифте хвостовой режим дал бы
  неправильную ширину. Измеряем `' '` один раз перед циклом (`spaceMismatch`); если не
  совпадает — отключаем T8 для этой строки (`tailStartCol = columns`).
* **Широкие/комбинирующие.** Для них `mHasNonOneWidthOrSurrogateChars=true` ⇒
  `tailStartCol=columns` ⇒ хвостовой режим не активируется, цикл работает по старой
  логике целиком.
* **A3 (масштаб рана).** `mismatchRatio` хвостовой клетки = −1 (аналитика в `?:`-ветке
  короткозамыкает на `fontWidthMismatch=false`), `scaleChanged` ложен. Граница
  контент-mismatched ↔ хвост-non-mismatched даст `fontWidthMismatch != lastRunFontWidthMismatch`
  ⇒ ран разорвётся правильно.
