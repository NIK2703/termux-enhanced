# Закрытие вкладки оставляет в убитой сессии — разбор и решение

**Дата:** 2026-09-19
**Симптом (пользователь):** 4 вкладки → перейти на 3-ю → закрыть: перекидывает на соседнюю (нормально).
Затем закрыть 2-ю: **остаёшься на закрытом терминале (в нём строка `signal 9`), а на панели вкладок
подсвечена вкладка справа от закрытой.**
**Требование:** такое состояние не должно возникать никогда.
**Статус:** причина класса найдена и закрыта инвариантом (код внедрён); точное звено в сценарии
пользователя подтверждается на устройстве командой `pagedump` (см. §6). Устройство в момент разбора
подключено не было.

> **Документ промежуточной итерации.** Он описывает первый заход (единый владелец активной страницы
> + перепривязка вью по сессии). Часть перечисленного в §4.1 в финальном коде **отсутствует**:
> `reconcileActivePage()`, `shiftAttachedViewsAfterRemoval()`, `recoverUnresolvedPage()`,
> `getDisplayedView()`, `setCurrentSessionForSession()`. Итоговое состояние и все отклонения от плана —
> в `docs/tab-close-architectural-fix.md`; аудит оптимальности — в
> `docs/tab-close-fix-optimality-review.md`. Настоящая причина симптома (раскладка `RecyclerView`
> держит `ViewHolder` удалённой страницы на экране) найдена только во второй итерации — §3.7-бис
> и §5-J того документа.

## 1. Что доказывает маркер «signal 9»

Строку рисует **не** шелл и не наша вкладка, а сам `TerminalSession`, в момент обработки выхода
процесса (`terminal-emulator/src/main/java/com/termux/terminal/TerminalSession.java:373-391`):

```java
if (msg.what == MSG_PROCESS_EXITED) {
    int exitCode = (Integer) msg.obj;
    cleanupResources(exitCode);                       // mShellPid = -1 ⇒ isRunning() == false
    String exitDescription = "\r\n[Process completed";
    ...
    } else if (exitCode < 0) {
        exitDescription += " (signal " + (-exitCode) + ")";   // ← "signal 9" = SIGKILL
    }
    exitDescription += " - press Enter]";
    mEmulator.append(...); notifyScreenUpdate();
    mClient.onSessionFinished(TerminalSession.this);
}
```

Отсюда два факта:

1. **«signal 9» = SIGKILL**, а SIGKILL сессии посылает ровно один наш путь —
   `TerminalSession.finishIfRunning()` (`:259-267`), который вызывает `removeClosingTab()` при закрытии
   вкладки (`TermuxSessionTabsController.java:722-736`). То есть на экране — терминал **той самой
   закрытой сессии**, а не соседней с похожим содержимым.
2. Эмулятор мёртвой сессии уже `isRunning() == false`. Значит, состояние «стоим на ней» — это
   состояние, в котором приложение считает активной сессию, которой **уже нет в списке сессий**.

`MainThreadHandler` — обычный `Handler` без Looper'а (`:72`), созданный на главном потоке, поэтому
`onSessionFinished → removeFinishedSession` идёт по главному потоку (не гонка потоков, а гонка
**состояний**).

## 2. Модель: четыре независимых куска состояния

«Активная страница» в этом приложении не хранится в одном месте — она собирается из четырёх
независимо поддерживаемых кусков. Инвариант, который обязан держаться всегда:

```
индекс страницы пейджера  ==  активный TerminalView  ==  подсвеченная вкладка  ==  ЖИВАЯ сессия из списка
```

| # | Кусок | Владелец | Чем обновляется |
|---|---|---|---|
| 1 | `mTerminalPager.getCurrentItem()` | `SessionPagerManager` | `setCurrentItem()` (в т.ч. **no-op**, если индекс не изменился) |
| 2 | активный `TerminalView` (`mTerminalView`) | `SessionPagerManager.onTerminalPageSelected()` | `getPagerPageView(position)` |
| 3 | подсветка вкладки | `TermuxSessionTabsController` | `updateTabs()` — **по сессии**; `setCurrentSession(position)` — **по позиции** |
| 4 | список сессий | `TermuxService` | add/remove |

Ключевые зависимости, из которых вырастает баг:

* **`getCurrentSession()` — это `mTerminalView.getCurrentSession()`**
  (`TermuxActivity.java:3857-3863`). Никакой валидации «эта сессия ещё в списке / ещё жива» нет ни
  здесь, ни где-либо ещё. Устарел указатель — «активной» становится убитая сессия.
* **Подсветка вкладки берётся из двух разных ключей.** `updateTabs()` ищет индекс сессии в списке
  (`TermuxSessionTabsController.java:226-234`), а пейджерный путь отдаёт **позицию страницы**:
  `withTabsController(tabs -> tabs.setCurrentSession(position))` (`SessionPagerManager.java:1103`).
  После закрытия вкладки позиция и сессия перестают совпадать: подсветка «по позиции» встаёт на
  вкладку, которая **сдвинулась в освободившийся слот**, т.е. на правого соседа закрытой.
  Это ровно вторая половина симптома.
* **Разрешение «вьюха страницы» — рукописная карта.** `mAttachedViews` (позиция → `TerminalView`)
  обновляется на `onBindViewHolder`/`onViewRecycled` и **вручную переиндексируется** при удалении
  (`TerminalPagerAdapter.java:249-263`). Ничто не сверяет её с тем, что RecyclerView реально
  разложил на экране.
* **`onTerminalPageSelected()` имеет два молчаливых выхода** (`SessionPagerManager.java:974-1084`):
  `selected == null` → `return`; `pageView == null` → отложенный путь (слушатель attach + `post` +
  страховка `postDelayed(300)`). В обоих `mTerminalView` **не** перепривязывается и подсветка **не**
  обновляется. Страховка раньше только гасила флаг подавления IME — состояние оставалось сломанным.

## 3. Дефекты, из которых складывается баг

| # | Дефект | Где | Следствие |
|---|---|---|---|
| D1 | Активная сессия = кэшированный указатель на вьюху; живость/наличие в списке не проверяются | `TermuxActivity:3857` | «Стоим в убитой сессии» может сохраняться сколько угодно |
| D2 | Подсветка вкладки задаётся и по сессии, и по позиции | `SessionPagerManager:1103` vs `TermuxSessionTabsController:226` | Подсвечен правый сосед закрытой вкладки |
| D3 | Карта позиция→вьюха поддерживается вручную и не сверяется с экраном | `TerminalPagerAdapter:249`, `:513`, `:582` | Вьюха на экране и «активная вьюха» могут разойтись |
| D4 | Удалённый слот **угадывается** по диффу списка, с веткой «несовпадений нет ⇒ удалён хвост» | `TerminalPagerAdapter:230-298` (до правки) | При расхождении копии адаптера и списка сервиса пейджер удаляет **не ту** страницу: на экране остаётся страница убитой сессии, а полоса вкладок уже перестроена по реальному списку → **точно наблюдаемый симптом** |
| D5 | Структурное удаление в полосе снимает **хвостовые** вьюхи независимо от того, какая вкладка закрыта | `TermuxSessionTabsController:249-254` | Корректно только потому, что анимация закрытия сняла вьюху заранее; закрытие без анимации (сессия завершилась сама) вылечивается лишь перепривязкой по индексу |

**Почему один сценарий работает, а другой нет.** Разница не в «середине» и не в «втором», а в том,
**сработал ли хоть один настоящий переход пейджера**:

* закрытие последней вкладки: `index = size - 1` даёт индекс, отличный от текущего →
  `setCurrentItem(restoreIndex, false)` реально переезжает → `onPageSelected` → штатный путь;
* закрытие средней вкладки: `restoreIndex == getCurrentItem()` → `ViewPager2.setCurrentItem()` —
  **no-op без колбэков** (это прямо задокументировано в `TermuxTerminalSessionActivityClient:599-610`),
  и всё держится исключительно на ручной перепривязке + на том, куда RecyclerView сам
  «переякорит» раскладку после `notifyItemRangeRemoved`. Любой сбой в этом ручном звене (D3/D4) —
  и пользователь остаётся на мёртвой странице, а полоса вкладок живёт по своему источнику истины.

Какой именно из D1–D5 сработал в конкретном проходе пользователя, из кода однозначно не выводится —
для этого и добавлен `pagedump` (§6), который печатает все четыре куска сразу.

## 4. Решение: инвариант вместо цепочки надежд

Цепочку нельзя «починить ещё раз» — она рассыпается от любого пропущенного шага. Поэтому вводится
одна проверка, которая **доказывает** инвариант после каждого структурного изменения списка сессий и
**ремонтирует** его, если какое-то звено отвалилось.

### 4.1. Изменения в коде

| # | Файл | Что сделано |
|---|---|---|
| F1 | `TerminalPagerAdapter` | `syncWithServiceList(list, removedIndex)` — точный индекс удалённой страницы из `TermuxService.removeTermuxSession()` вместо угадывания по диффу; ветка «несовпадений нет ⇒ хвост» осталась только как fallback. Карта `mAttachedViews` переиндексируется одним помощником `shiftAttachedViewsAfterRemoval()` |
| F2 | `TerminalPagerAdapter` | `getDisplayedView(position)` — вьюха, которую RecyclerView **реально разложил** (авторитетный ответ «что видит пользователь»); `rebindPage(position)` — принудительный полный rebind слота (payload-перегрузка `onBindViewHolder` всегда выполняет полную привязку, поэтому уведомление не «съедается») |
| F3 | `TermuxSessionTabsController` | `setCurrentSessionForSession(session)` — подсветка по **сессии** (индекс берётся из живого списка), а не по позиции. Позиционная подсветка физически больше не может встать на чужую вкладку — **НЕ ВНЕДРЕНО** (обходило гард `mEndScrollActive` и убивало анимацию новой вкладки; в коде позиционный `setCurrentSession(landedIndex)`, см. баннер выше) |
| F4 | `SessionPagerManager` | `reconcileActivePage(preferredIndex)` — страж инварианта (см. ниже); вызывается в конце `termuxSessionListNotifyUpdated()`, т.е. после каждого add/remove |
| F5 | `SessionPagerManager` | Пейджерный путь подсветки переведён на `setCurrentSessionForSession(selected)` — **НЕ ВНЕДРЕНО** (в коде `setCurrentSession(landedIndex)`, см. F3) |
| F6 | `SessionPagerManager` | Страховка отложенного пути (`pageView == null`, 300 мс) вместо «погасить флаг» вызывает `recoverUnresolvedPage(pos)`: принудительный rebind слота + повторная перепривязка, как только вьюха появилась |
| F7 | `TermuxDebugCommandReceiver` (debug) | Команда `pagedump` — оракул инварианта |

### 4.2. Страж `reconcileActivePage()`

Три случая, по возрастанию «сломанности»:

* **A. Активной сессии больше нет в списке** (`curIdx == -1`). Выбирается живая сессия
  детерминированно: сессия, занявшая слот закрытой вкладки (`preferredIndex`, с клампом к новому
  списку), иначе — текущая страница. Пейджер переводится на неё без анимации, выполняется штатная
  пер-сессионная бухгалтерия. **Это и есть гарантия «никогда не остаться в убитой сессии»** — она не
  зависит от того, сработал ли `setCurrentItem` и что сделал RecyclerView.
* **B. Пейджер стоит не на странице активной сессии** (список сдвинулся под ним) — переставляется по
  сессии, а не по позиции.
* **C. Страница занята не той сессией** — сначала спрашивается `getDisplayedView()` (что на экране):
  если слот показывает чужую сессию (обычно — только что закрытую), слот принудительно
  перевязывается (`rebindPage`), и после привязки бухгалтерия выполняется повторно; если слот ещё не
  разложен — проверяется карта.

На здоровом пути метод читает два индекса и одну идентичность сессии и ничего не делает.

### 4.3. Что осознанно **не** менялось

* **Правило выбора соседа при закрытии** оставлено прежним (сессия, занявшая слот закрытой вкладки;
  для последней вкладки — новая последняя). Менять «куда перекидывает» пользователь не просил, а
  любое изменение здесь — отдельное поведенческое решение.
* **Порядок `updateTabs()` → пейджерная синхронизация** в `TermuxActivity.termuxSessionListNotifyUpdated()`
  сохранён: он нужен пути добавления вкладки (`scrollStripToEnd()` обязан выставить резерв
  end-scroll до колбэков пейджера). Устаревший комментарий в `SessionPagerManager`, утверждавший
  обратный порядок, исправлен — он и был ловушкой для будущих правок.
* **Хот-путь `getPagerPageView()`** (карта раньше `findViewHolderForAdapterPosition`) не тронут:
  карта нужна именно в окне, когда ViewHolder ещё не разложен (свайп), и на ней держится
  IME/маршрутизация ввода. `getDisplayedView()` используется только как валидатор/ремонт.

## 5. Проверка на устройстве (когда телефон подключён)

```bash
ADB="C:/Users/Nikita/AppData/Local/Android/Sdk/platform-tools/adb.exe"
"$ADB" mdns services                 # IP динамический
"$ADB" connect <ip>:5555
"$ADB" logcat -c
# сценарий: 4 вкладки → 3-я → закрыть → закрыть 2-ю
for i in 1 2 3; do "$ADB" shell am broadcast -n com.termux.debug/com.termux.app.TermuxDebugCommandReceiver --es cmd new_tab; done
"$ADB" shell am broadcast -n com.termux.debug/com.termux.app.TermuxDebugCommandReceiver --es cmd switch_tab --es arg 2
"$ADB" shell am broadcast -n com.termux.debug/com.termux.app.TermuxDebugCommandReceiver --es cmd pagedump
"$ADB" shell am broadcast -n com.termux.debug/com.termux.app.TermuxDebugCommandReceiver --es cmd close_tab
"$ADB" shell am broadcast -n com.termux.debug/com.termux.app.TermuxDebugCommandReceiver --es cmd pagedump
"$ADB" logcat -d -s TIPanelCmd | grep -E "PAGEDUMP|recv:"
```

Критерии:

* **здоровое состояние после закрытия:** `curIdx == pager`, `displayedCur == activeCur == liveCur`,
  и это хендл сессии по индексу `curIdx`;
* **баг (до правки):** `curIdx == -1` (активная сессия мертва) и/или `displayedCur` = хендл убитой
  сессии, тогда как полоса вкладок подсвечивает соседа;
* A/B: правка отключается в одну строку (например, `false &&` перед вызовом
  `reconcileActivePage(...)`), сборка ставится на устройство только когда пользователь **не** тестирует
  (урок 19.09: не оставлять сломанную A/B-сборку на телефоне).

**Важно про `close_tab`:** ресивер вызывает `removeFinishedSession(currentSession)` напрямую, минуя
100-мс анимацию закрытия (`animateTabClose`/`removeClosingTab`). Для проверки именно пользовательского
пути (тап по «×») нужен реальный тап по координатам кнопки закрытия либо временный вызов
`TermuxSessionTabsController.closeSession()`. Разница существенна: анимация снимает вьюху вкладки
**до** изменения списка сессий, и именно в этом окне расходятся источники истины.

## 6. Что осталось подтвердить

1. `pagedump` на устройстве в сценарии пользователя — чтобы назвать конкретное звено (D3/D4) в его
   проходе, а не только класс.
2. Глазами: закрытие средней вкладки при поднятой клавиатуре (инвариант не должен ломать IME-логику

3. Прогон соседних сценариев: закрытие последней вкладки, закрытие не-текущей вкладки (сессия

   закрытия (end-scroll не должен «дёрнуться» из-за повторной бухгалтерии).

## 7. Второй проход: почему первая версия не помогла

Пользователь сообщил «не исправлено». Разбор второго прохода нашёл три дефекта в самой обвязке
инварианта — то есть страж был, но **мог не выполняться или проверять не то состояние**.

### 7.1 Страж стоял ВНУТРИ условия, которое само было неверным

```java
int newSize = service.getTermuxSessionsSize();
if (mTerminalPagerAdapter.getItemCount() != newSize) {   // <-- здесь
    int oldSize = mTerminalPagerAdapter.getItemCount();
    ...
    reconcileActivePage(preferredIndex);                  // <-- и страж здесь же
}
```

`getItemCount()` включает **плейсхолдер правого свайпа**, а `newSize` — только реальные сессии. Два
следствия:

1. Когда плейсхолдер взведён (а он взводится, как только ты попадаешь на **последнюю** вкладку — а
   именно туда и приводит закрытие предыдущей), числа расходятся на единицу всегда, и любое
   same-size обновление (обновление заголовка, снапшот) прогоняло весь структурный путь: сбрасывало
   и заново взводило плейсхолдер.
2. Обратный случай хуже: пока адаптер держал **живой** список сервиса, числа были равны **всегда**,
   и настоящее добавление/удаление пропускало весь блок целиком — без диффа, без уведомления и **без
   стража**.

**Исправлено:** сравниваются реальные счётчики — `TerminalPagerAdapter.getSessionCount()` (новый
метод) против `service.getTermuxSessionsSize()`.

### 7.2 Адаптер мог держать живой список сервиса

`TermuxService.getTermuxSessions()` возвращает **внутренний** список (`mShellManager.mTermuxSessions`),
а сервис вырезает из него сессию на месте (`onTermuxSessionExited` → `remove`). Конструктор адаптера
присваивал эту ссылку напрямую:

```java
this.mSessions = sessions;   // тот же объект, что у сервиса
```

Тогда `oldSize` и `newSize` — **один и тот же объект**, сравнение всегда «равно», и весь дифф молча
пропускается: `notifyItemRangeRemoved` не вызывается, пейджер не убирает закрытую страницу, а полоса
вкладок (перестраиваемая из того же живого списка) подсвечивает правильный таб. Это ровно сообщённый
симптом.

**Важно:** в обычном холодном старте `setup()` вызывается из `onCreate`, когда сервис ещё не подключён,
и адаптер получает пустой `ArrayList` — то есть этот дефект **не обязан** срабатывать. Но он реальный:
любой путь, где адаптер создаётся при уже подключённом сервисе, попадает в него.

**Исправлено:** конструктор делает снимок — `new ArrayList<>(sessions)`.

### 7.3 Страж проверял состояние ДО раскладки (главное)

`notifyItemRangeRemoved()` только **ставит изменение в очередь** (`AdapterHelper.mPendingUpdates`) и
просит перераскладку. Смещения позиций ViewHolder'ов и собственно раскладка происходят в следующем
layout-проходе. А `reconcileActivePage()` вызывался синхронно, сразу после — то есть смотрел на
**до-layout** картину. Проход мог увидеть согласованное состояние, а затем раскладка ставила на экран
другой ViewHolder — и починить это было уже некому.

**Исправлено:** инвариант стал двухпроходным.

* `enforceActivePageInvariant(preferredIndex)` — синхронный проход, как раньше (случаи A/B/C).
* `verifyVisiblePageIsLive()` — **posted** (`mTerminalPager.post`), выполняется после раскладки и
  задаёт единственный вопрос, который важен пользователю: **привязан ли TerminalView, реально
  находящийся на экране, к сессии, которая жива и всё ещё в списке?** Если нет — страница
  перепривязывается на сессию, которую разрешает индекс пейджера. Проход пропускается, если пейджер
  не в IDLE, поэтому он не может воевать со свайпом пользователя.

Плюс при срабатывании пишется предупреждение в logcat (тег `SessionPagerManager`) — именно оно
подтвердит, ловится ли состояние стражем:

```
Active page N is bound to a session that is not the live one
(shown=<handle>, expected=<handle>, sessions=N); rebinding the page ...
```

### 7.4 Заодно: закрытие НЕ-текущей вкладки больше не двигает пользователя

Ветка `preferredIndex >= 0` выбирала слот закрытой вкладки **всегда**, даже если закрывали фоновую
вкладку — то есть пейджер переезжал на соседа той вкладки, которую пользователь не трогал. Теперь
приоритет такой: остаться на текущей сессии, если она пережила удаление; и только если закрыли
**текущую** — переехать в её слот (правый сосед, а для последней вкладки — новая последняя).

## 8. Как подтвердить/опровергнуть на устройстве (одна строка)

```bash
adb logcat -c
# ...воспроизвести: 4 вкладки → 3-я → закрыть → закрыть 2-ю...
adb logcat -d -s SessionPagerManager:W
```

* **Строка есть** → страж сработал и починил состояние: привязка страницы была неверной, теперь это
  исправляется на лету. Если визуально всё равно плохо — значит сломан не источник состояния, а
  раскладка/скролл пейджера, и копать надо туда (это другой класс дефекта).
* **Строки нет, а симптом есть** → состояние четырёх источников согласовано, и «мёртвый экран» —
  это не рассинхрон состояния. Тогда следующий шаг — `pagedump` (см. §5) плюс `dumpsys activity`
  по окну: смотреть, какая вьюха реально нарисована и на какой позиции.

## 9. Проход 3: регрессия «при открытии новой вкладки выбирается предыдущая»

Пользователь: **«не исправлено и стало ещё хуже»**. Регрессию внёс проход 2, и она же объясняет,
почему проход 1 не дал эффекта: виноват был **источник истины**, которым я пользовался.

### 9.1 Механизм регрессии (подтверждён по коду)

Страж брал «активную сессию» из `TermuxActivity.getCurrentSession()`, а это **кэш `mTerminalView`**,
который на переходе **отстаёт по построению**:

1. `newSize > oldSize` → `restoreIndex = newSize - 1` (новый таб) → `setCurrentItem(restoreIndex, false)`.
2. `onTerminalPageSelected(restoreIndex)` → `getPagerPageView(restoreIndex)`. Новая страница ещё не
   разложена, а **в карте позиций на этом индексе лежит устаревшая запись плейсхолдера** (см. §9.3) —
   либо запись отсутствует. Тогда метод уходит в **отложенную** ветку «ждать attach» и **не**
   переставляет `mTerminalView`: он всё ещё указывает на **предыдущую** сессию.
3. Страж (проход 2) видел `activeIndex` предыдущей сессии и в **Case B** «исправлял» пейджер:
   `mTerminalPager.getCurrentItem() != activeIndex` → `selectPage(activeIndex)` → **возврат на
   предыдущую вкладку**.

Усугублял `getCurrentItem()`: при `setCurrentItem(item, false)` ViewPager2 делает
`mRecyclerView.scrollToPosition(item)` и обновляет `mCurrentItem` **лениво**, уже при обработке
скролла. То есть сразу после вызова `getCurrentItem()` может ещё возвращать **старый** индекс — и
Case A, у которого `target` брался из `getCurrentItem()`, выбирал ровно предыдущую вкладку.

### 9.2 Исправление: авторитет — это индекс, который мы только что выбрали

* `reconcileActivePage(int selectedIndex)` — на вход идёт **`restoreIndex`**, то есть страница,
  которую этот же синк только что запарковал. Не `preferredIndex` и не `getCurrentItem()`.
* **Case B удалён полностью.** Он и был регрессией: превращал отставание кэша в видимый прыжок.
  Отстающий кэш — это симптом, который надо **чинить**, а не источник истины, по которому надо
  рулить.
* **Case A** (сессия выпала из списка) теперь берёт `target = selectedIndex`, клампит и вызывает
  `selectPage(target)` — а тот заново прогоняет `onTerminalPageSelected()`, то есть **чинит сам
  отстающий кэш**.
* **Case C** сужен: только `getDisplayedView()` (ответ RecyclerView), и **только если вью реально
  разложена**. `null` = страница ещё не разложена → это transitional-состояние, им владеет отложенная
  ветка `onTerminalPageSelected()`, и лезть туда синхронно нельзя. Фолбэк на `getPagerPageView()`
  (собственную карту) убран: именно она и врёт.
* **Posted-проход** `verifyVisiblePageIsLive()` сужен до одного состояния, которое действительно
  нельзя показывать: **на экране вью, привязанная к сессии, которой больше нет в живом списке**.
  Он не сравнивает с кэшем активности (кэш отстаёт) и не чинит «ещё не привязанную» страницу
  (`shown == null` → выход). Именно поэтому он не может ни увести выбор, ни подраться с переходом.

### 9.3 Заодно: устаревшая запись плейсхолдера в карте позиций

`syncWithServiceList()` сбрасывал плейсхолдер через `notifyItemRemoved(mSessions.size())`, но
**не удалял запись из `mAttachedViews`**. Карта ключуется **позицией**, а не ViewHolder'ом, поэтому
слот продолжал резолвиться в мёртвую вьюху плейсхолдера (у неё нет сессии). Дальше `getAttachedView()`
на этом индексе отдавал плейсхолдер вместо реальной страницы: активная вью активности указывалась на
вью **без сессии**, и ввод/IME уходили в никуда до ручного переключения вкладки. Это и есть шаг 2
механизма из §9.1. Добавлено `mAttachedViews.remove(mSessions.size())` перед `notifyItemRemoved`.

### 9.4 Итог по проходам

| Проход | Что было не так | Статус |
|---|---|---|
| 1 | Страж был, но его выводы не проверялись на устройстве | снят |
| 2 | Страж стоял внутри неверного условия (`getItemCount()` считает плейсхолдер); адаптер мог держать живой список сервиса; страж смотрел состояние до раскладки | исправлено |
| 2 → 3 | Страж рулил по **отстающему кэшу** `mTerminalView` (Case B) ⇒ возврат на предыдущую вкладку при добавлении таба | Case B удалён, вход = `restoreIndex` |

Гейты прохода 3: `:app:compileDebugJavaWithJavac --offline --rerun` и `:app:assembleDebug --offline`

**Что важно проверить глазами (это и есть критерий приёмки):**
1. «+» / свайп справа → активной становится **новая** вкладка, не предыдущая.
2. 4 вкладки → 3-я → закрыть → закрыть 2-ю: ни разу не остаёшься на терминале с `signal 9`.
3. Закрытие **не-текущей** вкладки не двигает тебя с текущей.
