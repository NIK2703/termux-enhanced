# Аудит системы отрисовки терминала — 5

**Дата:** 2026-09-11
**Предмет:** `TerminalView.onDraw()` → `TerminalRenderer.render()` → `TerminalBuffer` / `TerminalRow`
**Статус предыдущих работ:** A1–D1 (`glyph-scroll-optimization.md`), E1–E6 (`…-2.md`),
F0–F7/T8 (`…-3.md`), G1–G7 (`render-optimality-audit-4.md`) — **все внедрены**.

Этот документ отвечает на два вопроса: **насколько система оптимальна сейчас** и **что ещё
имеет смысл оптимизировать**. Он опирается на (а) чтение текущего кода, (б) замеры стенда из
предыдущих аудитов и (в) **новые замеры на устройстве**, которых раньше не было.

---

## 1. Короткий вывод

1. **Скан строки больше не является узким местом.** G1–G5 срезали его с 16.6 до 5.6 µs/кадр на
   стенде. Это единицы процентов кадра. Дальнейшая микрооптимизация цикла колонок **не окупается**.
2. **Узкое место — путь отрисовки (submit + GPU).** На потоковом выводе полный перерисов плотного
   экрана стоит **p50 9 мс, из них GPU 6 мс**. Бюджет кадра при 120 Гц — **8.33 мс**. То есть
   полный перерисов **не влезает в 120 Гц** с запасом; запас отрицательный на p50.
3. **Следующая крупная возможность — не в рендерере, а в эмуляции.** `TerminalEmulator.append()`
   выполняется на главном потоке для каждого 64-КиБ чанка и **не коалесится по кадрам** —
   коалесится только перерисовка. Под нагрузкой это и есть источник хвоста 15–17 мс и
   `High input latency`.
4. Всё «дешёвое и структурное» уже выбрано. Остались либо вещи на доли процента, либо работа,
   требующая профилировщика GPU, либо вынос эмуляции с главного потока.

## 2. Что проверено и уже оптимально (не трогать)

Важно зафиксировать это явно — половина «очевидных» оптимизаций здесь уже сделана или
неприменима.

| Место | Факт |
|---|---|
| `TerminalBuffer.scrollDownOneLine()` | При **полноэкранном** скролле оба `blockCopyLinesDown()` получают `len == 0` и выходят сразу (`:543`). Скролл = `mScreenFirstRow++` + `mActiveTranscriptRows++` + `clear()` одной строки + `markInternalRowDirty()` одной строки. **O(1)**, ни одна строка не копируется. |
| Коалесинг перерисовки | `TerminalSession.notifyScreenUpdateCoalesced()` → один `Choreographer.postFrameCallback` на кадр (`:237-250`). Сколько бы чанков ни пришло за 8 мс — `onScreenUpdated()` один. |
| Прокрутка в истории при потоке вывода | `repaintAfterUpdate()`: `first > last` → только `invalidateScrollbarBand()` (`:1078-1088`), а тот сам выходит, если бегунок не сдвинулся (`:1128`). **Ноль перерисованных строк.** |
| Аллокации в кадре | `mClipBounds`, `mThumbRect`, `mScratchColumnAndRow`, все 13 run-массивов — поля и переиспользуются. `computeThumbRect()` пишет в `mThumbRect` (`:2124`). `getLineOrBlank()` отдаёт общую blank-строку и в `onDraw` не аллоцирует (`:666-674`). **Ноль аллокаций на кадр.** |
| Двойной фон | Лейауты и тема используют `@android:color/transparent`; `TerminalView.isOpaque()` возвращает `true` при выключенной прозрачности (`:1326`). Лишнего непрозрачного слоя под сеткой нет. |
| Ранняя разбивка на раны | B4 (дедуп сеттеров paint), C2 (два paint'а под два xfermode), F0 (обрезка хвостовых пробелов), A2 (blank-uniform), G4 (merge по разрешённому цвету) — всё на месте. |

## 3. Замеры на устройстве (новое)

**Стенд:** POCO F5 (`marble`), LineageOS, 1080×2400, режимы 60/90/120 Гц.
**Метод:** `dumpsys gfxinfo com.termux reset` → нагрузка → `dumpsys gfxinfo com.termux`.
Кадровые времена — это `FrameMetrics` (UI-поток + RenderThread до презентации), отдельно даётся
GPU-время. **Оговорка:** gfxinfo квантует кадр по vsync, поэтому «p50 5 мс» может означать
«работа ~1 мс, презентация в тот же vsync».

### 3.1. Жест (флинг), 3 свайпа

| Метрика | Значение |
|---|---|
| Кадров | 420 |
| p50 / p90 / p95 / p99 | **5 / 8 / 15 / 17 мс** |
| GPU p50 | 2 мс |
| Janky | 8 (1.90 %) |
| Missed Vsync | 0 |
| Slow UI thread / slow issue draw commands | 1 / 4 |

### 3.2. Потоковый вывод (`cat` файла 3.16 МБ, 40 000 строк)

| Метрика | Значение |
|---|---|
| Кадров | 76 |
| p50 / p90 / p95 / p99 | **9 / 17 / 18 / 20 мс** |
| GPU p50 | **6 мс** |
| Janky | 16 (21.05 %) |
| Slow UI thread / slow issue draw commands | 0 / 5 |

### 3.3. Накопленно за жизнь процесса (13.5 ч, в основном простой)

| Метрика | Значение |
|---|---|
| Кадров | 14 792 |
| p50 / p90 / p95 / p99 | 6 / 11 / 13 / 21 мс |
| Janky | 855 (5.78 %) |
| High input latency | 2148 (14.5 %) |

### 3.4. Как это читать

* **p50 5 мс у флинга занижен.** `runFlingFrame()` вызывает `doScroll()` только когда скролл
  перешагнул **целую строку** (`:1603`). Кадры, где строка не перешагнулась, ничего не
  инвалидируют → в них не рисуется ни одной строки. Медиана разбавлена этими «пустыми» кадрами.
* **p50 9 мс у потока — честная цена полного перериса плотного экрана.** 48 строк × ~70 глифов,
  каждая строка = полный перерис (якорь сдвинулся → `invalidate()` → `dirtyRect == null` →
  E2-скип не работает).
* **GPU 6 мс против 2 мс.** Разница ≈ трёхкратная. 1080×2400 = 2.6 Мпикс; при ~1.3 Гпикс/с один
  полный проход заливки ≈ 2 мс. Значит на потоке GPU делает **примерно три полных прохода** —
  это перерисовка поверх перерисовки (overdraw), а не стоимость глифов.
* **Вывод:** при 120 Гц (8.33 мс) полный перерис на p50 уже **не влезает**. Жест остаётся плавным
  только потому, что дисплей большую часть времени идёт на 60 Гц (16.67 мс) — тач-буст держится
  около секунды после отрыва пальца.

## 4. Где сейчас время в кадре

Оценка по совокупности замеров (доли — оценочные, порядок величины надёжен):

| Компонент | Оценка | Комментарий |
|---|---|---|
| Скан колонок (split на раны) | **единицы %** | 5.6 µs/кадр на стенде; на устройстве ~30–55 нс/клетку × 3840 клеток ≈ 0.1–0.2 мс |
| Submit draw-команд | ~1–2 мс | ~48 `drawTextRun` + фон + скроллбар |
| GPU | **~2–6 мс** | зависит от overdraw; см. §3.4 |
| Эмуляция (`append`) | **не ограничена кадром** | выполняется на главном потоке на каждый чанк, вне коалесинга |
| Прочее (Choreographer, SF, vsync-квантование) | ~2–3 мс | видно по тому, что p50 даже у пустых кадров 5 мс |

**Ключевое следствие:** дальше оптимизировать имеет смысл **submit/GPU и эмуляцию**, а не цикл
колонок.

## 5. Что осознанно не делаем

| Идея | Почему нет |
|---|---|
| **Кэш ранов по версии строки** (A4) | Экономит то же, что T8/G3, но ценой 5 ключей инвалидации нового состояния. Уже закрыто в `…-3.md`. |
| **Scroll-blit (сдвиг готовых пикселей канвы)** | (1) При полноэкранном скролле меняется содержимое **всех** видимых позиций, так что работа не избыточна. (2) В HWUI нет read-back канвы; блит требует собственного `Bitmap`-бэкенда, а это уводит растеризацию текста с GPU в софт — на 48 плотных строках это заведомый минус. (3) Сам скролл уже O(1) (§2). |
| **`drawPath()` для батчинга фонов** | Уже отвергнуто ранее: путь записывается в display list и проигрывается после `onDraw()`, что хрупко на части драйверов. |
| **Замена T8-скана хвоста на `mStyleUniformFrom`** | Формально корректно (`getStyleUniformFromColumn()` — консервативная верхняя граница начала хвоста, O(1)), но на разреженных строках (запись только у правого края) даёт **хуже**, чем скан, а сам скан — это 3840 сравнений символов на кадр ≈ 0.1 % кадра. **Не окупается.** |
| **Микрооптимизация `TerminalRow.getStyle()`** | Это `mStyle[column]` — обычное чтение массива, `final`-метод, инлайнится. Трогать нечего. |

## 6. Оставшиеся возможности

### H1 — Полноэкранная заливка в режиме `SRC` — только когда нужна прозрачность
**Где:** `TerminalRenderer.java:387` — `canvas.drawColor(bgColor, PorterDuff.Mode.SRC)`.

Режим `SRC` нужен ровно для одного: чтобы полупрозрачная заливка при **частичной** перерисовке не
накапливала альфу поверх пикселей прошлого кадра. Но эта строка выполняется **только при
`dirtyRect == null`**, то есть на полном перерисе, где предыдущее содержимое поверхности
несущественно. При `mBackgroundAlpha >= 255` (дефолт) цвет непрозрачный, и `SRC_OVER` даёт
**пиксельно идентичный** результат, зато позволяет HWUI уйти на быстрый путь «clear без
блендинга» вместо полноэкранного прохода со сменой режима.

* **Выигрыш:** оценочно 0.5–2 мс GPU на полном перерисе — то есть ровно тот дефицит, который
  мешает влезть в 120 Гц.
* **Риск:** низкий. Инвариант сохраняется, если оставить `SRC` при `mBackgroundAlpha < 255`.
* **Проверка:** флип режима + повторный `dumpsys gfxinfo reset` на том же `cat`. 10 минут.

### H2 — Профиль GPU, а не догадки
**Что:** снять Perfetto/`systrace` с треками `gfx`/`view` на сценарии `cat big_file` и посмотреть,
из чего состоят 6 мс GPU: полноэкранные заливки, глифы или скроллбар.

* **Зачем:** §3.4 показывает ~3 полных прохода заливки. Пока не видно, какие именно, любые правки
  draw-пути — лотерея. Это **предусловие** для H1 и любых дальнейших правок отрисовки.
* **Риск:** нулевой (только измерение).

### H3 — Убрать деление из общего пути `drawRunText`
**Где:** `TerminalRenderer.java:994` — `mes = mes / mFontWidth;` выполняется **всегда**, хотя
результат используется только внутри `if (fontWidthMismatch && …)` на `:996`.

Перенести внутрь ветки. Одно деление с плавающей точкой на ран на строку (≈150/кадр) исчезает из
общего пути. **Выигрыш:** доли процента. **Риск:** нулевой (чистый перенос).

### H4 — Кэшировать `decodeEffect` на ран
**Где:** `TextStyle.decodeEffect(mRunStyle[…])` вызывается в `runsMerge()` (`:897`, дважды на
сравнение), в блоке хвостового рана (`:758`) и в `drawRunText()` (`:984`).

Завести `mRunEffect[]`, заполняемый один раз в `addRun()`. **Выигрыш:** 2–3 декода на ран на
строку. **Риск:** низкий, но состояние растёт (14-й массив). Стоит делать только вместе с H5.

### H5 — Ранний выход в `drawRunText` для обрезанных ранов
**Где:** `TerminalRenderer.java:978-1100`. После F0 ран может иметь `runWidthChars == 0` — тогда
рисуется только курсор/фон. Сейчас всё равно считаются `effect`, пять булевых флагов,
`left`/`right` и деление.

Переставить так, чтобы разбор стиля выполнялся только когда текст реально рисуется
(`runWidthChars > 0 && !INVISIBLE`). **Выигрыш:** доли процента. **Риск:** низкий.

### H6 — Эмуляция не коалесится по кадрам  ← **самая крупная оставшаяся возможность**
**Где:** `TerminalSession.java:367-371`.

```java
int bytesRead = mProcessToTerminalIOQueue.read(mReceiveBuffer, false);
if (bytesRead > 0) {
    mEmulator.append(mReceiveBuffer, bytesRead);   // ← не коалесится
    notifyScreenUpdateCoalesced();                 // ← коалесится
}
```

Коалесится **только перерисовка**. Разбор байтов (`TerminalEmulator.append` → `TerminalBuffer.setChar`
→ `TerminalRow.setChar`, включая прокрутки) идёт на главном потоке на **каждый** чанк. При
`cat` большого файла это десятки тысяч `setChar` подряд в одном кадре: главный поток занят
разбором, кадр не начинается, и мы получаем ровно то, что видно в статистике —
`High input latency: 2148` (14.5 %) и хвост кадров 15–17 мс.

Два направления:
* **(а) Байтовый бюджет на кадр.** Обработать не больше N КиБ за один vsync-интервал, остаток
  отложить на следующий. Плавность в обмен на пропускную способность. Локально, без смены модели
  потоков. Начать стоит с этого.
* **(б) Вынести разбор в отдельный поток** с синхронизацией доступа к буферу. Радикально, но
  ломает текущий инвариант «весь доступ к dirty-состоянию и буферу — с главного потока»,
  задокументированный в `repaintAfterUpdate()` (`:1013-1024`). Требует отдельного проекта.

**Выигрыш:** это единственная позиция, способная убрать хвост 15–17 мс, а не доли процента.
**Риск:** средний (а) / высокий (б).

### H7 — Прозрачность окна при выключенной прозрачности фона
**Что:** тема держит `android:windowBackground = @android:color/transparent`, чтобы работали обои
за терминалом. При `mBackgroundTransparencyPercent == 0` (дефолт) это заставляет композитор
блюрить окно целиком, хотя содержимое непрозрачно.

**Что проверить:** действительно ли SF не может композитить слой как непрозрачный (у
`TerminalView.isOpaque()` уже возвращается `true`, так что HWUI-сторона в порядке). Если может —
переключать `windowBackground`/флаги окна при включении обоев.

* **Выигрыш:** потенциально ~1 мс GPU, но **не подтверждён**. **Риск:** средний (визуальные
  регрессы с обоями). Делать только после H2.

## 8. Ответ на исходный вопрос

**Насколько оптимальна система сейчас.** Для модели «перерисовать то, что изменилось, каждый кадр»
она близка к пределу: скан выжат до единиц процентов кадра, эмуляция скролла — O(1), частичные
перерисовки работают, аллокаций в кадре нет, «ничего не изменилось» стоит почти ноль. Оценочно
**90–95 % структурного предела** — выше, чем 80–85 % в прошлом аудите, именно за счёт G1–G7.

**Есть ли что оптимизировать.** Да, но уже не в цикле колонок:

1. **GPU-сторона полного перериса** — сейчас ~6 мс из 9 мс кадра, и это не даёт уложиться в 8.33 мс
   при 120 Гц. Первый шаг — H2 (профиль), затем H1.
2. **Эмуляция на главном потоке** — единственный оставшийся источник **крупного** выигрыша
   (хвост 15–17 мс, `High input latency` 14.5 %). Это уже за границей рендерера.
3. Всё остальное — доли процента.

Кратного ускорения в текущей модели не осталось: чтобы получить его, нужно менять модель
(вынос эмуляции или retained-пиксели), а не дописывать оптимизации в `render()`.
