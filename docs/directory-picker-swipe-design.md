> 1. Отпускание **в любой позиции вне строк списка** (нейтральная зона у пальца, полоса подсказки,

## 0. Требование в моей формулировке

Сегодня жест «свайп вправо с крайней правой вкладки» открывает **плейсхолдер-страницу** с
подсказкой «+ новый сеанс» по центру; отпускание на этой странице создаёт сеанс в cwd текущей
сессии.

Нужно превратить этот плейсхолдер в **вертикальный указатель-меню**:

1. В момент, когда плейсхолдер начинает появляться, запоминается **вертикальное положение
   пальца** `yA` и больше не меняется до конца жеста.
2. **В точке `yA` нет никакого пункта** — там зазор `gap`, отделяющий палец от списка (§4.7).
3. **Выше** `yA` рисуется список **10 новейших** директорий из истории рабочих директорий
   (`directory_history`, новые первыми), причём **новейшая — на нижней строке, у пальца**. Список
   упирается низом в `yA - gap` и растёт вверх по мере движения пальца вниз. Размещения вниз нет.
4. Подсказка «+ новый сеанс» стоит **всегда выше списка** — по центру свободной полосы между
   списком и верхней границей страницы. Она означает «новый сеанс в рабочей директории по
   умолчанию» (`default-working-directory` из настроек).
5. Если сверху не помещается столько пунктов, сколько есть в истории, список **усекается по числу
   пунктов**, отбрасывая самые старые; высота строки при этом не меняется. Если не помещается даже
   одна строка — список не показывается вовсе, и подсказка **центрируется по странице** (§4.2).
6. Список после появления **неподвижен**. Пользователь, не отпуская палец, ведёт его вверх/вниз;
   **отпускание выбирает ту строку, напротив которой по вертикали стоит палец**. Горизонтальная
   координата пальца игнорируется полностью (палец физически находится над последней вкладкой,
   а не над плейсхолдером — см. §3.4).
7. **Отпускание в любой позиции вне строк списка** — зазор у пальца, полоса подсказки, пустота
   над списком и всё, что ниже пальца — открывает сеанс в **рабочей директории по умолчанию**.
   Других исходов у жеста нет: это всегда «новый сеанс в какой-то директории».

Итог: жест всегда создаёт сессию — либо в конкретной директории из истории, либо в директории по
умолчанию. Отмены «в никуда» не существует.

Ключевое следствие: **выбор определяется положением пальца в момент `ACTION_UP`, а не фактом
доведения свайпа до конца**. Значит, коммит сессии обязан произойти *после* `ACTION_UP`, но
*раньше*, чем пейджер завершит settle (сегодня коммит висит на `onPageSelected`, который
срабатывает в начале settle) — иначе список исчезнет до того, как пользователь успеет выбрать.

## 2. Сценарий взаимодействия

```
[последняя вкладка] --свайп вправо--> плейсхолдер появляется
                                      │
                                      ├─ фиксируем yA (вертикаль пальца в этот кадр)
                                      ├─ считаем rows = сколько строк влезает выше yA (0…10)
                                      └─ рисуем подсказку «+ новый сеанс» над списком;
                                         при rows == 0 — только подсказку, по центру страницы
                                      │
              палец (не отпуская) едет вверх/вниз ──► подсветка строки под пальцем
                                      │
                       ACTION_UP ─────┴──► строка под пальцем = директория из истории
                                           иначе               = директория по умолчанию
                                              │
                        пейджер доезжает до плейсхолдера (settle)
                                              │
                        onPageSelected(placeholderIndex) → создаём сессию в выбранной директории
```

Палец **не отпускается** между появлением списка и выбором — это одно непрерывное движение:
вправо (раскрыть) + вверх/вниз (прицелиться) + отпустить.

## 3. Захват жеста и якоря

### 3.1. Куда вешать слушатель

| Хук | Видит `DOWN` | Видит `UP` | Проблема |
|---|---|---|---|
| `TerminalView` (GestureAndScaleRecognizer) | да | да | палец может стартовать над плейсхолдером/оверлеем; логика размазана по чужому классу |
| `PagerOverscrollController` (EdgeEffect-спай) | нет | косвенно (`onRelease`) | это не поток касаний, а unconsumed-дельта; координат Y нет вообще |
| `pager.setTouchListener` / `ViewPager2.OnTouchListener` | нет | нет | `FrameLayout` не перехватывает, пока ребёнок потребляет события |
| **`pagerRecyclerView.addOnItemTouchListener(...)`** | **да** | **да** | — |

Берём `OnItemTouchListener`. Это сработает: `TerminalView` выставляет
`requestDisallowInterceptTouchEvent(true)` **только** при вертикальном разборе жеста
(`TerminalView.java:573-577`), а при горизонтальном (`SCROLL_AXIS_HORIZONTAL`, `:579`) — нет.
Значит, для свайпа вправо `RecyclerView.onInterceptTouchEvent` (а с ним и наш
`OnItemTouchListener.onInterceptTouchEvent`) получает **весь поток**, включая `ACTION_DOWN`.

### 3.2. Состояние трекера

```java
// внутри SessionPagerManager
private float mFingerRawY;              // обновляется на каждом MOVE
private boolean mFingerDown;            // DOWN..UP/CANCEL
private boolean mAnchorLatched;         // якорь этого жеста уже зафиксирован
private String mPendingPickDirectory;   // результат ACTION_UP (null = «вне строк»)
private boolean mPendingPickReady;      // выбор этого жеста уже разрешён
private final int[] mPagerLocation = new int[2];   // для rawToPageY, без аллокаций на кадр
```

- `ACTION_DOWN` → `mFingerDown = true`, `mAnchorLatched = false`, `mPendingPickReady = false`,
  `mPendingPickDirectory = null`, `mFingerRawY = e.getRawY()`.
- `ACTION_MOVE` → `mFingerRawY = e.getRawY()`; если якорь уже зафиксирован — `picker.updateFinger()`.
- `ACTION_UP` → `mFingerRawY = e.getRawY()`; если якорь зафиксирован — `picker.resolvePick()` в
  `mPendingPickDirectory`, `mPendingPickReady = true`; `mFingerDown = false`.
- `ACTION_CANCEL` → выбор не разрешать (`mPendingPickReady = false`); `mFingerDown = false`.

Выбор хранится именно **на `ACTION_UP`**, а не читается в момент коммита: к моменту коммита
палец уже поднят, и `mFingerRawY` перестал бы отражать позицию отпускания.

### 3.3. Момент фиксации якоря

Якорь фиксируется **в кадре, когда плейсхолдер начинает появляться** — в `onPageScrolled`, при
первом за жест кадре с `position == realLast && positionOffset > 0` и `mUserScrollInProgress`:

```java
if (mUserScrollInProgress && mFingerDown && !mAnchorLatched
        && position == realLast && positionOffset > 0f) {
    mAnchorLatched = true;
    picker.show(/* anchorY */ rawToPageY(mFingerRawY), /* pageH */ mTerminalPager.getHeight());
}
```

Почему здесь, а не на `ACTION_DOWN`:

- буквальное «в момент появления плейсхолдера»;
- свайп может начаться с вертикального смещения — фиксируем то положение, при котором
  пользователь **увидел** список;
- на практике `yA ≈ downY`, потому что до этого кадра палец проходит лишь несколько процентов
  ширины.

Зачем в условии `mFingerDown`: **флинг**. Если палец уже поднят, а пейджер всё ещё досеивает к
плейсхолдеру, якорь зафиксировался бы по последнему `MOVE`, и на кадр вспыхнуло бы меню, до
которого пользователь физически не может дотянуться. С поднятым пальцем выбор не разрешается
вообще.

Обратный проход (`position == realLast`, offset убывает, возврат на вкладку) якорь не трогает —
`mAnchorLatched` уже `true`; на новом `ACTION_DOWN` он сбрасывается.

### 3.4. Система координат

Пейджер full-bleed, `PagerOverscrollController` двигает RecyclerView **только по X**
(`setTranslationX`), по Y ничего не смещается. Значит:

```java
int[] loc = new int[2];
mTerminalPager.getLocationOnScreen(loc);
float pageY = rawY - loc[1];      // Y в координатах страницы плейсхолдера
```

Горизонталь не нужна нигде: и хит-тест, и отрисовка работают только по Y (это прямо оговорено
в ТЗ — палец горизонтально находится над последней вкладкой).

## 4. Геометрия

### 4.1. Обозначения и константы

| Величина | Смысл | Значение |
|---|---|---|
| `H` | высота страницы (= высота пейджера) | ~2000 px на устройстве 1080×2400 |
| `pad` | безопасный отступ от верхней границы | 8 dp |
| `gap` | зазор между пальцем и низом списка, а также между подсказкой и списком | 12 dp |
| `hintPad` | внутренний отступ подсказки (сверху и снизу её полосы) | 8 dp |
| `hintH` | высота блока «+ новый сеанс» (иконка 48 dp + 8 dp + текст) | ~160 px |
| `n` | сколько директорий предлагает история (не более 10 новейших) | ≤ 10 |
| `rows` | сколько строк реально показывается | 0 ≤ `rows` ≤ `n` |
| `rowH` | высота строки — **фиксированная**, не адаптивная | 48 dp |
| `yA` | зафиксированный якорь (Y пальца в момент появления) | — |

Все величины — в px. Оверлей full-bleed: `terminal-margin-*` на него не влияют.

### 4.2. Единственное размещение — вверх

Размещение ровно одно. Список **всегда** прижат низом к точке `yA - gap`, то есть всегда лежит выше пальца, и растёт вверх по мере того, как палец опускается. Варианта «вниз» больше нет: палец — то, чем указывают, поэтому меню живёт в пространстве, которое палец **не** накрывает, и сторона у него всегда одна.

Сверху от пальца должны уместиться, если идти снизу вверх: зазор `gap` до пальца, сам список, зазор `gap` до подсказки, подсказка высотой `hintH` с отступами `hintPad` и верхний отступ `pad`:

```
availUp = (yA - gap) - pad - gap - (hintH + 2·hintPad)
rows    = min(n, floor(availUp / rowH))
```

`availUp` **резервирует** полосу под подсказку. Без этого резерва список при большом `rows` занял бы всю верхнюю половину страницы и подсказке не осталось бы места — то есть подсказка всегда выводится из позиции списка, а не наоборот.

Если `rows < 1` (в том числе при пустой истории) — списка нет вообще: `Mode.NONE`, показывается только подсказка, **центрированная в вертикальном пространстве страницы**:

```
hintTop = (H - hintH) / 2
```

Это не «вырожденный» случай, а полноценный режим: он же обслуживает пустую историю, и он же — исход, к которому список сходится, когда палец поднимается выше порога (на эталонной странице — выше `yA ≈ 436`).

### 4.3. Фиксированная высота строки и обрезка по числу пунктов

```
rowH = ROW_HEIGHT_DP = 48 dp          // константа, не зависит от места
rows = min(n, floor(availUp / rowH))  // единственная формула
```

**Строки не сжимаются и не растягиваются.** Высота строки — константа, поэтому «список длиннее места» решается единственным способом: **сокращается число пунктов**. `rows` — это сколько новейших директорий помещается над пальцем; остальные (самые старые) в этот раз просто не предлагаются.

Отсюда инварианты:

- `rowH == ROW_HEIGHT_DP` — всегда;
- `rows ≤ n`;
- `listTop ≥ pad + (hintH + 2·hintPad) + gap` — верхняя граница списка никогда не заходит в полосу подсказки.

48 dp — как в существующем popup истории (15 sp текст + вертикальные отступы ≈ 40 dp, берём с запасом на тап-таргет).

### 4.4. Позиция списка и порядок пунктов

```
listBottom = yA - gap
listTop    = listBottom - rows * rowH
```

`listBottom ≤ yA - gap` — инвариант **по построению**, а не пожелание: список физически не может зайти под палец, и «в точке пальца пусто» выполняется при любом `yA` и любом `n`. Именно поэтому зазор вообще нужен: он отделяет палец от последней строки.

**Новейшая директория — ближе всего к пальцу.** Список приходит из истории в порядке «новые первыми», и для единственного размещения это отображение **переворачивается**: строка `i` (считая сверху) показывает пункт `rows-1-i`. Верхняя строка — самая старая из показанных, нижняя, лежащая у пальца, — самая новая: до неё хватает самого короткого движения.

Отображение живёт в одном месте — `DirectoryPickerLayout.Result#itemIndexAt(row)`, и через него ходят **и** отрисовка, **и** хит-тест. Иначе подсвеченный пункт и выбранный разошлись бы: палец показывал бы на одну директорию, а открывалась соседняя.

Обрезка по числу пунктов (§4.3) отбрасывает **самые старые**: вьюхе передаётся `mItems.subList(0, rows)`, а переворачивается уже порядок отрисовки.

### 4.5. Позиция подсказки

```
band    = listTop - pad                // полоса между списком и верхней границей
hintTop = pad + (band - hintH) / 2     // по центру полосы
```

Ветка «прижать к верхней границе» ушла вместе с режимами: `band ≥ hintH + 2·hintPad` теперь выполняется **по построению** — это ровно тот резерв, который заложен в `availUp`. Единственное исключение — `Mode.NONE`, где подсказка центрируется по странице целиком (§4.2).

Нижнего варианта размещения подсказки нет. Горизонтальное поведение не меняется: существующий `setPlaceholderScrollOffset()` продолжает центрировать её в видимой полосе плейсхолдера (`translationX`); новым является только `translationY`, и он выражается как смещение от центра, потому что центрирование задано `layout_gravity` и на него опирается расчёт `translationX`.

### 4.6. Примеры на устройстве (H = 2000 px, pad = 24, gap = 36, hintH = 160, hintPad = 24, rowH = 132, n = 10)

|---|---|---|---|---|---|
| 1 | 435 | **0** | — | 920 (центр страницы) | не влезает даже одна строка → только подсказка |
| 2 | 436 | 1 | 268…400 | 66 | ровно одна, самая новая |
| 3 | 600 | 2 | 300…564 | 82 | 2 новейшие |
| 4 | 964 | 5 | 268…928 | 66 | 5 новейших |
| 5 | 1300 | 7 | 340…1264 | 102 | 7 новейших |

Свойство, которое видно из таблицы: низ списка всегда на `yA - 36`, а верх колеблется в пределах одной строки — `listTop = 268 + ((yA - 304) mod rowH)`. Подсказка при неполном списке почти не двигается (66…132 px) и уходит вниз только когда список уже максимален: при `rows = n` список перестаёт расти, и весь прирост места уходит в полосу над ним.

### 4.7. Нейтральная зона

Палец **всегда** лежит ниже низа списка: между `listBottom = yA - gap` и самим пальцем гарантирован зазор `gap = 12 dp`. Это и есть нейтральная зона — отпускание в ней (а также выше подсказки, в полосе подсказки и над списком) открывает директорию по умолчанию.

Инвариант «в точке пальца пусто» здесь выполняется **всегда**, в отличие от прежней модели с размещением вниз, где при длинном списке палец оказывался внутри него.

### 4.8. Горизонталь: раскрытие и усечение подписи

Плейсхолдер вползает справа, поэтому в каждый момент на экране виден его левый срез
`[0, offset·W]` (проверено по `setPlaceholderScrollOffset`: `translationX = W·(offset-1)/2`).
Строки рисуются **в канонической, полностью раскрытой геометрии**, а раскрытие применяется как
**горизонтальный сдвиг вьюхи**: `translationX = revealed − W`. Картинка та же, что при рисовании
строк ровно длины среза, но `onDraw` больше не зависит от раскрытия — display list записывается один
раз на жест, а не на каждый кадр, и список не появляется сразу на всю ширину.

Подпись строки выравнивается **по правому краю раскрытой области** и **обрезается границами
контейнера оверлея**. Это не произвольный срез: пока идёт жест, левая граница страницы совпадает с
правой границей соседнего терминала, поэтому отрезанная голова пути читается как уходящая **под
соседний терминал**. Хвост пути — то, что различает директории, — виден с первого же пикселя
раскрытия. Клип — тот же механизм, что и раньше, но теперь он применяется к сдвинутому поддереву:
`clipChildren` родителя выставляет `clipToBounds` рендер-ноде контейнера (`View.java:24878`).

Отсюда же и «без рекомпозиции»: `ellipsize()` не вызывается вообще, ширины подписей меряются
**один раз** на набор пунктов (`setItems` / `premeasure` / смена размера текста) и переиспользуются,
а на кадр приходится только запись свойства рендер-ноды.

| Что | Когда считается |
|---|---|
| сдвиг раскрытия `translationX = revealed − W` | каждый кадр (одна запись свойства рендер-ноды) |
| ширина подписи `measureText` | один раз на набор пунктов (`premeasure`, вне жеста) |
| позиция `x = W - padH - labelWidth` | один раз на жест (геометрия каноническая) |
| усечение текста | **никогда** — обрезает клиппер |

Строки, отброшенные по числу пунктов (§4.3), рисуются нулевой длины — их просто нет в цикле;
никакого пересчёта геометрии при движении пальца не происходит.

### 4.9. Затухание всего содержимого плейсхолдера

Прозрачность теперь применяется к **всему оверлею плейсхолдера** (`terminal_placeholder_hint_container`),
а не только к блоку «+ новый сеанс»: подсказка и список директорий — один слой и приходят/уходят
по одной кривой `alpha = min(1, offset)` — линейной. Вариант `offset · 1.5` откатывался: он
сатурировал на `0.667` и ломал старт затухания с фактической альфы вытягивания. Раньше `setAlpha`
стоял на `_content`; теперь он переехал на контейнер, а на самом `_content` явно выставляется
`alpha = 1`, иначе альфы перемножились бы (`0.5 · 0.5 = 0.25`).

Затухание идёт через `View.setAlpha()`, то есть применяется рендер-нодой на этапе композитинга —
**display list содержимого не пере-записывается**. Уточнение (аудит 1, §4.1): «ни одного лишнего
прохода» верно именно для пере-записи display list, но не для композитинга. У `FrameLayout`
`hasOverlappingRendering()` по умолчанию `true`, поэтому при `alpha < 1` HWUI уходил в
`saveLayerAlpha` **во всю страницу** — offscreen-буфер на каждом кадре жеста. Поэтому у контейнера
стоит `android:forceHasOverlappingRendering="false"`: альфа раскладывается в пейнт каждого вложенного
опа через `AlphaFilterCanvas`, без offscreen-буфера.

При бинде плейсхолдера контейнеру выставляется `alpha = 0`: ViewHolder может создаться уже во время
жеста, и старт с нуля стоит максимум одного невидимого кадра, тогда как старт с единицы дал бы
вспышку полностью непрозрачного оверлея.

### 4.10. Затухание при коммите (150 мс)

Свайп закоммитил новую сессию — оверлей не должен исчезать мгновенно. Раньше он гас в тот же кадр,
что и перепривязка слота, и это читалось как рывок: страница-плейсхолдер пропадала целиком, а под
ней оказывался уже готовый терминал.

Теперь коммит запускает затухание **всего оверлея** за `PLACEHOLDER_FADE_OUT_MS = 150` мс
(`DecelerateInterpolator`), и только по его завершению контейнер уходит в `GONE`. Новый терминал
уже привязан к тому же ViewHolder, поэтому он всё это время виден **под** оверлеем — сессия не
«появляется», а проявляется из-под уходящего плейсхолдера.

Ключевая деталь — **порядок**: `fadeOutPlaceholderOverlay()` вызывается *до* `commitPlaceholder()`,
потому что перепривязка слота выполняется на следующем layout-проходе, и флаг `mPlaceholderFadingOut`
обязан быть поднят к этому моменту. Иначе ветка `onBindViewHolder` для реальной сессии выставила бы
контейнеру `GONE` и съела затухание.

Пока флаг поднят, владельцем видимости и альфы оверлея является анимация, и все остальные пути
держатся в стороне:

| Путь | Что делает при `mPlaceholderFadingOut` |
|---|---|
| `onBindViewHolder` (ветка реальной сессии) | не трогает `visibility`/`alpha` контейнера |
| `setPlaceholderScrollOffset()` | применяет `translationX`, но не переписывает альфу |
| `endPickerGesture()` → `hideDirectoryPicker()` | не вызывает `DirectoryPickerController#hide()` |
| `onViewRecycled()` | отменяет анимацию и снимает флаг (страницу унесли мид-фейд) |

Жёсткий сброс (`hide()`: список очищен, `translationY` подсказки возвращён в 0, вьюха списка
`GONE`) перенесён в **end action** анимации. Именно поэтому во время затухания список и подсказка
остаются ровно там, где их оставил жест, и уходят вместе с контейнером, а не раньше него.

150 мс выбраны так, чтобы затухание укладывалось внутрь settle'а пейджера: к моменту его окончания
страница уже неподвижна, и затухание читается как хвост самого свайпа, а не как отдельная анимация.

Побочный эффект, который пришлось закрыть: если затухание прервано ресайклом, `hide()` до вьюхи не
доходит. Поэтому `DirectoryPickerController#bind()` теперь **всегда** приводит вьюху в чистое
состояние (пустой список, `GONE`) — переиспользованный ViewHolder не может показать строки
предыдущего жеста.

Второй побочный эффект — гонка с ре-армом плейсхолдера. Слот справа пересоздаётся **через кадр**
после коммита, поэтому к моменту end action новый плейсхолдер может быть уже привязан — к другому
ViewHolder, и `DirectoryPickerController` уже привязан к его вьюхам. Поэтому сброс пикера в end
action выполняется только если затухавший контейнер всё ещё текущий:

```java
final boolean stillCurrent = (mPlaceholderHintContainer == container);
if (stillCurrent) mPlaceholderHintContainer = null;
container.setVisibility(View.GONE);
container.setAlpha(1f);
if (stillCurrent) mDirectoryPicker.hide();   // иначе снесём состояние НОВОЙ страницы
```

Контейнер коммитнутой страницы уходит в `GONE` в любом случае — stale-вьюха внутри неё невидима, а
`bind()` всё равно чистит её при следующем использовании.

## 5. Хит-тест и выбор

```java
// DirectoryPickerController
@Nullable
public String resolvePick(float pageY) {
    final DirectoryPickerLayout.Result layout = mLayout;
    if (layout == null) return null;
    final int itemIndex = layout.itemIndexAt(layout.indexAt(pageY));
    return (itemIndex >= 0) ? mItems.get(itemIndex) : null;   // null = «ВСЁ остальное»
}
```

Отдельного enum для исхода нет намеренно: два исхода — это `String` и `null`, и `null` здесь
означает не «ошибку», а полноценный исход «директория по умолчанию». Ветвление происходит ровно
один раз, в `SessionPagerManager#resolvePickDirectory()` (§6).

Хит-тест работает только по **вертикали** — палец во время жеста не может находиться над строками
по горизонтали. Строки, отброшенные обрезкой (§4.3), в хит-тесте не участвуют: `indexAt()`
ограничен `rows`, поэтому отпускание в зазоре под списком (и вообще ниже `listBottom`) — это
«вне строк» и даёт директорию по умолчанию.

**Решения зафиксированы:**

1. **Свободные зоны → директория по умолчанию.** Отпускание вне строк (зазор между низом списка и
   пальцем, полоса подсказки, пустота над списком и всё, что ниже пальца) открывает сессию в
   `getProperties().getDefaultWorkingDirectory()`. Ни «ничего не делать», ни «cwd текущей сессии»
   как исход не существуют: у жеста ровно два исхода — конкретная директория из истории либо
   директория по умолчанию. Перечислять зоны не нужно: всё, что не попало в полосу строки, — это
   default. Такой хит-тест ещё и не имеет мёртвых зон по построению.
2. **Подсветка — только у строк истории.** Блок «+ новый сеанс» не подсвечивается никогда.
   Строка под пальцем подсвечивается акцентной заливкой (та же схема, что в
   `DirectoryHistoryPopupController#updateHighlight`) и обновляется на каждом `ACTION_MOVE` — это
   единственная обратная связь, по которой пользователь целится, поэтому её нельзя откладывать
   до `ACTION_UP`. Отсутствие подсветки у подсказки само по себе информативно: «палец ни на чём →
   сработает директория по умолчанию».
3. **Хаптика** (необязательно). Короткий тик при смене подсвеченной строки — жест «слепой»
   (палец не над списком), тактильная отсечка помогает. Отдельно тикать вход в нейтральную зону
   не нужно.

## 6. Коммит сессии

```
ACTION_UP                       → picker.resolvePick(pageY) → mPendingPickDirectory
                                  mPendingPickReady = true
DRAGGING → SETTLING             → onPageSelected(placeholderIndex)
                                  └─ mUserScrollInProgress == true
                                     → commitPlaceholderToSession()
IDLE                            → endPickerGesture(): mPendingPickReady = false,
                                  mPendingPickDirectory = null, hideDirectoryPicker()
```

Коммит начинается с затухания оверлея (§4.10):

```java
TermuxSession newSession = client.createSessionForPlaceholder(false, null, resolvePickDirectory());
if (newSession == null) { cancelPlaceholder(); return; }

// BEFORE the rebind: onBindViewHolder() runs on the next layout pass and must already see the
// fade flag, otherwise it sets the container GONE and the placeholder vanishes in one frame.
mTerminalPagerAdapter.fadeOutPlaceholderOverlay();

mTerminalPagerAdapter.commitPlaceholder(service.getTermuxSessions(), placeholderIndex);
```

### 6.1. Почему плейсхолдер и новая вкладка — одна страница, а не две

Это не следствие анимации, а свойство структуры. Плейсхолдер — **настоящая страница пейджера**
(`TerminalPagerAdapter` отдаёт `mSessions.size() + 1` элементов, пока `mPlaceholderActive`), и
коммит не переключает страницу, а **переиспользует её**:

| Что | До коммита | После коммита |
|---|---|---|
| Число элементов адаптера | `N + 1` (N сессий + плейсхолдер) | `N + 1` (сессий стало N+1, плейсхолдер снят) |
| Позиция в пейджере | `N` | `N` — **та же** |
| ViewHolder позиции `N` | плейсхолдерный | тот же самый, перепривязанный in-place |
| `TerminalView` позиции `N` | тот же объект | **тот же объект**, теперь с сессией |
| Аниматор элементов | — | `pagerRv.setItemAnimator(null)` — переходов нет by construction |

Три вещи делают это возможным и обязаны сохраниться при любых правках:

1. **`commitPlaceholder()` не трогает счётчик.** `mSessions` заменяется на список сервиса, который
   уже содержит новую сессию, а `mPlaceholderActive` снимается — `getItemCount()` не меняется, и
   ViewPager2 не получает повода пересоздать страницу.
2. **Перепривязка идёт payload'ом** (`notifyItemChanged(idx, PAYLOAD_REBIND)`): без payload
   RecyclerView имеет право пропустить bind для уже привязанного ViewHolder'а, и страница
   осталась бы без сессии.
3. **Плейсхолдер не переставляется синхронно.** `notifyItemInserted` во время коммита заставил бы
   ViewPager2 сделать `snapToPage()` и отмотать пейджер назад; поэтому слот справа ре-армится
   только на следующем кадре в `post()`.

Итог: пользователь видит **одну и ту же страницу**, содержимое которой меняется — оверлей
затухает за 150 мс (§4.10), а терминал новой сессии уже отрисован под ним. Ни слайда, ни
кросс-фейда между двумя страницами не происходит, потому что второй страницы не существует.

`commitPlaceholderToSession` берёт директорию из уже разрешённого выбора:

```java
// SessionPagerManager
private void commitPlaceholderToSession() {
    ...
    TermuxSession newSession = client.createSessionForPlaceholder(
            false, null, resolvePickDirectory());
    ...
}

@NonNull
private String resolvePickDirectory() {
    if (mPendingPickReady && mPendingPickDirectory != null) return mPendingPickDirectory;
    return mActivity.getProperties().getDefaultWorkingDirectory();   // ВСЁ остальное
}
```

`getDefaultWorkingDirectory()` уже подставляет runtime-home вместо compile-time
`TERMUX_HOME_DIR_PATH`, а `createNewSession()` дополнительно прогоняет результат через ту же
подстановку (`TermuxTerminalSessionActivityClient:863`) — двойная подстановка идемпотентна.

Нужный overload (сейчас его нет):

```java
public TermuxSession createSessionForPlaceholder(boolean isFailSafe, String sessionName, String directory) {
    return createNewSession(isFailSafe, sessionName, directory,
            NewSessionSelectMode.CALLER_MANAGED, false, false);
}
```

Существующий двухаргументный метод остаётся тонкой обёрткой с `directory = null` — обратная
совместимость со всеми текущими вызовами сохраняется, но сам жест вправо больше по этому пути
не ходит (он всегда передаёт конкретную директорию).

**Сброс оверлея** обязателен в трёх местах, иначе состояние утечёт между жестами:
`TerminalPagerAdapter#onViewRecycled`, `onBindViewHolder` (ветка не-плейсхолдера) и
`SessionPagerManager#endPickerGesture()` (её же вызывает `cancelPlaceholder()`).

**Что НЕ меняется:** `TerminalPagerAdapter#commitPlaceholder` (in-place rebind), `mUserScrollInProgress`,
резервирование end-scroll в таб-строке, `managePlaceholderForPosition`. Вся механика «плейсхолдер
становится сессией без прыжка» переиспользуется как есть.

## 9. Краевые случаи

| Случай | Поведение |
|---|---|
| История пуста | `n = 0` → `Mode.NONE`, списка нет, подсказка центрируется по странице; отпускание в любом месте = сессия в директории по умолчанию |
| В истории 1–10 записей и места хватает | список из `n` строк, `rowH = ROW_HEIGHT_DP`; история кончилась раньше места — остаток полосы пуст |
| В истории больше 10 | берутся 10 новейших, остальные не показываются вообще (без «ещё N…») |
| Места хватает меньше чем на `n` строк | `rows = floor(availUp / rowH)`, отбрасываются **самые старые**; строка не сжимается |
| `default-working-directory` не задана | свойство возвращает home (с подстановкой runtime-пути), пустой строки не бывает |
| Директория по умолчанию совпадает со строкой истории | не дублируется: в списке её нет, но отпускание на этой строке даёт тот же путь |
| `yA` у верхней границы (выше порога) | `rows = 0` → `Mode.NONE`: только подсказка, по центру страницы |
| `yA` у нижней границы | список над пальцем на всю доступную высоту, подсказка прижата к верхней полосе; между ними широкая пустая полоса |
| Свайп отменён (возврат на вкладку) | `ACTION_UP` → выбор разрешён, но `onPageSelected` на плейсхолдер не сработает → сессия не создаётся; оверлей скрыт |
| `ACTION_CANCEL` (системный жест, звонок) | выбор не разрешается; оверлей скрыт |
| Программный `setCurrentItem` на плейсхолдер | `mUserScrollInProgress == false` → якорь не фиксируется, оверлей не показывается |
| Очень низкая страница (ландшафт, ~350 dp) | `availUp` почти всегда меньше `rowH` → `Mode.NONE`; список появляется только если палец опущен достаточно низко, и тогда состоит из 1–2 строк |
| Прозрачность фона / обои | оверлей обязан использовать цвета схемы с той же альфой, что и фон страницы, иначе на полупрозрачном фоне появится «плашка». Строки рисуем поверх `TerminalView`-заливки без собственного фона |
| Бегунок скроллбара / selection-режим | жест не начинается с этих областей: `TerminalView` перехватывает их до пейджера → оверлей не появится |

## 10. Проверка

### 10.1. Юнит-тесты (без устройства)

`DirectoryPickerLayoutTest` — 21 кейс на чистой функции (`PAGE_H = 2000`, `PAD = 24`, `GAP = 36`,
`HINT_PAD = 24`, `HINT_H = 160`, `ROW_H = 132`). Ключевые инварианты:

- `listBottom == yA - gap` при любом `yA` и любом `n` — «список всегда кончается в одном зазоре над пальцем»;
- **размещения вниз не существует**: ни при каком `yA` список не начинается ниже пальца;
- порог ровно на одной строке: `yA = 436` → `rows == 1`, `yA = 435` → `Mode.NONE` и подсказка в
  центре страницы (`(H - hintH) / 2`);
- `rows == min(n, floor(availUp / rowH))` и `rows ≤ n` всегда;
- `rowH == ROW_H` во всех случаях — высота строки не зависит ни от `n`, ни от `yA`;
- новейший пункт на строке у пальца: `itemIndexAt(rows - 1) == 0`;
- `itemIndexAt` покрывает каждый пункт ровно один раз;
- подсказка всегда выше списка (`hintTop + hintH + hintPad ≤ listTop`) и внутри страницы;
- список внутри страницы при любом `yA ∈ [0, H]`;
- хит-тест: строка под пальцем отдаёт свой пункт; всё вне строк — `-1` (→ директория по умолчанию);
  отброшенные обрезкой строки недоступны; граница `listBottom` исключающая;
- вырожденные входы (`H = 0`, `n = 0`) не падают.

Тесты держатся ради компиляционной дисциплины чистой функции; **метод проверки самой фичи —
только устройство** (§10.2): синтетические прогоны эту функцию не подтверждают.

### 10.2. Проверка на устройстве

Проект уже умеет это делать (см. `android-screen-diff` / `termux-render-device-verify`):

1. **Функционально** — debug-команда `picker <yFrac> <dyFrac>`: программно эмулирует
   `DOWN(yFrac) → MOVE(вправо) → MOVE(dyFrac) → UP`, логирует `Pick` и `mode`. Проверяем матрицу
   `yFrac × dyFrac` и сверяем с таблицей §4.6.
2. **Пиксельно** — скриншот в трёх состояниях (палец сверху / по центру / снизу) и проверка полос:
   `hintTop`, `listTop`, `listBottom` должны совпадать с расчётными с точностью до пикселя.
3. **Живой жест** — `input motionevent` с паузой: DOWN на последней вкладке у правого края,
   несколько MOVE вправо, затем MOVE по вертикали, затем UP. Проверка: создалась сессия в
   выбранной директории (`logcat CHDIR_DEBUG`), а не в cwd текущей.
4. **Регрессия существующего жеста** — при пустой истории: свайп вправо → сессия в директории по
   умолчанию (не в cwd текущей сессии — это осознанное изменение поведения, см. §11).

## 11. Решения и остаток

**Закрыто (ред. 3):**

| Вопрос | Решение |
|---|---|
| Отпускание вне строк списка | **рабочая директория по умолчанию** (`default-working-directory`), без вариантов |
| Подсветка подсказки «+ новый сеанс» | **не подсвечивается** никогда; подсветка только у строк истории |
| Порог «плейсхолдер появился» | **первый пиксель** — `positionOffset > 0` |

**Закрыто (ред. 7 — текущая):**

| Вопрос | Решение |
|---|---|
| Сторона размещения списка | **только вверх**; адаптивное «вниз» удалено целиком |
| Что если сверху не влезает | список усекается по числу пунктов, **вплоть до нуля**; при нуле — подсказка по центру страницы |
| Высота строки | **фиксированная** `ROW_HEIGHT_DP = 48 dp`; не сжимается и не растягивается |
| Порядок пунктов | новейший — на строке у пальца (обратный порядок данных) |
| Обрезка длинных подписей | без рекомпозиции: подпись прижата вправо и уходит под соседний терминал (§4.8) |
| Прозрачность | затухает **весь** оверлей плейсхолдера одной кривой (§4.9) |

**Закрыто (ред. 8):**

| Вопрос | Решение |
|---|---|
| Что происходит с плейсхолдером при коммите | не исчезает мгновенно: **затухание 150 мс**, новый терминал проявляется из-под оверлея (§4.10) |
| Кто владеет видимостью оверлея во время затухания | анимация; bind, `setPlaceholderScrollOffset` и `hide()` в это время в стороне |
| Жёсткий сброс состояния | перенесён в end action анимации; `bind()` дополнительно всегда чистит вьюху списка |

**Осталось решить (не блокирует):**

1. **Текст подсказки.** Сейчас надпись «+ новый сеанс» стоит над областью, которая открывает
   *директорию по умолчанию*, — это может вводить в заблуждение, если пользователь не помнит
   настройку. Вариант: добавить под надписью вторую строку с путём по умолчанию (тогда
   `hintH` растёт на ~20 dp и учитывается в §4.5 автоматически). Требует новой строки в
   `strings.xml` + 12 локалей. Если оставляем одну надпись — правок ресурсов не нужно вообще.

**Осознанное изменение поведения:** сегодня отпускание на плейсхолдере создаёт сессию в **cwd
текущей сессии**. После правки — в **директории по умолчанию**. Для пользователя, у которого
`default-working-directory` пуста (то есть home), а текущая сессия сидит в `~/projects`, это
заметная разница. Альтернатива — считать ветку «вне строк» равной `directory = null` (то есть
сохранить старое поведение cwd). В ТЗ явно сказано «рабочая директория по умолчанию», поэтому
реализуем как описано; флаг для отката — одна строка в `commitPlaceholderToSession`.
