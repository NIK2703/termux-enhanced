# Пузырёк по уходу в фон: разбор и реализация

Дополнение к `docs/bubble-window-analysis.md`. Там — про то, как пузырёк вообще возможен и почему
в нём живёт настоящее окно приложения. Здесь — про две новые вещи: кнопку «Пузырёк» в нотификации
приложения и опцию автоматического открытия/закрытия пузырька по уходу в фон.

## 1. Постановка

1. **Кнопка в нотификации.** В нотификации сервиса (той, что висит постоянно) добавить действие
   «Пузырёк» рядом с «Разбудить»/«Выход». Это **единственный** ручной способ открыть пузырёк:
   пункт контекстного меню терминала («Ещё…») убран по просьбе пользователя — см. §2.4.
2. **Автоматический пузырёк.** Опция: когда приложение уходит в фон — пузырёк открывается; когда
   возвращается — закрывается.

Второе — это не «ещё одна кнопка», а изменение поведения на **каждом** уходе в фон, поэтому оно
сделано выключенным по умолчанию: такое нельзя включать за пользователя.

## 2. Кнопка «Пузырёк»

### 2.1 Почему broadcast, а не activity

Кнопку нажимают **в шторке**, то есть приложение в этот момент почти всегда в фоне. Если повесить
на неё `PendingIntent.getActivity(...)`, то нажатие поднимет весь UI на передний план — ровно то,
чего пользователь не просил: он хотел пузырёк, а получил полноэкранное приложение. Поэтому действие
шлёт broadcast в `TermuxBubbleReceiver`, а тот уже публикует нотификацию пузырька.

Побочный эффект: `TermuxBubbleManager.showBubble()` больше не принимает `Activity`, только
`Context`. Это честнее — публикация пузырька никогда и не требовала activity, а требование
«приложение в foreground» из прежнего javadoc относилось к *подавлению нотификации* и к старой
(Android 10) ветке для не-разговорных нотификаций, а не к самой публикации.

### 2.2 Когда кнопка показывается

Два условия, оба намеренные:

- `TermuxBubbleManager.areBubblesAvailable(this)` — иначе кнопка была бы мёртвой;
- `!TermuxBubbleManager.isBubblePosted(this)` — если пузырёк уже висит, кнопка лишняя, а её нажатие
  не безобидно: перепубликация той же нотификации заново выставляет `setAutoExpandBubble(true)` и
  **разворачивает свёрнутый пользователем пузырёк**.

Условие вычисляется при **сборке** нотификации, а сервис собирает её не постоянно: только при старте,
смене сессий/задач и переключении wakelock. Поэтому одной проверки мало — состояние пузырька меняется
вне сервиса, и без явного сигнала кнопка остаётся в том виде, в каком её застал последний пересбор:
открыл пузырёк — кнопка всё ещё на месте, закрыл — её всё ещё нет. Именно это и было замечено.

Решение: **каждое изменение состояния пузырька просит сервис пересобрать нотификацию**
(`TermuxBubbleManager.requestServiceNotificationRefresh()` — `startService` с действием
`ACTION_REFRESH_NOTIFICATION`). Сигнал не описывает, что изменилось: сервис сам перечитывает состояние
(`buildNotification()` вызывает `isBubblePosted()`), иначе два источника истины разъедутся.

Запрос посылается из **двух** мест — `showBubble()` (после публикации) и `cancel()` (после снятия), —
потому что это единственные воронки, через которые проходят все пути: автоматика, кнопка в шторке,
debug-хук, остановка сервиса. Действие обрабатывается в `onStartCommand`, и пересборку делает
**явный `republishNotification()`** в его `case`.

Именно здесь была вторая ошибка первой версии: считалось, что `runStartForeground()` в начале
`onStartCommand` уже всё переопубликовал, и `case` был пустым. Но `startForeground()` идёт через
activity manager и обещает, что у foreground-сервиса есть *какая-то* нотификация, — а не то, что
шторка перечитает её содержимое. `NotificationManager.notify()` с тем же id — это ровно тот вызов,
который сервис уже делает на каждое изменение сессии, то есть заведомо работающий. `updateNotification()`
для этого не годится: он дополнительно останавливает сервис, если сессий и задач не осталось, а
появление/исчезновение пузырька — не повод заканчивать сессию.

Две тонкости:

- **`cancel()` пересобирает нотификацию только если состояние действительно изменилось.** Автоматика
  зовёт `cancel()` на **каждом** возврате в приложение, и пересборка нотификации каждый раз была бы
  чистым мусором. Но у пути «пользователь выбросил пузырёк» (`ACTION_BUBBLE_DISMISSED`) проверка
  «а был ли он вообще» ненадёжна: SystemUI удаляет запись нотификации **раньше**, чем доставляет
  delete-intent, поэтому `isBubblePosted()` в этот момент уже может читать `false`. Такой вызов идёт
  через `cancel(context, true)` — «состояние изменилось не нами, пересобирай безусловно».
- **`startService` здесь законен даже из фона**: сервис уже запущен (`r.startRequested == true`),
  а ограничение фонового старта на Android 12+ проверяется только для незапущенного сервиса. На
  всякий случай вызов обёрнут в try/catch и никогда не влияет на результат публикации пузырька.

### 2.2.1 Почему `isBubblePosted()` — это ДВА источника

Пузырьковая нотификация публикуется с `setSuppressNotification(true)`, то есть её специально нет в
шторке (см. §2.3). Есть основания полагать, что подавленная пузырьковая нотификация может
отфильтровываться из `NotificationManager.getActiveNotifications()` — тогда ответ по записи читался бы
`false` ровно тогда, когда пузырёк на экране, и кнопка не скрывалась бы никогда.

Точно проверить это в песочнице не удалось (нужен вызов из приложения, а исходники фреймворка целиком
не читаются), поэтому предикат сделан независимым от ответа: `isBubblePosted()` = запись в NMS **или**
собственный флаг приложения `sBubblePosted`, который ставится при публикации и снимается во всех путях
снятия. Флаг живёт в процессе и умирает вместе с ним — а вместе с процессом умирает и пузырёк, так что
«ложно-истинный» флаг не может пережить то, что он описывает.

Выбор в пользу **OR**, а не замены: запись — единственный способ заметить пузырёк, снятый помимо нас,
а флаг — единственный способ не зависеть от фильтрации подавленных нотификаций. Ошибка каждого из них
по отдельности безобидна, вместе они покрывают друг друга.

**Но записи можно верить только от текущего процесса.** Нотификация переживает процесс, который её
опубликовал: замерено на устройстве — запись пузырька (`id=1342`) оставалась в списке и после
`am force-stop`. Никакой новый процесс её не отменит (отменять нечего — пузырька нет), поэтому
наивная проверка «есть запись с нашим id» оставалась `true` **навсегда**, и кнопка не показывалась
больше никогда — ровно то, на что жаловался пользователь. Отсюда отсечка по времени: запись считается
доказательством, только если `posted.getPostTime() >= PROCESS_START_TIME_WALL_CLOCK` (время старта
процесса, посчитанное как `System.currentTimeMillis() - SystemClock.elapsedRealtime()`), иначе она
логируется и игнорируется. Живой пузырёк эту проверку проходит всегда: его опубликовал этот же
процесс, и там уже стоит флаг.

Вторая половина той же ошибки — «залипший» флаг. Его снимает `cancel()`, а `cancel()` вызывается в
том числе на **каждом** возврате в приложение (`maybeAutoHideBubbleOnForeground`), поэтому
пропущенное событие снятия самоисправляется при первом же открытии приложения: `wasPosted` читается
до отмены и равен `true`, значит пересборка заказывается и кнопка возвращается.

Ярлык — строка `action_open_in_bubble` (14 локалей); значение сокращено до одного слова
(«Пузырёк», «Bubble», …), потому что в шторке рядом с «Разбудить»/«Выход» полная формулировка
«Открыть в пузырьке» не помещается и обрезается. Иконка — `res/drawable/ic_bubble.xml` (контур
«облачка»), потому что подходящего drawable в проекте не было.

### 2.4 Пункт контекстного меню убран

Ручной вход «Открыть в пузырьке» из меню «Ещё…» удалён по просьбе пользователя: кнопка в шторке
делает то же самое и доступна из любого места, а два входа в одну функцию в меню — лишний шум.

Удалено вместе с ним (иначе осталось бы мёртвым кодом):

| Что | Где |
|---|---|
| `menu.add(… CONTEXT_MENU_OPEN_IN_BUBBLE_ID …)` и его условие `areBubblesAvailable` | `TermuxActivityViewHelper.buildContextMenu` |
| константа `CONTEXT_MENU_OPEN_IN_BUBBLE_ID = 13` | `TermuxActivityViewHelper`, `TermuxActivityPopupController` |
| ветка `case CONTEXT_MENU_OPEN_IN_BUBBLE_ID` | `TermuxActivityPopupController.onContextItemSelected` |
| `Host.openInBubble(TerminalSession)` + реализация | `TermuxActivityPopupController`, `TermuxActivity` |
| `bubble_unavailable_message`, `bubble_open_failed_message` | все 14 локалей |

Строки-тосты стали ненужными вместе с методом: показать их больше неоткуда — кнопка в шторке
показывается только когда пузыри **доступны** (§2.2), а при недоступных пузырях её просто нет.

Проверка мёртвости ключей:

```bash
grep -rn "CONTEXT_MENU_OPEN_IN_BUBBLE_ID\|openInBubble" --include=*.java app/src/
grep -rn "bubble_unavailable_message\|bubble_open_failed_message" app/src/
```

### 2.3 Заодно исправлено: подавление нотификации

`setSuppressNotification(true)` — это **обмен**: нотификация не попадает в шторку в обмен на
пузырёк. Раньше он запрашивался всегда, когда у приложения включены пузыри. Но платформа может
всё равно не сделать пузырёк — см. §11.5 основного документа: канал получает
`DEFAULT_ALLOW_BUBBLE` (-1) принудительно, `canBubble()` для него false, и приложение это
изменить не может. В таком состоянии `suppress` + «пузырька нет» = **пользователь теряет
нотификацию и не получает ничего**.

Теперь подавление запрашивается только если `channel.canBubble()` тоже true. Если канал не умеет —
нотификация остаётся видимой как запасной вариант. На устройстве, где канал уже разрешён
(`mAllowBubbles=1`), поведение не меняется.

## 3. Что именно триггерит автоматику

Ключевой вопрос — не «как открыть», а **на какое событие подписаться**. Кандидаты и что с ними не
так:

| Событие | Годится? | Почему |
|---|---|---|
| `onPause()` | нет | срабатывает на каждом диалоге и на перекрытии любым окном |
| `onStop()` сам по себе | нет | срабатывает и на своих переходах, и при гашении экрана, и при повороте |
| `ProcessLifecycleOwner` | нет | app-level «процесс в фоне» срабатывает в том числе на **гашение экрана** (§3.2) |
| `onUserLeaveHint()` | как **намерение**, не как действие | платформенный сигнал «пользователь сам ушёл»: Home, Recents, переключение приложений. Но приходит слишком рано (§3.1) |
| `onTaskRemoved` | нет | это про выкидывание задачи из Recents, другое событие |

`onUserLeaveHint()` **не** вызывается, когда:
- экран гаснет или включается блокировка — и это правильно: телефон убрали в карман, пузырёк не нужен;
- происходит смена конфигурации.

Закрытие — `onResume()` основного окна: пользователь вернулся к полноэкранному приложению, значит
плавающее окно лишнее. Отменяем нотификацию, SystemUI убирает пузырёк.

### 3.1 Замер: `onUserLeaveHint` вызывается и на СВОИХ переходах, и приходит слишком рано

Здесь была ошибка, и она стоила регрессии. Первая версия считала `onUserLeaveHint` достаточным
условием и открывала пузырёк прямо в нём. На устройстве это выглядело так (опция включена, ни одного
нажатия Home):

```
A) терминал на переднем плане, пузырька нет:            bubble=0
B) запускаем SettingsActivity (свой переход, БЕЗ Home): bubble=1   <-- пузырёк открылся сам
C) теперь жмём Home из Настроек:                        bubble=1
```

в `logcat` — `START u0 {act=android.intent.action.VIEW … cmp=com.termux.debug/com.termux.app.bubble.TermuxBubbleActivity}`
в момент шага B. То есть `onUserLeaveHint` срабатывает и на переходе между **своими** activity.

Причина не в «кривом сигнале», а в порядке исполнения. Хинт доставляется **внутри транзакции паузы**,
а для перехода между двумя activity одного приложения платформа кладёт паузу и запуск следующего
экрана в **один батч**, и пауза идёт первой. В момент хинта следующего экрана ещё не существует,
поэтому отличить свой переход от ухода в лаунчер там физически нечем: в обоих случаях «стартованных
activity приложения» ровно одна — эта самая.

Отсюда решение: **хинт — только намерение, решение — в `onStop()`.** К моменту `onStop` батч уже
исполнен, и вопрос «пользователь ушёл из приложения или приложение выставило вперёд свой экран?»
решается счётчиком стартованных activity всего приложения
(`TermuxApplication.getStartedActivityCount()`, `ActivityLifecycleCallbacks`): после остановки нашего
окна `> 0` означает, что на экране другой **наш** экран, то есть приложение всё ещё на переднем плане.

Порядок проверок в `maybeAutoOpenBubbleAfterStop()`:

| Проверка | Что отсекает |
|---|---|
| `mUserLeaveHintSeen` (потребляется) | гашение экрана, блокировка, поворот — `onStop` там есть, хинта нет |
| `getStartedActivityCount() > 0` | свои переходы: Настройки, Help, выбор bootstrap, диалоговые activity |
| `isChangingConfigurations()` | пересоздание окна (страховка: хинта при повороте и так нет) |

Флаг `mUserLeaveHintSeen` сбрасывается в `onStart()`, чтобы хинт, который уже был оценён и **отвергнут**
на своём переходе, не сработал позже на постороннем `onStop`.

Цена решения: автоматика привязана к **окну терминала**. Уход в фон из Настроек (Home, будучи в
Настройках) пузырёк не откроет — приложение ушло в фон, но терминала на экране не было. Это
сознательно (§5).

### 3.2 Почему не `ProcessLifecycleOwner`

Он даёт ровно то, что нужно по названию — «весь процесс в фоне», — но срабатывает и на **гашение
экрана**: последняя activity уходит в `onStop`, процесс формально в фоне. Телефон, убранный в карман,
получал бы пузырёк с терминалом. `ProcessLifecycleOwner` пришлось бы дополнять тем же хинтом
`onUserLeaveHint`, то есть тем же самым условием, что и здесь, — но с новой зависимостью
(`androidx.lifecycle:lifecycle-process` в проект не входит) и без выигрыша.

## 4. Ловушки

### 4.1 Рекурсия: пузырёк — тот же самый класс

`TermuxBubbleActivity extends TermuxActivity`, поэтому **все** колбэки жизненного цикла выполняются
дважды с противоположным смыслом. Без различения:

- уход из пузырька (Home, будучи в пузырьке) открыл бы **второй** пузырёк;
- `onResume` пузырька был бы прочитан как «пользователь вернулся в приложение» и **закрыл бы
  пузырёк, по которому только что тапнули**.

Решение — виртуальный `isBubbleWindow()`: `false` в `TermuxActivity`, `true` в
`TermuxBubbleActivity`. Обе автоматические ветки начинаются с этой проверки. Это единственное, что
подкласс добавляет к поведению.

### 4.2 «Уже висит» — не переоткрывать

Иначе каждый уход в фон заново разворачивал бы свёрнутый пузырёк. Проверка — `isBubblePosted()`.

### 4.3 Пузыри выключены → мусор на каждом уходе

Если пользователь не разрешил пузыри, публикация даст **обычную нотификацию** — то есть при
включённой опции в шторке появлялось бы уведомление при каждом нажатии Home, а при возврате
исчезало. Проверка `areBubblesAvailable()` это отсекает.

### 4.4 Нет сессий → не плодить шелл

`TermuxActivity` при старте создаёт сессию, если её нет. Открывать пузырёк «на всякий случай» при
уходе из приложения без сессий — значит запускать новый shell просто чтобы было что показать.
Проверка: `service != null && !service.isTermuxSessionsEmpty()`.

### 4.5 `isFinishing()` — Back ≠ Home

На части версий `onUserLeaveHint()` вызывается и когда activity закрывают. Пузырёк, всплывающий
поверх лаунчера сразу после выхода по Back, — абсурд. Проверка `isFinishing()`.

### 4.6 Размер pty: кто владеет геометрией окна

Размер pty — свойство **сессии**, а не окна (`JNI.setPtyWindowSize`, побеждает последний записавший),
а сессию одновременно могут показывать **два** окна: полноэкранное и пузырёк (второй экземпляр того же
класса). Раньше это выглядело так: уходишь в пузырёк, возвращаешься — и терминал в полноэкранном окне
остаётся **размером с пузырёк**; в обратную сторону — пузырёк показывает сетку полноэкранного окна.

Причина не в «рефлоу», а в том, что размер **никто не переотправлял**:

| Шаг | Что происходит с pty |
|---|---|
| полноэкранное окно, view 62×42 | pty = 62×42 |
| уход в пузырёк: view пузырька, скажем, 40×20, `onSizeChanged` | pty = 40×20 |
| возврат в полноэкранное окно | **ничего**: view не переразмечался (тот же размер), `onSizeChanged` не срабатывает, а `updateSize()` сравнивает с эмулятором **сессии** (там уже 40×20) — но вызова-то нет |

То есть `TerminalView.updateSize()` сам по себе корректен (обе проверки внутри — по содержимому, а не
«вызывался ли я раньше»), не хватало только **повода его вызвать** при возврате окна на передний план.

Лечится `TerminalView.reassertSessionSize()` — «отправить свою геометрию ещё раз, хотя ничего не
менялось» — который вызывается из `TermuxActivity.onResume()` и `onWindowFocusChanged(true)`. Поскольку
пузырёк — тот же класс, один и тот же вызов закрывает **оба** направления: любое окно, выходя на
передний план, объявляет pty свой размер.

Две тонкости:

- **Идемпотентность.** Если размер совпал с эмулятором сессии, `updateSize()` до ioctl не доходит, так
  что вызов на каждом resume стоит одного сравнения. Именно поэтому его можно вешать и на
  `onWindowFocusChanged`: второй, более поздний шанс нужен, потому что `onResume` может отработать
  раньше, чем закрывающееся окно пузырька доделает свою переразметку.
- **Только текущая страница.** Остальные страницы пейджера переразмечаются при следующем бинде: путь
  бинда уже сравнивает размер с эмулятором сессии и переотправляет его, если тот разошёлся.

Цена: пока живы оба окна одной сессии, при переносе фокуса терминал переразмечается один раз. Это
принятая цена (альтернатива — отдавать pty только одному окну — ломает «настоящее окно», см. §11.3
основного документа), но теперь переразметка заканчивается **правильной** геометрией, а не чужой.

### 4.7 IME

**Риск подтвердился на устройстве, и он был не гипотетический.** Замер: клавиатура в полноэкранном
окне закрыта (`kb=0`), уходим по Home → пузырёк открывается **вместе с клавиатурой** (`kb=1`,
`mCurrentFocus=…TermuxBubbleActivity`). Клавиатура при этом всплывает поверх того приложения, куда
ушёл пользователь — то есть опция «тихо показать терминал» на деле влезает в чужой интерфейс.

Причина — не платформа, а наш собственный код. Пузырёк это **холодный старт того же класса
activity**, поэтому он проходит обычный старт-путь, а на холодном старте проект исторически
показывает клавиатуру всегда:

- `TermuxTerminalViewClient.onResume()` → `setSoftKeyboardState(true, …)`, где
  `restoreFromState = !isOnResumeAfterOnCreate() || isActivityRecreated()` на холодном старте даёт
  `false` ⇒ ветка `SoftKeyboardRestore.showWithRetry(...)` — **явный показ**;
- плюс per-session реконсиляция в `applyTextInputVisibilityForSession(...)` из
  `onSessionPageSelected`: у окна пузырька **свой** `SessionUiStateStore`
  (`private final … mTextInputState = new SessionUiStateStore()` — на activity, не статический),
  записей о сессии в нём нет, и `isSoftKeyboardIntent()` отдаёт глобальный дефолт «видно» ⇒ ещё один
  показ.

«Скрывать при старте» тут не подходит как лечение: это не «скрыть клавиатуру», а «не просить её», и
штатный путь скрытия вдобавок ставит окну `SOFT_INPUT_STATE_ALWAYS_HIDDEN`, который **вытесняет
`ADJUST_RESIZE`** — тогда клавиатура в маленьком пузырьке не подожмёт окно, а накроет его.

Реализовано в **две стадии**, потому что первая закрыла не всё.

**Стадия 1 — не просить клавиатуру самим.** У окна пузырька отдельный флаг подавления
холодного старта (`TermuxTerminalViewClient.mBubbleStartupImeSuppressed`):

- поднимается в `onResume()`, когда этот resume и есть холодный старт; снимается на следующем
  resume (это уже возврат в существующий пузырёк — обычное окно) и по первому
  `onUserInteraction()`;
- закрывает **оба** наших пути показа: `setSoftKeyboardState` в окне пузырька не показывает вообще,
  а `isStartupSoftKeyboardHidePending()` (шлюз реконсиляции) возвращает `true` и на этом флаге;
- **никаких флагов окна не ставит** — в пузырьке клавиатура не «прячется», её просто никто не просит;
- дополнительно закрыты два отложенных ре-ассерта клавиатуры
  (`scheduleSwitchKeyboardReassert` / `scheduleKeyboardReassertOnActiveView`), иначе они вернули бы
  клавиатуру через 300 мс.

Первая попытка снимала флаг в `applyStartupSoftKeyboardState()` («страница жива») — **это не
сработало**, и замер это показал: `showSoftInput requested by
TermuxActivity.applyTextInputVisibilityForSession:4621`. Причина: пейджер прогоняет стартовую
реконсиляцию **несколько раз** (перевыбирает страницу 0 на каждое уведомление списка сессий, пока
сессии восстанавливаются), а `consumePendingKeyboardRestoreIfReady()` снимает флаг уже после первой.
Поэтому флаг живёт весь холодный старт.

Диагностика, которая это дала (оставлена в коде, потому что вопрос «кто открыл клавиатуру?» иначе
не решается): `SoftKeyboardRestore` — единственная воронка всех **автоматических** показов (ручные
пути — тап и кнопка KEYBOARD — идут через `KeyboardUtils.showSoftKeyboard` напрямую), и теперь она
пишет в лог первый кадр стека за своими пределами.

**Стадия 2 — не дать платформе показать её самой.** После стадии 1 наших запросов не осталось
вообще, а `mInputShown` всё равно был `true`, причём `mShowExplicitlyRequested=false`, то есть
**ничего нашего не просило**. Это тот самый авто-показ по получению фокуса окном, от которого
основное окно защищается в `onResume()` и в `runKeyboardRestore()`: окно с
`STATE_UNSPECIFIED|ADJUST_RESIZE`, получая фокус с сфокусированным `TerminalView`
(`onCheckIsTextEditor=true`), показывает IME само. На холодном старте пузырька эта защита не
выполняется — блок под `if (willRestoreKeyboard)`, а на холодном старте `willRestoreKeyboard`
равен `false`.

Лечение: окну пузырька ставится `SOFT_INPUT_STATE_ALWAYS_HIDDEN | SOFT_INPUT_ADJUST_RESIZE`
(новый помощник `KeyboardUtils.setSoftKeyboardAlwaysHiddenAndAdjustResize`). Оба бита обязательны и
это разные биты одного поля: `setSoftKeyboardAlwaysHiddenFlags` заменяет режим целиком и теряет
`ADJUST_RESIZE` (клавиатура накрыла бы пузырёк вместо того, чтобы поджать его), а
`setSoftInputModeAdjustResize` теряет `ALWAYS_HIDDEN`.

Побочно: `onSingleTapUp` теперь перед показом снимает `ALWAYS_HIDDEN`
(`setSoftInputModeAdjustResize`) — как это уже делают кнопка KEYBOARD и реконсиляция. Иначе
`ALWAYS_HIDDEN`, оставшийся от политики холодного старта, работал бы против явного показа.

**Замеры (Android 13, `dumpsys input_method`):**

| Момент | `softInputMode` | `mShowExplicitlyRequested` | `mInputShown` |
|---|---|---|---|
| после Home (пузырёк открылся) | `ALWAYS_HIDDEN\|ADJUST_RESIZE` | false | **false** |
| после тапа по терминалу в пузырьке | то же | **true** | **true** |

То есть: пузырёк появляется молча, а тап внутри него клавиатуру открывает — подавление не
заблокировало её, а только убрало самопроизвольный показ. В логе это подтверждается парой строк
`Bubble cold start: suppressing automatic soft keyboard shows` →
`Bubble cold start: IME suppression ended by user interaction`.

Оракул для двух окон — **системный**, а не `uistate`: `uistate` отвечает про экземпляр, который
отдаёт `TermuxActivity.getInstance()`, а это полноэкранное окно. Реальное состояние IME в системе:
`dumpsys input_method | grep -E "mInputShown|mCurFocusedWindow"`.

### 4.8 «Выход» из нотификации при открытом пузырьке

Пользователь может нажать «Выход» в шторке, пока приложение в фоне с открытым пузырьком. Сессии
умирают, а окно пузырька осталось бы висеть пустым. Поэтому `requestStopService()` теперь заодно
вызывает `TermuxBubbleManager.cancel(this)`.

### 4.9 Разворот пузырька

И ручной, и автоматический путь используют `setAutoExpandBubble(true)` — то есть пузырёк открывается
развёрнутым и забирает фокус. Для **автоматического** действия это спорно: он закрывает ~60% экрана
и может утащить за собой клавиатуру (§4.7). Оставлено так сознательно: опция включается вручную, и
человек, который её включил, ждёт, что терминал будет видно, а не что появится точка. Если на
практике окажется навязчиво — правится одной строкой в `showBubbleInternal`
(`setAutoExpandBubble(false)` для автоматического пути).

### 4.10 Несколько окон

Нотификация пузырька одна (id `1342`), поэтому и пузырёк один — второй не появится. Повторный
`showBubble()` — это обновление той же нотификации.

Но два окна одного класса делят и **статическое** состояние. Найденный дефект: `TermuxActivity.sInstance`
(`private static volatile`, ставился в `onCreate`, обнулялся в `onDestroy`) — при двух окнах
`onDestroy()` пузырька обнулял ручку **полноэкранного** окна, которое продолжало жить. Проявление:
debug-хук отвечал `TIPanelCmd: no-activity: cmd=bubble`. Потребители у ручки только debug-сборки
(`TermuxDebugCommandReceiver`, `TermuxDebugActivity`), но дефект настоящий. Исправлено:

- `onCreate`: `if (sInstance == null || !isBubbleWindow()) sInstance = this;` — полноэкранное окно
  всегда выигрывает, пузырёк забирает ручку только если он единственный (то есть когда приложение
  открыли сразу в пузырёк);
- `onDestroy`: `if (sInstance == this) sInstance = null;` — снимаем только свою.

Побочное следствие для отладки: `uistate`/`pagedump` теперь всегда отвечают про **полноэкранное**
окно, даже когда на экране пузырёк. Для состояния IME это значит, что нужен системный оракул (§4.7).

Прочее разделяемое состояние проверено: у `TermuxActivity` больше нестатических полей нет, а
статический кэш шрифта в `TermuxTerminalSessionActivityClient`
(`sCachedTypeface`/`sCachedTypefaceKey`/`sCachedTypefaceCheckedAtMs`) — только кэш, делить безопасно.

## 5. Итоговая семантика

| Состояние | Опция выключена (по умолчанию) | Опция включена |
|---|---|---|
| Открыть пузырёк вручную (кнопка в шторке) | открывается | открывается |
| Уход в фон (Home/Recents) | ничего | пузырёк открывается |
| Возврат в полноэкранное окно | пузырёк закрывается | пузырёк закрывается |
| Возврат **через пузырёк** (тап по нему) | пузырёк остаётся | пузырёк остаётся |
| Уход из пузырька в фон | ничего | ничего (второй не открывается) |
| Свои экраны (Настройки, Help) | ничего | ничего |
| Уход в фон **из** Настроек/Help | ничего | ничего — автоматика привязана к окну терминала (§3.1) |
| Экран погашен / блокировка | ничего | ничего |
| Закрытие по Back | ничего | ничего |
| «Выход» из нотификации | пузырёк закрывается | пузырёк закрывается |
| Пузыри запрещены в системе | кнопка не показывается | ничего не происходит |
| Размер терминала при переходе окно ↔ пузырёк | каждое окно объявляет pty свой размер (§4.6) | то же |
| Кнопка «Пузырёк» в нотификации | есть, пока пузырька нет; скрывается, пока он висит (§2.2) | то же |

**Закрытие при возврате не зависит от опции.** Опция решает только, появляется ли пузырёк **сам**;
она не решает, может ли он пережить возврат приложения на передний план. Пузырёк и полноэкранное окно
показывают одну сессию одновременно — состояние, в котором пузырёк закрывает часть экрана, терминал
виден дважды, а pty принадлежит тому окну, которое тронули последним. Поэтому `onResume`
полноэкранного окна снимает пузырёк **всегда**, кем бы он ни был открыт — автоматикой или кнопкой в
шторке. Вернуть его можно той же кнопкой: она показывается, когда пузырька нет.
| Клавиатура при появлении пузырька | — | не всплывает (§4.7); тап по терминалу внутри пузырька открывает её как обычно |

## 6. Что сознательно не сделано

- **Пузырёк не переживает возврат в приложение — и не должен.** Ни при включённой опции, ни при
  выключенной, ни когда его открыли кнопкой в шторке (§5). «Постоянный пузырёк» — это другая функция,
  и делать её надо отдельным переключателем, а не подразумевать.
- **Не добавлена настройка «свёрнутый/развёрнутый»** — см. §4.9, пока это константа.
- **Не отслеживается смерть сервиса извне** — если сервис убьют (LMK), нотификация пузырька уйдёт
  вместе с ним, потому что она принадлежит тому же uid и процессу; отдельной обработки не нужно.
- **Не трогается `excludeFromRecents`** пузырька — он не должен попадать в Recents, и не попадает.

## 7. Как проверять

```bash
ADB=/c/Users/Nikita/AppData/Local/Android/Sdk/platform-tools/adb.exe
$ADB connect <ip>:5555

# 1. Кнопка в нотификации: есть ли действие
$ADB shell dumpsys notification --noredact | grep -A4 "termux_app_notification_channel"

# 2. Опция включена
$ADB shell am start -n com.termux.debug/com.termux.app.TermuxActivity
#    Настройки → Отображение → Окно → «Пузырёк при уходе в фон»

# 3. Уход в фон и состояние пузырька
$ADB shell input keyevent KEYCODE_HOME
$ADB shell dumpsys notification --noredact | grep -E "mAllowBubble|isBubble|termux_bubble"

# 4. Возврат
$ADB shell am start -n com.termux.debug/com.termux.app.TermuxActivity
$ADB shell dumpsys notification --noredact | grep "termux_bubble"   # должно быть пусто

# 5. Что за окно на экране
$ADB shell dumpsys window | grep -E "mCurrentFocus|mFocusedApp"

# 6. Клавиатура — СИСТЕМНЫЙ оракул (uistate отвечает про полноэкранное окно, см. §4.10)
$ADB shell dumpsys input_method | grep -E "mInputShown|mCurFocusedWindow"
```

Оракул «пузырёк действительно появился» — только `dumpsys notification`: успешный `notify()` ничего
не значит, решение принимает SystemUI (`mAllowBubble=true` / `isBubble=true`).

## 8. Что обязательно проверить на устройстве

1. **Публикация из фона.** Нотификация — «разговор» (`MessagingStyle` + `Person` + long-lived
   shortcut), поэтому по документации пузырёк разрешён без foreground. Проверено: публикация из фона
   даёт `mAllowBubble=true` / `isBubble=true`, то есть пузырёк, а не обычную нотификацию.
2. **Клавиатура (§4.7).** ✅ Проверено: уход при закрытой клавиатуре → пузырёк появился,
   `mInputShown=false`; тап по терминалу внутри пузырька → `mInputShown=true`. Осталось проверить
   руками, что уход при **открытой** клавиатуре тоже не тащит её за собой (наш код её не просит, но
   платформенный авто-показ по фокусу гасится флагом окна — стоит убедиться на живой клавиатуре).
3. **Развёрнутость (§4.9).** Не мешает ли развёрнутый пузырёк при каждом уходе.
4. **Возврат через пузырёк.** Тап по пузырьку не должен его закрывать (проверка `isBubbleWindow()`
   в `onResume`). Возврат через `am start` проверен: нотификация пузырька уходит (count 0).
5. **Переразметка (§4.6).** Как выглядит терминал после возврата — нет ли «поехавшей» разметки.
6. **Живость полноэкранного окна после закрытия пузырька (§4.10).** ✅ Проверено: после
   `bubble cancel` debug-хук `uistate` отвечает полным дампом, а не `no-activity`.
