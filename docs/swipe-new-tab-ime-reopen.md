# Переоткрытие клавиатуры при свайп-создании вкладки

**Симптом.** Клавиатура открыта, пользователь на последней вкладке, свайп вправо за крайнюю правую
вкладку создаёт новую. Первая такая вкладка создаётся чисто; начиная со второй — в момент создания
клавиатура «переоткрывается» (видимо падает и возвращается).

**Статус.** P1 + побочная правка **применены** в `TerminalPagerAdapter` (см. §6). Компиляция
пройдена (`:app:compileDebugJavaWithJavac`, BUILD SUCCESSFUL). Проверка на устройстве — §6.3.
Решение архитектурное: удаление механизма, а не очередной гард.

---

## 1. Почему это не баг IME-слоя

Путь создания вкладки свайпом **не совпадает** с путём кнопки «+»:

| | кнопка «+» / debug `new tab` | свайп вправо |
|---|---|---|
| точка входа | `TermuxTerminalSessionActivityClient.addNewSession` | `SessionPagerManager.commitPlaceholderToSession` |
| создание сессии | `createNewSession(..., SELECT_AND_SCROLL, ...)` | `createSessionForPlaceholder` → `createNewSession(..., CALLER_MANAGED, ...)` |
| синхронизация адаптера | `syncWithServiceList` → `notifyItemRangeInserted` | **пропускается**, затем `commitPlaceholder` — перепривязка слота на месте |

`SessionPagerManager.termuxSessionListNotifyUpdated()` на пути свайпа — **no-op**: `getItemCount()`
уже включает placeholder, поэтому `getItemCount() == newSize` и весь блок синхронизации
(`stopScroll`, `setCurrentItem`, `onTerminalPageSelected`) не выполняется
(`SessionPagerManager:1243`). Отсюда следствие, которое объясняет расхождение замеров:
debug-команда `new tab` **не воспроизводит** провал, потому что идёт по другому пути.

IME-слой при этом ведёт себя корректно: `createNewSession` снимает `inheritedKeyboard`
до мутации и поднимает окно `beginSessionUiChurn(900 мс)`, так что намерение `kbIntent`
не отравляется системным HIDE. Падение клавиатуры — физическое: **вью страницы заменяется**.

## 2. Механизм: пересоздание `TerminalView` при коммите placeholder

Адаптер включает stable ids (`TerminalPagerAdapter:176`) и отдаёт
`getItemId()` = `session.mHandle.hashCode()`, а для placeholder — свежий `mPlaceholderId`.

`commitPlaceholder` перепривязывает тот же ViewHolder на месте, вызывая `onBindViewHolder`
**напрямую**, а не через `bindViewHolder`. Значит `holder.mItemId` остаётся равен id placeholder,
под которым этот холдер был связан. Чтобы RecyclerView не отверг холдер на следующем проходе
раскладки, слот должен и дальше отдавать тот же id — для этого есть алиас:

```java
private TermuxSession mCommittedSession = null;   // TerminalPagerAdapter:67
private long mCommittedId = RecyclerView.NO_ID;   // :68

// getItemId(), :291
if (mSessions.get(position) == mCommittedSession) return mCommittedId;
```

**Алиас — один на весь адаптер.** Цепочка событий:

1. RecyclerView при каждом проходе раскладки сперва матчит холдер по позиции
   (`getScrapOrHiddenOrCachedHolderForPosition`), а затем валидирует его
   `validateViewHolderForOffsetPosition`, где при `hasStableIds()` проверяется
   `holder.getItemId() == adapter.getItemId(position)`.
2. Расхождение → холдер помечается `FLAG_INVALID` и уходит в `recycleViewHolderInternal`:
   вью **физически отцепляется от окна** (`onDetachedFromWindow`), а затем — поскольку под эту
   позицию есть ровно один холдер — RecyclerView тут же достаёт его из пула и привязывает к той
   же позиции. Новый `TerminalView` при этом **не создаётся**: происходит отцепление и повторное
   присоединение того же вью (замерено, §6.3). Для IME это эквивалентно, потому что фокус
   снимается именно на отцеплении.
3. Коммит #1: алиас один, он принадлежит коммитимому слоту → расхождений нет.
4. Коммит #2: `mCommittedSession` перезаписывается на S2, алиас `P1` для S1 **теряется** →
   `getItemId(1)` внезапно становится `h(S1)` → холдер страницы 1 (она ещё на экране как левый
   сосед при `offscreenPageLimit == 1`) отвергается → отцепляется и присоединяется обратно.
5. Коммит #k: теряют алиас **все k−1 предыдущих** слотов.

Отцепление — это и есть провал клавиатуры. `ViewGroup.removeViewInternal` для вью с фокусом
вызывает `clearFocusForRemoval()`, то есть **снимает фокус без передачи**; окно оказывается без
сфокусированной вью, `InputMethodManager` завершает input-сессию, IME скрывается. Дальше
`applyTextInputVisibilityForSession` (`TermuxActivity:4337`, `showKeyboardIfFocused && !imeVisibleNow`)
или `scheduleSwitchKeyboardReassert` (+300 мс, `:4369`) возвращают её — это и есть видимое
«переоткрывается».

Так объясняются все три наблюдения: первый раз чисто; со второго ломается и ухудшается с каждой
вкладкой; debug-хуки не воспроизводят.

### Косвенное подтверждение в самом коде

Комментарий в `commitPlaceholder` (`TerminalPagerAdapter:669-695`) уже описывает ровно этот класс
аварии для `mChangedScrap`: «RecyclerView resolves a changed ViewHolder out of mChangedScrap
**BY ITEM ID** … the lookup misses, the on-screen page is recycled». Однослотовый алиас — тот же
дефект, только для `mAttachedScrap` и накапливающийся.

## 3. Архитектурное решение

### P1 (основное, субтрактивное): убрать stable ids у пейджера

Stable ids здесь не покупают ничего:

* аниматор выключен — `pagerRv.setItemAnimator(null)` (`SessionPagerManager:338`), т.е. нечему
  сохранять идентичность элемента для change-анимации;
* `notifyDataSetChanged()` сознательно не используется — только инкрементальные уведомления,
  для которых идентичность элемента не нужна;
* ViewPager2 сам адресует страницы по позиции (`getCurrentItem`, `scrollToPosition`).

А стоит это ровно описанной аварией. С `hasStableIds() == false` холдер матчится **по позиции**
и всегда переиспользуется: слот не может «сменить личность», потому что личность у него одна —
позиция. Требование «тот же ViewHolder, без пересоздания» становится структурным, а не
поддерживаемым вручную.

Правки в `TerminalPagerAdapter`:

1. убрать `setHasStableIds(true)` (`:176`);
2. удалить `PLACEHOLDER_ID_BASE`, `mPlaceholderId`, `mCommittedSession`, `mCommittedId` (`:56-68`)
   и переопределение `getItemId` (`:283-297`);
3. в `setPlaceholderActive(true)` убрать `mPlaceholderId++` (`:638`);
4. в `commitPlaceholder` убрать присвоение `mCommittedSession` / `mCommittedId` (`:664-666`),
   сам прямой `onBindViewHolder` оставить (проверен и работает);
5. переписать док-комментарии `:47-68` и `:669-695` — описанный там сценарий
   `mChangedScrap`-по-id становится невозможным.

Дополнительно разблокируется упрощение: `commitPlaceholder`'s fallback
`notifyItemChanged(placeholderIndex, PAYLOAD_REBIND)` становится безопасным
(`canReuseUpdatedViewHolder` возвращает true при нулевом аниматоре).

**Побочная правка того же класса:** `syncWithServiceList` при сбросе placeholder делает
`notifyItemRemoved(mSessions.size())`, но не чистит `mAttachedViews` (`:218-221`). Карта ключуется
позицией, поэтому слот продолжает резолвиться в мёртвую вью placeholder — ввод и IME уходят
в никуда. Добавить `mAttachedViews.remove(mSessions.size())` перед уведомлением.

### P2 (инвариант): окно не остаётся без сфокусированной вью

P1 убирает этот конкретный источник, но не класс: отцепить сфокусированную вью может любая
структурная правка (закрытие вкладки, далёкий переход при `offscreenPageLimit == 1`).
Правило формулируется один раз и принадлежит **одному** владельцу:

> пока намерение клавиатуры «показана», ни одна мутация пейджера не имеет права оставить окно
> без приаттаченной и разложенной сфокусированной вью.

Проверка — в одном месте, на выходе из структурного обновления (а не в каждом сайтах):
если `getCurrentFocus() == null` и `shouldImeBeUp()`, постить `requestFocus()` на вью целевой
страницы, с гейтом `isAttachedToWindow() && isLaidOut() && hasWindowFocus()`.
Отдельных «спасателей» по сайтам (posted `requestFocus` в реконсиляции, подпорки в фокус-листенере)
не должно быть: они срабатывают **после** провала и потому лишь ремонтируют, а не предотвращают.

### P3: намерение — команда, а не измерение

Уже выполняется и должно быть закреплено: `createNewSession` снимает `inheritedKeyboard`
**до** мутации и пишет его в намерение; внутри окна `mSessionUiChurn` (900 мс) ни один
`onImeVisibilityChanged` не перезаписывает намерение. Нельзя добавлять записи намерения,
основанные на `computeImeVisibility()` внутри перестройки: там это наблюдение, а не команда,
и оно честно сообщает «вниз», когда обслуживаемая вью отцеплена.

### P4: единый источник истины о «где мы»

`TermuxActivity.getCurrentSession()` — производная от `mTerminalView`, то есть **отстающий кэш**.
Истина о том, где мы оказались, — индекс, который запарковал пейджер (`restoreIndex`). Любая
логика, сверяющая пейджер с `getCurrentSession()` и что-то по этому исправляющая, будет
возвращать пользователя на предыдущую вкладку. Это уже стоило одной регрессии.

## 4. Проверка (только на устройстве)

Воспроизведение — **реальный свайп**, не debug-команда: жест слушается на пейджере
(`SessionPagerManager:217-281`), поэтому нужен `input swipe 1000 500 60 500 400` по области
терминала, и пейджер обязан стоять на последней вкладке.

Оракул:

* `uistate` через debug-приёмник (~85 мс/сэмпл) — `kb=`;
* `TerminalView.onCreateInputConnection` — сигнал (пере)привязки IME: после P1 на один
  свайп-коммит должно быть **ровно одно** срабатывание (новая страница), а не 2–3;
* `setTerminalView` — число различных `new` за коммит должно стать равным 1.

Набор прогонов:

1. Три свайп-создания подряд с открытой клавиатурой → `kb=` ни разу не покидает 1.
2. Негативное направление: клавиатура намеренно скрыта (`ime hide`) + тот же сценарий →
   `kb=` обязан остаться 0. «Держать клавиатуру» — не значит воскрешать закрытую.
3. `switch tab 0` при ≥3 вкладках, затем создать вкладку кнопкой «+» и закрыть вкладку
   (не последнюю и последнюю) — регрессии P1 по переиспользованию холдеров.

A/B в одной сборке (`false && stableIds()`), как требует практика проекта; релиз не трогать,
пока debug не доказан.

## 5. Чего не делать

* Не лечить в IME-слое: гарды, блоки записи намерения, «ремонт по факту падения» — всё это
  срабатывает уже после отцепления вью и лишь маскирует симптом.
* Не расширять алиас до `Map<сессия, id>`: лечит симптом, но оставляет дизайн, в котором слот
  меняет личность, и добавляет хрупкое правило «когда алиас можно удалять».
* Не добавлять posted `requestFocus` в реконсиляцию: LOSS и hide идут **до** неё.
* Не поднимать страж внутри колбэка, который само событие и вызывает — он всегда на шаг позже.

## 6. Что применено

### 6.1 П1 — stable ids удалены

`TerminalPagerAdapter` (один файл, −57/+27 строк):

* конструктор: убран `setHasStableIds(true)`;
* удалены `PLACEHOLDER_ID_BASE`, `mPlaceholderId`, `mCommittedSession`, `mCommittedId`;
* удалено переопределение `getItemId()` целиком — адаптер больше не объявляет идентичность
  элементов вообще;
* `setPlaceholderActive(true)`: убран `mPlaceholderId++`;
* `commitPlaceholder`: убрано присвоение алиаса, прямой `onBindViewHolder` оставлен как есть —
  это единственный механизм, который гарантирует, что слот сохраняет **тот же** ViewHolder,
  тот же `TerminalView` и тот же фокус через коммит;
* док-комментарии переписаны: вместо правил «уникальность id / наследование id» зафиксировано,
  почему идентичность элементов здесь не нужна и чем она вредит.

Нумерация строк выше (`§2`, `§3`) относится к состоянию **до** правки.

### 6.2 Побочная правка

`syncWithServiceList` и `setPlaceholderActive(false)` теперь снимают запись
`mAttachedViews.remove(mSessions.size())` перед `notifyItemRemoved(...)`: карта ключуется
позицией, и слот уходящего placeholder иначе продолжал бы резолвиться в мёртвую вью.

### 6.3 Проверка на устройстве (выполнена)

Устройство: `192.168.243.115:5555`, LineageOS `marble`, debug-пакет `com.termux.debug`.
Сценарий — **реальный жест** `input swipe 1000 500 60 500 400` (пейджер на последней вкладке),
опрос `uistate` через debug-приёмник. A/B — один и тот же билд с флагом
`PVDBG_LEGACY_STABLE_IDS` (инструментация временная, снята).

**Оракулы.** Временно логировались `TerminalView.onAttachedToWindow` / `onDetachedFromWindow`
(`ATTACH`/`DETACH`), `onCreateInputConnection` (`IC`) и в адаптере — `CREATE` / `RECYCLE` /
`BIND` / `COMMIT`. Ключевой сигнал — не `CREATE`, а пара `RECYCLE ... boundPos=N-1` + `DETACH`
сразу после `COMMIT`.

**LEGACY (stable ids + однослотовый алиас) — баг воспроизведён:**

```
20.587 COMMIT idx=2 sessions=3
20.601 DETACH view=221120308 focus=0          ← страница pos=1 отцеплена
20.602 RECYCLE holder=215038471 view=221120308 boundPos=1
20.602 BIND pos=1 holder=215038471 view=221120308
20.851 UISTATE sessions=3 pager=2 kb=0         ← клавиатура упала
21.004 UISTATE sessions=3 pager=2 kb=1         ← и вернулась
```

Тот же паттерн на коммите #3 (`RECYCLE ... boundPos=2` → `kb=0` → `kb=1`). То есть симптом
воспроизводится **со второго** свайпа и повторяется на каждом следующем — ровно как в отчёте.

**FIXED (stable ids убраны) — провала нет:**

* ни одного `RECYCLE` холдера, чей `boundPos` равен только что закоммиченной странице;
* `IC` вызывается один раз за коммит, на вью закоммиченной страницы;
* `DETACH` встречается только у вью из пула, которые не на экране и не в фокусе;
* `kb=1` без единого провала: 42 сэмпла за три свайп-создания, `DROPS=0`.

**Негативное направление.** `kb force-hide` → `kb=0`; свайп создаёт вкладку (sessions 4→5) →
`kb=0` на всех 16 сэмплах. Исправление не воскрешает намеренно скрытую клавиатуру.

**Регрессии.** `switch tab 0` при 5 вкладках, `+` (new tab), закрытие вкладки — без крашей
(`logcat -b crash` пуст), `kb` ведёт себя как ожидается. Закрытие проверено на завершённых
сессиях (`run exit` + `close tab`): счётчик уменьшается 5→4→3→2→1, т.е. ветка уменьшения
списка (`syncWithServiceList` + побочная правка) отработала 5 раз без нареканий.

**Замечание по debug-хуку (не связано с правкой):** `close tab` для **живой** сессии счётчик не
уменьшает и через 8 с — `removeFinishedSession` снимает только завершённые. Счётчик берётся из
`TermuxService`, адаптер на него не влияет.

**Сборка.** `:app:compileDebugJavaWithJavac` и `:app:assembleDebug` — BUILD SUCCESSFUL
(с `--rerun`, без демона). Финальная чистая сборка (инструментация снята) переустановлена и
перепроверена тем же сценарием: `SAMPLES=42 DROPS=0`. Релиз не трогался.
