# Прокрутка вывода терминала: второй аудит (новые возможности)

Второй проход по той же системе. Базовое состояние — рабочее дерево после внедрения
A2 / A3 / B1 / C2 (см. §0.1 первого документа
[`glyph-scroll-optimization.md`](./glyph-scroll-optimization.md)).

Цель этого прохода — найти то, чего в первом аудите не было. Поэтому ниже **не повторяются**
A1 (скролл ⇒ `markAllDirty()`), A4 (кэш ранов), B1, B2, C1, C2, D1 — они уже описаны там.
Здесь только новые наблюдения, помеченные **E1…E6**, плюс два явных «рассмотрено и отвергнуто».

Все утверждения о координатах проверены по коду, не по памяти:

* `TerminalBuffer.externalToInternalRow()` (строка 238): `internal = mScreenFirstRow + external`.
* `TerminalBuffer.scrollDownOneLine()` (466–489): `mScreenFirstRow = (mScreenFirstRow + 1) % mTotalRows`.
* `TerminalView.onScreenUpdated()` (879–896): follow-text компенсация `mTopRow -= rowShift`.
* `TerminalView.repaintAfterUpdate()` (965–969): условие полного кадра.

в прошлом кадре, но из-за `markAllDirty()` + `mTopRow != oldTopRow` мы всё равно перерисовываем
весь экран на каждый vsync. Это и есть E1.

## 1. Разбор случая «пользователь в истории» (это ядро E1)

### 1.1 Что происходит сейчас

Пусть экран 48 строк, пользователь отмотал на 5 строк вверх (`mTopRow == -5`),
`isAutoScrollDisabled() == true`. Пришёл чанк вывода в 3 строки.

1. `TerminalEmulator.append()` пишет символы, вызывает `scrollDownOneLine()` трижды.
2. Каждый `scrollDownOneLine()` делает `markAllDirty()` (строка 469).
3. Плюс трижды `mScreenFirstRow = (mScreenFirstRow + 1) % mTotalRows`,
   `mActiveTranscriptRows += 1`.
4. `onScreenUpdated()` видит `isAutoScrollDisabled()` и делает компенсацию:
   `mTopRow -= rowShift` (строка 894) и `decrementYTextSelectionCursors(rowShift)`.
5. `repaintAfterUpdate(oldTopRow)`:
   * `mTopRow != oldTopRow` → **true** (компенсация изменила `mTopRow`);
   * `screen.isAllDirty()` → **true** (шаг 2).
   * ⇒ `invalidate()`, полный кадр.

### 1.2 Почему это лишняя работа

Проверим, что показывает пиксель. Пиксельная строка `p` рисует внешнюю строку `mTopRow + p`.

* До чанка: `mTopRow = -5`, строка `p` показывает внешнюю `p − 5`.
* После: `mScreenFirstRow` вырос на `rowShift`, `mTopRow` уменьшился на `rowShift`.
  Внутренний индекс строки `p`:
  `internal' = mScreenFirstRow' + (mTopRow' + p)`
  `= (mScreenFirstRow + rowShift) + (mTopRow − rowShift + p)`
  `= mScreenFirstRow + mTopRow + p = internal`.

**Тот же внутренний индекс ⇒ та же строка ⇒ те же пиксели.** Компенсация follow-text ровно
для этого и существует. Единственное, что реально изменилось на экране — это новые строки
*внизу* экрана (внешние `44..47` при `mTopRow = -5`), которые **не видны**: видимый диапазон
внешних строк — `[mTopRow, mTopRow + rows − 1] = [-5, 42]`, а новые строки лежат за его
правым (нижним) краем.

Итого: **ни один видимый пиксель не изменился, но нарисован полный кадр.**
И так на каждый чанк вывода, то есть до 60 раз в секунду, всё то время, пока пользователь
читает историю (`tail -f`, `cat big.log`, сборка, любой потоковый вывод).

### 1.3 Почему `markAllDirty()` там не нужен

`markAllDirty()` в `scrollDownOneLine()` поставлен потому, что содержимое *внешних* координат
действительно сдвигается: после `mScreenFirstRow++` то, что было внешней строкой `e`, стало
внешней строкой `e − 1`. Но внешняя координата — это не содержимое, это просто способ
адресации, и в follow-text режиме она сдвигается **ровно вместе с `mTopRow`**.

Правильная формулировка: скролл меняет не содержимое строк, а *отображение* внешних координат
в пиксели. Поэтому:

* если вид **скомпенсировал** сдвиг (`mTopRow -= rowShift`), содержимое на экране на месте —
  нужно красить только строки, в которые реально писали;
* если вид **не компенсировал** (живое дно, `mTopRow == 0`), сдвинулся весь экран — нужен
  полный кадр.

Разницу даёт «якорь» — внутренний индекс верхней видимой строки (см. E1a).

## 2. E1 — убрать полный кадр в режиме «пользователь в истории»

Две правки, они работают только в паре.

### E1a. Якорь содержимого вместо `mTopRow != oldTopRow`

`mTopRow` — это адрес, а не содержимое. Сравнивать надо внутренний индекс верхней видимой
строки: он не меняется при follow-text компенсации и меняется при любом реальном сдвиге
(скролл на живом дне, скролл пользователя, флинг, перетягивание скроллбара).

`TerminalBuffer.externalToInternalRow()` уже `public`, так что новый API не нужен:

```java
// TerminalView
private int mLastAnchorRow = Integer.MIN_VALUE;

// … в repaintAfterUpdate(), вместо `mTopRow != oldTopRow`:
final int activeTranscript = screen.getActiveTranscriptRows();
boolean anchorChanged;
if (mTopRow < -activeTranscript) {
    // onScreenUpdated() уже клампит, но onDraw() клампит ещё раз — перестрахуемся.
    anchorChanged = true;
} else {
    final int anchor = screen.externalToInternalRow(Math.max(mTopRow, -activeTranscript));
    anchorChanged = (anchor != mLastAnchorRow);
    mLastAnchorRow = anchor;
}

boolean fullRepaint =
    anchorChanged
    || isSelectingText()
    || mScrollbarDragging
    || screen.isAllDirty();
```

Проверка по случаям:

| Ситуация | `mTopRow` | `mScreenFirstRow` | якорь | нужен полный кадр? |
|---|---|---|---|---|
| живое дно, без вывода | 0 | = | не изменился | нет ✓ |
| живое дно, вывод со скроллом | 0 | +n | изменился | да ✓ |
| в истории, follow-text | −n | +n | **не изменился** | **нет** ← выигрыш |
| пользователь крутит колесо | изменился | = | изменился | да ✓ |
| флинг | изменился | = | изменился | да ✓ |
| снап вниз `mTopRow = 0` | изменился | = | изменился | да ✓ |

### E1b. `scrollDownOneLine()`: сдвигать dirty-диапазон, а не красить всё

Как показано в §1.2, содержимое внешней строки `e` после скролла оказывается во внешней строке
`e − 1`. Значит pending-диапазон грязных строк надо сдвинуть на −1 и добавить строку,
которую скролл открыл заново:

```java
public void scrollDownOneLine(int topMargin, int bottomMargin, long style) {
    if (topMargin > bottomMargin - 1 || topMargin < 0 || bottomMargin > mScreenRows)
        throw new IllegalArgumentException(...);

    if (topMargin == 0 && bottomMargin == mScreenRows) {
        // Полноэкранный скролл: содержимое внешней строки e переехало в e-1. Переносим
        // pending-диапазон вместе с ним вместо markAllDirty(). Вид компенсирует сдвиг
        // (mTopRow -= rowShift) там, где пользователь в истории, и тогда эти строки
        // окажутся вне видимой полосы — перерисовки не будет вообще.
        if (!mAllDirty && mFirstDirtyRow <= mLastDirtyRow) {
            final int minRow = -mActiveTranscriptRows;   // после инкремента ниже — ок
            mFirstDirtyRow = Math.max(minRow, mFirstDirtyRow - 1);
            mLastDirtyRow = Math.max(minRow, mLastDirtyRow - 1);
        }
        markRowDirty(mScreenRows - 1);                   // открывшаяся снизу строка
    } else {
        // Скролл-регион (htop, less): часть строк переезжает, часть остаётся. Таких
        // программ немного, а разбор «кто куда» — отдельная головная боль. Оставляем
        // как было.
        markAllDirty();
    }

    blockCopyLinesDown(mScreenFirstRow, topMargin);
    blockCopyLinesDown(externalToInternalRow(bottomMargin), mScreenRows - bottomMargin);
    mScreenFirstRow = (mScreenFirstRow + 1) % mTotalRows;
    if (mActiveTranscriptRows < mTotalRows - mScreenRows) mActiveTranscriptRows++;
    // … очистка открывшейся строки без изменений …
}
```

Три вещи, которые надо удержать:

1. **`mScreenRows - 1` — не видима в follow-text режиме.** Видимая полоса внешних строк —
   `[mTopRow, mTopRow + mScreenRows - 1]`, и при `mTopRow < 0` её верхний конец строго меньше
   `mScreenRows - 1`. То есть открывшуюся строку красить не нужно — `invalidateRowRange()`
   сам отсечёт её по `last < visTop` / `first > visBottom`. Она просто помечена на будущее:
   если пользователь вернётся вниз, `mTopRow` изменится ⇒ полный кадр ⇒ она будет нарисована.
2. **Писавшиеся строки не теряются.** Если в том же чанке программа писала во внешнюю строку
   20 (статус-строка TUI), `setChar` пометил 20; после сдвига это 19; пиксельная строка,
   которая показывала 20 до сдвига, показывает 19 после — это **та же** пиксельная строка,
   и она получит инвалидацию. Ничего не пропускается.
3. **Частичный скролл не трогаем.** `blockCopyLinesDown` для `topMargin > 0` физически
   переставляет ссылки в `mLines`, так что внешние строки остаются на месте, а скроллируемая
   область съезжает — одно правило сдвига тут не подходит. `markAllDirty()` остаётся.

### E1c. Что даёт E1 на практике

| Режим | Сейчас | После E1 |
|---|---|---|
| живое дно, потоковый вывод | полный кадр | полный кадр (без изменений) |
| в истории, потоковый вывод | полный кадр | **0–3 строки** (обычно 0 — курсор внизу за краем экрана) |
| в истории, ввод без скролла | полный кадр (из-за `isSelectingText()`/`mTopRow`) | 1 строка |
| печать в видимую строку из истории | полный кадр | 1 строка |

Случай «пользователь отмотал назад, чтобы почитать, пока идёт вывод» — это ровно тот сценарий,
на котором терминал и тормозит сильнее всего, потому что там одновременно и полный кадр
на каждый vsync, и пользователь смотрит на экран.

### E1d. Что обязательно делает E1 нетривиальным

Полный кадр сегодня — это ещё и единственный способ перерисовать скроллбар. После E1 в
follow-text режиме кадров не будет вообще, а `getScrollbarRange()` при этом растёт
(транскрипт пополняется) — бегунок должен ползти. Значит E1 **нельзя включать без E3**.

## 3. Остальные новые находки

### 3.1 E2 — dirty-диапазон это bounding box

`markRowDirty()` хранит только `[mFirstDirtyRow, mLastDirtyRow]`. Если за один чанк программа
пометила строку 0 (заголовок) и строку 47 (футер), «грязными» считаются все 48 строк.

Это не гипотетика: ровно так работают `htop`, `top`, `btop`, любые TUI с шапкой и подвалом,
и любые строки состояния с прогрессом. Каждый тик такого приложения — полный кадр, хотя
реально изменились две строки.

**Что делать.** Заменить пару `int` на битовое множество по строкам:
`long[] mDirtyRows` длиной `(mTotalRows + 63) / 64` — для 10000 строк это 157 `long`, 1.2 КБ.
Дальше два варианта, от простого к правильному:

* *Простой:* оставить одну полосу инвалидации, но в `render()` пропускать чистые строки.
  Не работает: `render()` перед отрисовкой заливает весь `dirtyRect` фоновым цветом
  (строки 306–318), и чистые строки внутри полосы будут стёрты.
* *Правильный:* `invalidateRowRange()` отдаёт по одному прямоугольнику на каждый
  непрерывный участок грязных строк, а `render()` заливает фон **построчно** — только
  под грязными строками. Клип канваса при этом остаётся объединением, так что лишнего
  не нарисуется.

Подвох, который надо учесть: `clearDirtyState()` сейчас вызывается в `repaintAfterUpdate()`,
то есть **до** `onDraw()`. С битовым множеством так делать нельзя — `render()` читает
признаки во время отрисовки. Переносим очистку в конец `render()`, и чистим только строки,
попавшие в `[renderStartRow, renderEndRow)`. Побочный плюс: строки, изменившиеся **вне**
экрана, сохранят признак до того момента, как станут видимыми (сейчас он теряется).

Приоритет ниже E1: E1 убирает полный кадр в самом частом сценарии, E2 — во втором по частоте.

### 3.2 E3 — скроллбару нужна собственная инвалидация (обязательно вместе с E1)

Сейчас `drawScrollbar(canvas)` вызывается на каждом кадре, включая частичные, и комментарий
в `onDraw()` (2506–2510) объясняет почему: полоса инвалидации во всю ширину всегда накрывает
зону скроллбара, и `render()` заливает её фоном, стирая бегунок.

После E1 в follow-text режиме кадров не будет вообще, а состояние скроллбара меняется
(растёт `mActiveTranscriptRows`, смещается бегунок). Значит в `onScreenUpdated()`, на пути
«nothing to repaint», нужно явно инвалидировать узкую полосу справа:

```java
if (nothingVisibleChanged) {
    screen.clearDirtyState();
    invalidateScrollbarBand();   // invalidate(getWidth() - band, 0, getWidth(), getHeight())
    return;
}
```

Ширина полосы — та же, что в `computeThumbRect()`. Это в точности тот «узкий прямоугольник»,
про который в первом аудите был пункт C3: он там отложен как «мелочь», а здесь оказывается
необходимым условием для E1.

#### 3.2.1 Поправка: полосу надо не заливать фоном, а перерисовывать строки

Наивная реализация («инвалидировать полосу, `render()` зальёт её фоном, `drawScrollbar()`
нарисует бегунок сверху») в сочетании с E2 **неверна**, и в этом легко ошибиться:

* сетка занимает всю ширину (`columns = viewWidth / fontWidth`), поэтому под бегунком
  находятся **символы** последних колонок;
* E2 пропускает негрязные строки, значит «залить фоном и ничего не нарисовать» = навсегда
  (до следующего полного кадра) сбривать правые 1–2 символа у всех строк полосы;
* если же заливку оставить, а строки не рисовать, останется и «призрак» старого бегунка —
  старые пиксели бегунка ничем не перекрываются.

Правильная схема:

1. Полоса = **объединение** старой и новой позиции бегунка, а не весь трек
   (`mLastThumbTop/mLastThumbBottom` запоминаются в `drawScrollbar()`; первое появление
   бегунка — весь трек, потому что восстанавливать нечего).
2. Строки, попавшие в это объединение, помечаются грязными
   (`markRowsIntersectingDirty()`) — тем же правилом, что и мигание курсора: пиксели
   изменились, хотя содержимое строки — нет.
3. `render()` дополнительно страхуется: если в клипе **ни одной** грязной строки, он
   рисует все строки клипа (`forceDraw`). Это перекрывает и случай, когда клип дал
   фреймворк (частичная перерисовка полного `invalidate()` при обрезке родителем) — там
   пропуск строк привёл бы к тому же сбриванию.

Цена — несколько строк на кадр вместо 48, выигрыш E1 сохраняется.

### 3.3 Почему не трогаем `isSelectingText()`

`repaintAfterUpdate()` считает `isSelectingText()` достаточным условием полного кадра.
Логика понятна: пока идёт выделение, `decrementYTextSelectionCursors(rowShift)` двигает
курсоры выделения вместе с текстом, и проще перерисовать всё.

После E1 это можно ослабить — выделение сдвигается так же, как follow-text, поэтому
достаточно частичного кадра. Но: рядом есть `renderTextSelection()` (рукоятки), который
вызывается только на полном кадре (строки 2498–2504), и его поведение при частичном клипе
надо проверять отдельно. Выигрыш при этом невелик — при живом дне полный кадр нужен всё
равно. Оставляем как есть, фиксируем как известный резерв.

### 3.4 E4 — A2: O(columns) → O(1) через флаг в `TerminalRow`

A2 (быстрый путь пустой строки) перед тем, как пропустить строку, сканирует все колонки:
`line[column] != ' ' || lineObject.getStyle(column) != uniformStyle`. На пустом экране это
48 × 80 загрузок массива на кадр — не бесплатно, но и не главное.

`clear(style)` (строка 201) уже делает строку и пустой, и однородной: `Arrays.fill(mText, ' ')`,
`Arrays.fill(mStyle, style)`. Значит признак можно поддерживать инкрементально:

* `clear(style)`: `mBlankAndUniform = true`;
* `setChar(column, codePoint, style)`: `if (codePoint != ' ' || style != mUniformStyle) mBlankAndUniform = false;`

Тогда A2 превращается в одну проверку поля. Тонкость: пробел с чужим стилем — это не пустая
клетка (может быть фон или подчёркивание), поэтому условие именно такое, а не «только
непробел».

Ожидаемый выигрыш — десятые доли миллисекунды на кадр. Делать последним, когда больше нечего.

### 3.5 E5 — `drawScrollbar()` на каждом кадре

Два `drawRoundRect()` (заливка + обводка в состоянии покоя) и два `setColor` на **каждом**
кадре, включая частичные. Плюс при не заданных `mScrollbarColorsSet` — чтение
`TerminalColors.COLOR_SCHEME` и `getPerceivedBrightnessOfColor()` дважды за кадр.
Ранний выход есть только при `getScrollbarRange() <= 0`, то есть при пустой истории.

Гейт по пересечению `mClipBounds` с зоной скроллбара возможен только после C3 (узкая полоса
инвалидации). Само по себе это мелочь; ценность — в том, что C3 перестаёт быть «мелочью»
и становится prerequisites для E1/E3/E5 сразу.

### 3.6 E6 — деление в `measureCodePoint()`

На каждый кодпоинт каждой строки каждого кадра:

```java
final float measuredCodePointWidth = measureCodePoint(...);
final boolean fontWidthMismatch = Math.abs(measuredCodePointWidth / mFontWidth - codePointWcWidth) > 0.01;
```

Одно деление на 3840 кодпоинтов (48×80). Если хранить в `bmpMeasures` не абсолютную ширину,
а уже нормированную `width / mFontWidth`, деление исчезает; массив пересчитывается там же,
где и сейчас (на смене `Typeface`/`textSize`). Эффект на уровне шума — записываю для полноты,
чтобы не возвращаться.

## 4. Что НЕ предлагается (рассмотрено и отвергнуто)

### 4.1 Blit-скролл через offscreen-bitmap

Классическая оптимизация терминалов: держать отрисованный экран в `Bitmap`, при скролле
делать `drawBitmap(bmp, 0, -dy * lineHeight, …)` и дорисовывать только открывшуюся строку.
Это сняло бы полный кадр и на живом дне — то есть закрыло бы A1 целиком.

Почему не предлагается:

1. **Прозрачность.** Фон рисуется через `PorterDuff.Mode.SRC` (C2). Блит поверх собственной
   картинки с SRC-заливками и альфой ≠ перерисовка из буфера: порядок композиции меняется,
   и полупрозрачные клетки начнут накапливаться. Придётся держать отдельный слой и
   композитить — это уже не «быстрая правка».
2. **Контракт клипа.** Вся частичная перерисовка построена на
   «`getClipBounds()` = что менять, `rowToPixelTop()` = куда рисовать». Блит ломает
   соответствие между клипом и содержимым: после блита «что менять» — это одна полоса,
   а «что уже нарисовано» — сдвинутая картинка. Придётся переписывать и `render()`,
   и инвалидацию.
3. **Упругий overdrag.** `glyphYOffset()` намеренно попадает в рендер тем же `yOffset`, чтобы
   инвалидация и отрисовка совпадали побитно (документировано в `TerminalView`, строки
   1000–1013). Блит добавляет третью систему координат.
4. **Readback.** На HW-ускоренном канвасе читать назад собственные пиксели дорого; держать
   параллельный software-`Bitmap` — это двойная отрисовка каждого кадра.

Выигрыш есть только в режиме «живое дно», где E1 ничего не меняет. Соотношение
сложность/риск/выигрыш — плохое.

### 4.2 Перенос трекинга грязных строк во внутренние индексы кольца

Выглядит заманчиво: помечать «грязной» не внешнюю строку, а слот `mLines[]` — тогда
`scrollDownOneLine()` вообще не трогал бы dirty-состояние (слот не меняется, меняется только
его внешний номер), и E1b не понадобился бы.

Отвергнуто: внутренний индекс ничего не говорит о том, какая строка **видна**. Видимость
определяется `mTopRow` во внешних координатах, и обратного отображения нет. Пришлось бы
на каждой видимой строке всё равно вычислять `externalToInternalRow()` и проверять бит —
то есть платить за битовое множество (E2), не получив взамен ничего, чего не даёт сдвиг
диапазона из E1b. E1b — 6 строк, вариант с индексами — новая структура данных плюс
изменения в `setChar`, `blockCopy`, `blockSet`, `allocateFullLineIfNecessary`.

### 4.3 Собственный `Choreographer`-коалесцинг вместо существующего

Уже сделано (`notifyScreenUpdateCoalesced`), один кадр на vsync. Менять нечего.

## 5. Порядок внедрения

1. **E1a + E1b + E3 — одним коммитом.** Они не имеют смысла по отдельности: E1a без E1b
   упрётся в `markAllDirty()`, E1 без E3 заморозит скроллбар.
   Перед коммитом пройтись по контрольному списку из §6.
2. **Замер** (§7). Если E1 не даёт измеряемого выигрыша — откатывать не надо, но E2 тогда
   тоже не стоит делать.
3. **E2** (битовое множество + построчная заливка фона). Отдельно, после E1.
4. **C3 + E5** (узкая полоса инвалидации, гейт скроллбара).
5. **E4**, потом **E6** — по остаточному принципу.

Не начато и не запланировано: A4 (кэш ранов со сдвигом) — ждёт замера «сканирование против
`drawTextRun`» из §8 первого аудита; B2, D1 — по-прежнему не в приоритете.

## 6. Контрольный список для E1 (это не формальность)

Правка touching `markAllDirty()` — самая опасная в проекте. Проверить руками на устройстве:

* [ ] Живое дно, `yes | head -c 100000` — текст не «залипает», нет артефактов внизу экрана.
* [ ] Живое дно, `htop` — шапка и подвал обновляются (частичный скролл ⇒ `markAllDirty()`).
* [ ] Живое дно, `vim` / `less` (alt screen) — переход туда-обратно не оставляет мусора.
* [ ] Отмотать в историю во время `tail -f` — картинка стоит, **бегунок скроллбара ползёт** ← ключевая проверка E3.
* [ ] Отмотать в историю, выделить текст, дождаться вывода — выделение не сползло.
* [ ] Отмотать в историю, затем резко вернуться вниз (снап) — полный кадр, артефактов нет.
* [ ] Флинг вверх/вниз во время вывода — нет «рваных» полос.
* [ ] Переворот экрана во время вывода (resize ⇒ `markAllDirty()`).
* [ ] Включить прозрачность фона (50%) — повторить первые три пункта.
* [ ] Очень длинная история: отмотать в самый верх 10000-строчного транскрипта и держать,
      пока идёт вывод (там follow-text срывается по условию
      `-mTopRow + rowShift > rowsInHistory` — полный кадр, как и было).

## 7. Как измерять E1

Микрозамер тут неприменим: выигрыш — в количестве отрисованных строк на кадр, а не в
скорости одной функции. Нужны системные метрики:

```bash
adb shell dumpsys gfxinfo com.termux framestats | head -40   # или
adb shell dumpsys gfxinfo com.termux
```

Смотреть на «Janky frames» и на распределение времени кадра до и после, в двух сценариях:

* **A (живое дно):** `while :; do echo …; done` — должно быть **без изменений**;
  если стало хуже — E1a даёт ложные полные кадры.
* **B (в истории):** тот же вывод, но отмотать на 200 строк вверх — должно стать
  заметно лучше.

Плюс грубый, но наглядный тест: включить в настройках «Показывать поверх» /
Profile GPU rendering (полосы на экране) и сравнить высоту столбцов в сценарии B.
