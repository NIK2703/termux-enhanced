# Проектирование упругого оттягивания вертикального скролла терминала (глифовое пространство)

**Цель:** вертикальный скролл истории терминала должен вести себя так же, как горизонтальный
пейджер сессий (см. `elastic-pager-overscroll-design.md`): упираясь в границу
(`mTopRow == 0` — «дно», живой вывод; `mTopRow == -activeTranscriptRows` — «верх» истории),
экран не останавливается колом, а **оттягивается за палец** с нарастающим сопротивлением и
пружинит обратно. Отдельное требование — **соразмерная реакция на импульс флинга**,
который прилетает в границу: чем жёстче флик, тем больше оттягивание, но безотносительно
к этому — всегда конечное и предсказуемое.

**Область:** `terminal-view/src/main/java/com/termux/view/TerminalView.java`
(новый блок «Elastic over-drag», без выделения в отдельный класс — см. §9).

**Ключевое отличие от пейджера:** смещение применяется **в глифовом пространстве** — как
добавка к смещению сетки glyph-grid, а не как `translationY` вью. Почему — §3.

---

## 1. Модель позиции: что такое «граница» в терминале

| Величина | Смысл | Диапазон |
|---|---|---|
| `mTopRow` | строка буфера в верхней строке экрана (истина в последней инстанции) | `[-getActiveTranscriptRows(), 0]`, целое |
| `mTopRow == 0` | прибиты к «дну», виден живой вывод | нижняя граница |
| `mTopRow == -transcript` | прибиты к «верху» истории, дальше некуда | верхняя граница |
| `mGridOffsetY` | сдвиг glyph-сетки, прибитой к верхнему краю вью | `-mFontLineSpacingAndAscent`, целое |
| `rowToPixelTop(r)` | view-y верхнего края внешней строки `r` | `round(glyphY + lsAndAscent + (r - mTopRow) * ls)` |

Скролл **в историю** = `mTopRow` уменьшается = контент едет **вниз**.
Скролл **к «дну»** = `mTopRow` растёт = контент едет **вверх**.

Новая величина:

| Величина | Смысл |
|---|---|
| `mOverdragRawPx` | накопленный (недемпфированный) проход пальца за границу, px, **знак = знак gesture-velocity** (`> 0` — за верх истории, `< 0` — за живое дно) |
| `mOverdragPx` | то, что реально применено к сетке: **целое** число px, `sign * round(damp(|raw|))` |

Инвариант: `mOverdragPx != 0 ⟹ mTopRow` лежит ровно на одной из двух границ.
Никакой другой код `mTopRow` в этот момент не двигает (флинг на границе стоит,
`onScreenUpdated()` на границе компенсацию не делает), так что инвариант держится сам.

## 2. Где измеряется оттягивание

Пейджер брал «невостребованный драг» из `EdgeEffect`-канала `RecyclerView`. Здесь такого
канала нет — скролл полностью рукописный, и это плюс: **оба направления (туда и обратно)
проходят через один `onScroll()`**, значит bleed реализуется точно, а не «на глаз».

```
onScroll(e, distanceX, distanceY)
  → dy = distanceY + mScrollRemainder
  → dy = applyOverdrag(dy)                 // ← новый узел: вернуть долг или взять оттягивание
  → deltaRows = (int)(dy / lineSpacing); mScrollRemainder = dy - deltaRows*lineSpacing
  → doScroll(e, deltaRows)
```

Направления (проверено по действующему коду и его комментариям):

* `distanceY < 0` — палец вниз, `mTopRow` уменьшается, **в историю**;
* `velocityY > 0` (флинг) — тоже **в историю** (ось скроллера инвертирована: `-velocityY`).

То есть `distanceY` и `velocityY` для одного и того же жеста **противоположны по знаку**.
Чтобы не путаться, внутри блока over-drag вводится своя ось

```
p = -distanceY        // p > 0 — палец толкает за ВЕРХ истории; p < 0 — за живое ДНО
```

и её знак **совпадает** со знаком `velocityY` и со знаком `mOverdragRawPx`. Один знак на
все три канала (драг, флинг, колесо) — это и есть «корректно» в требовании.

### 2.1 `applyOverdrag(dy)` — три случая

| Состояние | Вход | Действие |
|---|---|---|
| Не оттянуты (`raw == 0`) | `p > 0` и мы на верху истории | весь `dy` уходит в оттягивание, скролла нет (`вернуть 0`) |
| Не оттянуты | `p < 0` и мы на дне | то же, вниз |
| Не оттянуты | иначе | обычный скролл, `dy` не тронут |
| Оттянуты | `sign(p) == sign(raw)` | палец тянет **дальше за границу** → `raw += p`, скролла нет |
| Оттянуты | `sign(p) == -sign(raw)` | палец **возвращает** → `returned = min(|raw|, |p|)` гасит `raw`, остаток идёт в обычный скролл |

Первая строка таблицы считается **точнее**: драг разрезается ровно по границе. Пусть до
верхней границы осталось `toEdge = (mTopRow + transcript) * rowHeight` px, а палец просит
`p > toEdge`. Тогда `toEdge` всё ещё скроллит (и ровно доводит `mTopRow` до границы — `toEdge`
кратно высоте строки), а `p - toEdge` уходит в резинку. Без разреза быстрый свайп отдавал бы
весь дельта-кадр в `doScroll()`, тот обрезал его по границе, и до одного события жеста
(десятки px на быстром свайпе) терялось — заметный «залип» перед началом оттягивания.

**Bleed считается в RAW-пространстве**, а не в демпфированном (в отличие от пейджера, где
приходилось пересчитывать `inverseDamp`). Здесь это и проще, и физичнее: резинка — функция
расстояния пальца от границы, и возврат ровно по той же кривой означает «палец вернулся на
границу». Следствия:

* **позиция непрерывна**: `damp(0) == 0`, так что в момент пересечения контент ровно на границе;
* **скорость делает скачок с `C·v` на `v`** (с ~55 % до 100 % от скорости пальца) — это
  врождённое свойство любой резинки («контент догоняет палец»), в точке разворота скорость
  пальца минимальна, поэтому на глаз не читается;
* никакого `inverseDamp()` и никакого рассинхрона «сырой накопитель ↔ анимируемое смещение» —
  ровно тот класс бага, который сломал пейджер (§9.1 того дока), здесь исключён конструктивно.

### 2.2 Что НЕ должно оттягиваться

* `isSelectingText()` — драг выделяет текст;
* `mScrollbarDragging` — ползунок скроллбара и так прямое манипулирование;
* `isMouseTrackingActive() || isAlternateBufferActive()` — позицию скролла держит приложение,
  истории нет (тот же гейт, что уже стоит в ветке `EDGE_GLOW_ENABLED`);
* `getActiveTranscriptRows() == 0` — скроллить нечего, растягивать «пустышку» было бы ложью.

## 3. Где применяется смещение — глифовое пространство (принципиально)

```
private float glyphYOffset() { return mGridOffsetY + mOverdragPx; }
```

и используется **в трёх** местах, которые обязаны быть согласованы:

1. `onDraw()` → `mRenderer.render(..., mGridOffsetX, glyphYOffset(), dirtyRect)`;
2. `rowToPixelTop(r)` → инвалидация строк и хит-тест курсора;
3. `getColumnAndRow(...)` → хит-тест тача (выделение, мышь).

`TerminalRenderer.render()` внутри считает полосу строк от `base = yOffset + mFontLineSpacingAndAscent`
— то есть **та же формула, что в `rowToPixelTop()`**. Значит, передавая смещённый `yOffset`,
мы автоматически сохраняем согласованность частичных перерисовок: пока сетка оттянута и в терминал
приходит вывод, `repaintAfterUpdate()` инвалидирует полосу, а рендерер по смещённому `base`
выбирает ровно те строки, которые реально оказались под этой полосой.

### Почему не `translationY`

| Причина | Суть |
|---|---|
| **Рассинхрон dirty-rect** | `invalidate(0, top, w, bottom)` считается в координатах вью, а трансформация применяется фреймворком отдельно. При `translationY` зона повреждения и зона, где строки реально нарисованы, расходятся на `mOverdragPx` каждый кадр → рваные строки при частичных перерисовках. В глифовом пространстве обе формулы берут один и тот же `yOffset`. |
| **Лишнее уезжает** | `translationY` двигает скроллбар, ручки выделения и всё остальное, нарисованное в координатах вью. Оттягивание должно двигать **текст**. |
| **Дробные пиксели** | `updateSize()` намеренно прибивает `mGridOffsetY` к целому: на дробном смещении соседние прямоугольники фона строк делят дробную границу и антиалиасинг даёт видимые «волосяные» швы (комментарий там же). Смещение тоже округляется до целого px — §5. |

Смещение в глифовом пространстве даёт ещё один приятный эффект: «пустая» полоса у края
заливается **фоном терминала** (на полном кадре `drawColor(bg)`), а не обоями за вью —
при оттягивании видно фон самого списка, а не «дыру» в иерархии.
(При включённой прозрачности — фон полупрозрачный, и в полосе видно обои, тоже консистентно.)

## 4. Кривая оттягивания

> Физика вынесена в **`ElasticOverdrag`** (`terminal-view`) — один класс на обе поверхности
> (вертикальный скролл терминала и горизонтальный пейджер сессий). И терминал, и пейджер
> теперь только решают, **куда** девать смещение; как оно считается — определено ровно в одном
> месте. Дальше в этом параграфе описана именно она.

### 4.1 Предел — 20 % поверхности

От констант в dp отказались: всё считается от собственного размера поверхности `E`
(для терминала — высота view, для пейджера — ширина страницы):

```
M = 0.2 · E       предел оттягивания
L ≈ 0.748 · E     проход пальца, который этот предел достигает — вычислен, не выбран
```

Пропорциональность — это и есть смысл требования: предел читается как «эта поверхность
резиновая», а не как «где-то внутри есть пружина на 56 dp». Планшет и телефон тянутся на одну
и ту же долю своего экрана.

Два числа выше — не два независимых решения. `M` — это требование («20 % длины списка»).
`L` **выводится** из него и из наклона у границы:

```
f'(0) = π·M/(2L) = BOUNDARY_SLOPE = 0.42   ⇒   L = π·M/(2·0.42) ≈ 0.748·E
```

Именно здесь была ошибка прошлой редакции: `L` был прибит к одному экрану, а предел при этом
сжимался. При `L = E` и `M = 0.2·E` наклон у границы равен `π·0.2/2 = 0.31` — контент отстаёт
от пальца на две трети, и весь жест ощущается как «тащу что-то через патоку», независимо от
того, какое число написано в константе предела. Сейчас предел можно менять одной строчкой:
наклон у границы от этого не двигается, двигается только то, насколько глубоко резинка
загрубеет к концу хода.

### 4.1.1 Квант — строка глифов

Поверхность терминала состоит из строк: смещение применяется в пространстве глифов, и
«20 % высоты» — это не целое число строк. Поэтому `ElasticOverdrag` принимает квант `unitPx`
(для терминала это `mRenderer.mFontLineSpacing`), и предел округляется до **целого числа
строк**:

```
строк = E / rowHeight                       (целых видимых строк)
M     = round(0.2 · строк) · rowHeight
L     = M · π/(2·BOUNDARY_SLOPE)            (тоже целое число строк, т. к. L/M — константа)
```

На экране 1080 px при строке 44 px: 24 строки, `M = round(4.8)·44 = 220 px`, `L = 823 px`.
Погрешность против ровно 20 % — меньше половины строки (< 2 % предела), а выигрыш
видимый: в крайнем положении контент сдвинут ровно на 5 строк, и сверху не висит
половинка обрезанной строки. Тот же `rowHeight` — единственное место, где происходит
перевод «строки ↔ px» (§7.2); смешивать эти две шкалы и есть то, из-за чего «предел 20 %»
превращается в 17 % полезного хода.

У пейджера кванта нет (страница непрерывна) — он передаёт `0`, что означает «не квантовать».

### 4.2 Кривая — четверть синуса, а не гипербола

```
f(x) = M · sin( (π/2) · x / L ),   0 ≤ x ≤ L,   далее M
```

| свойство | следствие |
|---|---|
| `f''(0) = 0` | у самой границы отклик **точно линейный** — ни ватного старта, ни мёртвого миллиметра |
| `f'(0) = π·M/(2L) = 0.14` | экран идёт за пальцем на 14 % — втрое круче, чем 0.42, и вчетверо круче iOS (0.55): резинка сопротивляется очень жёстко с первого пикселя, поэтому жест читается как «тяну против чего-то тугого», а не как «контент просто продолжает ехать» |
| `f(L) = M`, `f'(L) = 0` | предел **достигается**, а не преследуется: при подходе к нему кривая уже горизонтальна, поэтому «стены» нет — палец просто перестаёт получать ответ |
| замкнутая форма `f⁻¹` | нужна для bleed-пути (§6, §7.2) — `x = (2L/π)·asin(y/M)` |

У гиперболы `C·M·x/(C·x+M)` (было и здесь, и в пейджере) предел — асимптота: при `x = L`
она даёт `0.33·M·…` ≈ 35 % предела, то есть заявленные «E/3» на практике превращались в
`E/9`. Плюс её `f''(0) ≠ 0` — сопротивление начинается на первом же пикселе.

Таблица (в долях `E`, то есть от высоты экрана):

| проход пальца `x` | 5 % | 10 % | 20 % | 30 % | 40 % | 224 % = `L` |
|---|---|---|---|---|---|---|
| смещение `f(x)` | 0.70 % | 1.40 % | 2.79 % | 4.17 % | 5.53 % | **20 % = M** |
| отдача `f(x)/x` | 14 % | 14 % | 14 % | 14 % | 14 % | 8.9 % |

Первые ~15 % экрана контент идёт за пальцем на 0.14 (сразу чувствуется сильное сопротивление),
дальше резинка плавно загрубеет и к концу хода мягко выходит на полку — предела достигает палец,
дошедший до ~224 % экрана (≈ 2.2 высоты), а не до упора в «∞». Это цена тройного сопротивления:
потянуть на те же 20 % экрана теперь нужно провести пальцем почти вдвое с лишним длиннее самого
экрана.

### 4.3 Накопитель обрезан по `L`, а не по «четырём экранам»

`raw ∈ [−L, L]`. Это одновременно предохранитель арифметики (ограниченный накопитель не
может дать NaN — см. §10) и исправление ощущения: палец, ушедший за `L`, больше ничего не
добавляет, но и **не копит долг**, поэтому возврат начинается с первого же пикселя назад, без
мёртвой зоны, пропорциональной тому, насколько далеко за предел ушли.

## 5. Округление до целого пикселя

Применяемое смещение — **целое** число px: `mOverdragPx = sign(raw) * round(damp(|raw|))`.

Причина: см. §3 (швы между фонами строк на дробных границах). Цена — квантование в 1 px,
что на 60 fps неразличимо (полный ход ~80 px за ~20 кадров). Побочно: `rowToPixelTop()`
остаётся целочисленной, и сравнение «смещение не изменилось → не инвалидировать» работает точно.

## 6. Отпускание и пружина

```
onUp / onCancel / onLongPress  →  releaseOverdrag()
```

* если `raw == 0` — ничего;
* иначе — `ValueAnimator.ofFloat(raw, 0f)` с интерполятором `ElasticOverdrag.SPRING` —
  замкнутой формой **критически задемпфированного** осциллятора (вторая производная,
  настоящая пружина, а не безье-кривая):

```
y(t) = (1 + ωt)·e^(−ωt)          переходная характеристика при ζ = 1
Y(t) = y(t) − y(1)·t             … с вычтенным остатком
value(t) = from · Y(t),    ω = 8.5,  длительность 140 ms
```

`Y(0)=1`, `Y(1)=0` **точно**, `Y'(t) = −ω²t·e^(−ωt) − y(1) < 0` на всём `[0,1]`.

**Колебаний нет вообще — и это доказуемо, а не «на глаз незаметно».** Критическое
демпфирование (`ζ = 1`) — самый быстрый возврат, который не осциллирует, а монотонность
`Y` исключает даже одиночный перелёт. Прежний `ζ = 0.65` перелетал на 6.8 % амплитуды:
при старом пределе 56 dp это было ~4 px (терпимо), при новом пределе в треть экрана это
уже ~15 px вздрагивания за границей — именно то, от чего требовалось избавиться.

При этом возврат по-прежнему **упругий**, а не «деревянный» ease-out: отпущенный из покоя
контент **разгоняется** к границе (максимум скорости на `t = 1/ω`, ~16 мс) и только потом
осаживается. Безье-ease-out делает наоборот — он быстрее всего в первом кадре, поэтому
читается как «уехало», а не как «вернулось».

**Зачем вычитать остаток.** У чистого `y(t)` к `t=1` остаётся ~1.7 %: аниматору пришлось бы
покрыть их одним кадром в конце — 4 px на оттягивании в 230 px, то есть заметный щелчок там,
где глаз всего чувствительнее. Вычитание `y(1)·t` размазывает эти 1.7 % по всему возврату
(это дрейф заметно меньше 1 % амплитуды), и движение приходит на границу уже **в покое**:
без щелчка, без корректирующего кадра. Побочно: «записать честный 0» в `onAnimationEnd`
становится настоящим no-op, а не заплаткой.

Анимируется **raw**, а не смещение. Прерывание пружины (новый тач) просто замораживает
`raw` там, где он был, и следующий драг естественно продолжает оттуда — никакого
пере-засева аккумуляторов, никакого второго источника правды.

### 6.1 Перелёта больше нет — и это снимает целый класс артефактов

Раньше перелёт уводил `raw` за ноль, то есть сетку в противоположную сторону: при
оттягивании за **верх истории** контент проскакивал границу «к настоящему» и пустая полоса
появлялась снизу. Полоса заливалась фоном и читалась как «недокрученная строка», но это
была именно заплатка на артефакт. Теперь граница не пересекается никогда:

* пустая полоса живёт только на той стороне, за которую тянут;
* §6.2 (инвариант «не оттянуты в покое») теряет последний источник хвоста;
* bleed-путь пейджера (§6 его документа) больше не может получить смещение, у которого знак
  противоположен породившей его оттяжке — а именно из этого там вырос баг «вывод всех сессий
  пропал». Защита «только уменьшение по модулю» оставлена, но теперь она страхует то, чего
  физика не допускает.

### 6.2 Инвариант «никогда не оттянуты в покое»

Тот же, что спас пейджер: после любого жеста смещение обязано быть ровно `0`.

* пишут ноль: `onAnimationEnd` пружины, `resetOverdrag()`;
* `resetOverdrag()` (мгновенно, без анимации) вызывается из
  `updateSize()` (смена геометрии/шрифта), `onDetachedFromWindow()`,
  `onScreenUpdated()` — если `raw != 0`, а `mTopRow` больше не на границе
  (очистили историю, alt-buffer, переключение сессии);
* страховка: `onUp/onCancel` постит `settleOverdragNow()` — «если пружины нет, драга нет,
  а `raw != 0` → сбросить». Стоит одна проверка, спасает от любого забытого пути выхода.

Худший случай при ошибке в арифметике — **отсутствие анимации**, а не «содержимое уехало
навсегда» (и тем более не NaN-трансформация, как было у пейджера: `raw` ограничен
`MAX_RAW_TRAVEL_PX`, `damp()` на конечном аргументе конечна и монотонна).

## 7. Импульс флинга в границу — соразмерность

Это вторая половина требования. Флинг работает на пиксельной оси `OverScroller`
(`startPx = mTopRow * rowHeight`, `minPx = -transcript*rowHeight`, `maxPx = 0`); когда он
упирается, `runFlingFrame()` уже умеет это замечать — там стоит (выключенный)
`EDGE_GLOW_ENABLED`-блок с `mScroller.getCurrVelocity()`. Он и переиспользуется.

### 7.1 Что подаётся на вход

`getCurrVelocity()` — **норма**, всегда `≥ 0`, поэтому знак берётся из
`mFlingRawVelocity` (gesture-скорость, с которой флинг запущен; `> 0` = в историю = верх).
Важно: берётся скорость **в момент удара**, а не при запуске — флинг успевает затормозить,
и именно остаточная скорость определяет силу удара. Это и есть «соразмерно».

Вход обрезается снизу порогом, чтобы переход был непрерывным:

```
vEff = max(0, v - mMinFlingVelocity)          // ниже порога флинга — отскока нет вообще
```

### 7.2 Импульс → дальность вылета: резинка как пружина в пространстве смещения

Флинг — это не палец, и считать его пальцем (как делала предыдущая версия этой модели)
нельзя. Палец ведёт контент **кинематически** (§4.2): за каждым пикселем хода пальца
следует `BOUNDARY_SLOPE` пикселей смещения, и ровно этот коэффициент и есть сопротивление,
которое пользователь чувствует. У флинга пальца нет — у него есть **скорость**, и резинка
должна её погасить. Поэтому для флинга работает *динамика*:

* **Скорость входа — скорость импульса.** Контент уже движется со скоростью `v`, когда
  доезжает до границы, поэтому в резинку он входит с той же скоростью: `ẏ(0) = v`, без
  каких-либо коэффициентов перед ней. Флинг вдвое быстрее — вылет вдвое быстрее. (Раньше
  импульс прогонялся через кривую хода пальца, то есть входил со скоростью
  `BOUNDARY_SLOPE·v` — 14 % от скорости удара — и потом должен был проехать то же
  расстояние в восемь раз медленнее. Это и была «анимация, ставшая втрое медленнее».)
* **Дальность — дело жёсткости.** Как далеко эта скорость уедет, пока резинка её не
  поглотит, решает только жёсткость резинки: `y_peak = v / ω`. Сопротивление выросло
  втрое — жёсткость выросла втрое — и вылет стал **втрое короче и втрое быстрее**.
  В предыдущей версии амплитуда была привязана к доле предела, поэтому утроение
  сопротивления не меняло расстояние вовсе, а растягивало только время: худшее из двух.

Резинка — маятник **в пространстве смещения**, то есть в том пространстве, в котором глаз
и измеряет движение (а не в пространстве хода пальца):

```
U(y) = A·(1 − cos κy),   κ = π/(2M),   A = (ω/κ)²
ÿ    = −U'(y) = −A·κ·sin(κy)
```

`A` подобрано так, чтобы частота малых колебаний была ровно `ω` — той самой, на которой
работает пружина возврата (§6). Одна резинка, одна жёсткость, две половины одного отскока:
флинг её нагружает, пружина разгружает, и в точке разворота они встречаются в покое.

Точка разворота — в замкнутой форме из `½v² = U(y_peak)`:

```
y_peak = acos(1 − (v·κ/ω)² / 2) / κ        (обрезано по M)
```

Для всех обычных фликов это просто `v/ω` (аргумент `acos` близок к 1, а
`acos(1 − ε²/2) ≈ ε`), и насыщение до предела включается лишь на запредельных скоростях.
Иными словами: **вылет проезжает одну постоянную времени на той скорости, с которой
пришёл флик**. Для сравнения — та же таблица до и после:

| `vEff` (px/s) | отскок сейчас (`ω = 60.7 рад/с`) | отскок в предыдущей модели |
|---|---|---|
| 1000 | 16 px (7 % предела) | 31 px (14 %) |
| 2000 | 33 px (15 %) | 61 px (28 %) |
| 3683 | 61 px (28 %) | 110 px (50 %) |
| 5000 | 82 px (37 %) | 168 px (76 %) |
| 10 000 | 165 px (75 %) | 220 px (полка) |
| ≥ 22 000 | 220 px (полка) | 220 px (полка) |

Сантехнический предел `OVERDRAG_MAX_ABSORB_VELOCITY_DP` (8000 dp/s) оставлен только как
защита арифметики.

Здесь больше нет ни модели трения платформы, ни «экранов строк, которые флику осталось
проехать», ни высоты глифов: жёсткость резинки на три порядка больше торможения флинга
(`ω²y ≈ 3·10⁵ px/s²` при растяжении 80 px против ~2·10³ px/s² трения), так что на этом
коротком участке трение — шум; а амплитуда теперь свойство резинки, а не контента, и
измерять её в строках незачем. Высота строки по-прежнему нужна, но только там, где она и
была уместна — как квант предела (§4.1.1).

### 7.3 Сценарий

```
runFlingFrame():
  …
  if (!mFlingDeltaMode && !mFlingAbsorbedAtEdge && mTopRow на границе && v > mMinFlingVelocity):
      absorbIntoOverdrag(sign(mFlingRawVelocity), v)   // ElasticOverdrag.impact() + startOverdragImpact()
      mFlingAbsorbedAtEdge = true
```

Флинг **не penetrating** границу: он доезжает до неё по сплайну и останавливается
(как `EdgeEffect.onAbsorb`), дальше отскок играет отдельная пружина. Это осознанный выбор —
см. §8.

Одновременные сценарии корректны, потому что смещение аддитивно к `mTopRow` и не мешает ему:

* **флинг внутрь из оттянутого состояния** → флинг крутит `mTopRow`, пружина гасит смещение,
  обе анимации живут параллельно и обе приходят в ноль/цель;
* **флинг наружу** → доезжает до края, absorb, отскок.

### 7.4 Колесо / тачпад

У колеса нет события «отпустил», поэтому держать оттягивание нельзя — был бы залипший сдвиг.
Поэтому колесо (`onGenericMotionEvent`) получает **одноразовый** вариант: если тик упирается
в границу, играется absorb с небольшой амплитудой и **сразу** `releaseOverdrag()`.
Никакого удерживаемого состояния.

### 7.5 Вылет во времени — почему он теперь «знает» скорость импульса

Амплитуда из §7.2 — это ещё не всё: нужен **тайминг**. Раньше импульс просто записывался в
`mOverdragRawPx` в один кадр — список **телепортировался** на вершину, анимировался только
возврат, и скорость вылета не имела никакого отношения к скорости удара.

Теперь весь вылет проигрывается по времени. `ElasticOverdrag.impact(v, …)` интегрирует
маятник из §7.2 симплектическим Эйлером по 1 мс (`ω·dt ≈ 0.06` — шаг безусловно устойчив,
ошибка энергии — доли пикселя, накопления нет), а последний сэмпл **пришпиливается** к
аналитической `y_peak`: интегратор владеет *временем*, алгебра — *дальностью*. Два числа
сходятся в пределах пикселя.

Длительность — четверть периода маятника, `(π/2)/ω ≈ 26 мс` (на больших амплитудах до
~31 мс: маятник почти изохронен). Это ровно столько, сколько и должно быть: контент
въезжает за границу на скорости `v`, и его надо остановить, не уведя далеко, — быстро здесь
и есть правильно. Для сравнения: предыдущая версия модели тратила на тот же вылет ~460 мс,
потому что считала движение в **пространстве хода пальца**, где эффективная жёсткость равна
`A·κ² ∝ 1/L²`, а `L` при утроении сопротивления утроился. Формально «утроить
сопротивление» она выполнила, а на глаз получилось «анимация стала втрое медленнее» —
ровно наоборот.

Сэмплы публикуются как **raw-проход** (то, что анимируют обе поверхности), хотя интеграция
идёт в смещении: `damp(undamp(y)) == y` точно, поэтому воспроизводится ровно та кривая,
которая интегрировалась, а инвариант «raw — единственный источник правды» не нарушается.

Обе поверхности играют сэмплы одинаково: `ValueAnimator` на `1 мс`-шагах с **линейным**
интерполятором (сами сэмплы и есть тайминг; любое сглаживание здесь переформировало бы
движение), на каждом кадре пишется `raw = base + edgeSign · impact.travelAt(progress)`, а по
завершении `travelAt(1) = peak` передаётся в критически демпфированную пружину возврата —
резинка нагружена импульсом и отпущена пружиной, что и есть деление, которое есть в жесте.

Связка с инвариантами: `mOverdragImpact` отменяется вместе с пружиной (`cancelOverdragAnimators`),
а `settleOverdragNow`/`releaseOverdrag` встают на него в Guard («ещё растягивается — само
отпустится»), поэтому прерывание вылета пальцем или вторым, более сильным флингом не оставляет
список оттянутым. Пейджер зеркалит то же самое через `mImpact`/`cancelAnimators`.

## 8. Варианты, которые отпали

| Вариант | Почему не годится |
|---|---|
| **A. `setTranslationY` на `TerminalView`** | Рассинхрон dirty-rect, уезжает скроллбар, дробные пиксели — всё в §3. |
| **B. Двигать сам `mTopRow` за границу («несуществующие строки»)** | `mTopRow` — индекс в буфере: `-transcript-1` либо кинет `IllegalArgumentException` в `getLineOrBlank()`, либо нарисует мусор. Плюс сломалась бы компенсация истории в `onScreenUpdated()`. |
| **C. Дать флингу penetrating границу через `OverScroller.fling(..., overY)`** | Самый «айосный» вариант, но требует переписать жизненный цикл флинга (`springBack()`, завершение по `isFinished()`, tail-cut) и теряет общую резиновую кривую: пробитие диктуется сплайном скроллера и жёстко клипуется по `overY`. Риск ради нюанса ощущения — именно так рождаются баги уровня «пропал вывод всех сессий». Отклонён. |
| **D. Вернуть системный `EDGE_GLOW_ENABLED`** | Glow — чисто визуальный оверлей, контент не двигается; задача стоит про движение. Код остаётся на месте (выключен), перехват over-drag стоит **перед** ним, так что при включении обоих побеждает over-drag. |
| **E. Вынести в отдельный класс-контроллер** | Как `PagerOverscrollController` не выйдет: тут нужен доступ к `mTopRow`, `doScroll()`, `rowToPixelTop()`, `onDraw()` и к трём каналам ввода. Интерфейс получился бы больше самой логики. Оформлено отдельным секционированным блоком внутри `TerminalView`, как уже сделано для скроллбара. |

## 10. Инварианты (итог)

1. **Конечность.** `raw` обрезан по `L` (= 2.244 высоты view), `damp()` на ограниченном
   аргументе конечна (`|sin| ≤ 1`), нечисловое значение приравнивается к `0`.
2. **Ограниченность.** `|mOverdragPx| ≤ M = 0.2 · высоты` — целиком производное от размера
   поверхности, без внешних констант, которые могли бы рассинхронизироваться с `L`.
3. **Целые пиксели.** Смещение сетки целое, швы между строками не появляются.
4. **Только на границе.** `mOverdragPx != 0` возможно лишь при `mTopRow` ровно на границе;
   `onScreenUpdated()` это проверяет и сбрасывает, если перестало быть правдой.
5. **Никогда не оттянуты в покое.** После жеста — ровно `0` (пружина, `resetOverdrag()`,
   posted `settleOverdragNow()`).
6. **Аддитивность.** Смещение не участвует ни в `mTopRow`, ни в физике флинга,
   ни в компенсации истории — худший исход любой ошибки: «анимации не было».
