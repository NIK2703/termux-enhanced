# Прозрачность фона и блочные глифы (`▀ ▄ █ ▌ ▐ ░ ▒ ▓`) — расследование

**Дата:** 2026-09-11
**Ветка:** `perf/glyph-scroll-optimization`
**База:** `de4616ec` + незакоммиченная правка `terminal-view/.../TerminalRenderer.java` (+73 / −8)
**Устройство:** LineageOS `marble`, 1080×2400, wireless adb, root; `fontsize=26`,
`terminal-background-transparency=20`, `blur=true`, `blur-radius=0`, `color-scheme-light=Monet`

Документ фиксирует весь путь: жалобу, инструментарий, диагноз, реализованную правку,
её проверку на устройстве и **остаточную аномалию, которая пока не закрыта**.

---

## 1. Жалоба

Пользователь включил прозрачность фона 20 % и увидел в opencode **непрозрачную полосу в нижней
части поля ввода**. После первой правки полоса стала полупрозрачной, но «отображается странно:
глифы отображаются какими-то прямоугольниками, несоразмерными области, в которой они должны
отображаться».

## 3. Диагноз

### 3.1 «Полоса» — это глиф, а не фон

`uiautomator dump` показал нижнюю границу поля ввода opencode буквально:

```
  ┃  Build · GLM 5.3 Flash Chat.B.AI
  ╹▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀
  tab agents  ctrl+p commands
```

То есть строка `  ╹` + 61 × **`▀` U+2580 UPPER HALF BLOCK**.

Геометрия это подтверждает: прямоугольник фона строки (pass A) покрывает **всю** строку
(`mFontLineSpacingAndAscent = mFontLineSpacing + mFontAscent` ⇒ верх = верх строки), а полоса
занимает только **16 px из 31** — ровно верхнюю половину ячейки. Половину строки фон нарисовать
не может.

### 3.2 Единственное место в рендерере без `mBackgroundAlpha`

`grep -rln mBackgroundAlpha` по всему репозиторию возвращает **один файл** —
`terminal-view/src/main/java/com/termux/view/TerminalRenderer.java`. Внутри него все 12 мест
`setColor` разобраны поштучно:

| Строки | Что | alpha учтён? |
|---|---|---|
| 430–432 | цвет фона ячейки (`bgColor`) | да |
| 460 / 503 | базовая заливка (SRC) | да |
| 582 / 587 | быстрый путь A2 для пустых строк | да |
| 889 / 903 | групповая заливка pass A | да |
| 1091 / 1098 | заливка mismatch-рана (SRC) | да |
| 1114 / 1121 | курсор (SRC) | да |
| **1146 → `drawTextRun` (1197)** | **заливка глифа** | **НЕТ** |

```java
if (foreColor != mLastPaintForeColor) {
    mTextPaint.setColor(foreColor);          // 1146 — непрозрачный ARGB
    mLastPaintForeColor = foreColor;
}
...
canvas.drawTextRun(text, startCharIndex, runWidthChars, startCharIndex, runWidthChars,
                   left, y - mFontLineSpacingAndAscent, false, mTextPaint);   // 1197, SRC_OVER
```

`TerminalView.java` чист: единственный `drawColor` (2668) alpha применяет, скроллбар рисует
заранее запечённые alpha-значения (`0x1F`/`0x0D`/`0x33`/`0x88`/`0xBB`).

### 3.3 Семантика `mBackgroundAlpha` (важно!)

```java
mBackgroundAlpha = Math.round(255f * (100 - percent) / 100f);   // 271
```

При «прозрачности фона 20 %» это **204**, т.е. фон на 80 % непрозрачен и 20 % обоев просвечивают.
Это **непрерывность фона**, а не «альфа прозрачности». Любая правка глифа обязана использовать то
же число, что и фоновые заливки, иначе блок-глиф перестанет совпадать с фоном.

## 4. Почему очевидные правки не работают

1. **Просто подставить alpha в `mTextPaint`.**
   SRC_OVER от `(C, a)` поверх базы, которая сама `(A, a)`, даёт `2a − a²`. При `a = 0.8`
   (наш случай) это `0.96` — по-прежнему почти непрозрачно. Именно это и наблюдалось.

2. **`PorterDuff.SRC` на текстовой кисти.**
   У текстовой кисти покрытие **вне глифа равно 0**, поэтому SRC затрёт всю остальную часть
   ячейки. По той же причине заливка mismatch-рана (1089–1101) не использует `mTextPaint`,
   а ходит через `mBgSrcPaint`.

## 5. Правка №1 — `DST_OUT` + `SRC_OVER` (заменена, см. §12)

> **Исторический раздел.** Двойная отрисовка закрыла исходную жалобу, но на AA-крае и в
> ~1 px перекрытии соседних глифов давала сетку/ободок. Итоговая правка — одна отрисовка в
> `SRC_ATOP` (§12).

Идея: блок-элемент — это по смыслу фон, поэтому его надо **вырезать из уже нарисованной ячейки
и поставить обратно с альфой фона**. Двойная отрисовка, без offscreen-слоя.

```java
/** H1: true, если все кодпоинты рана — блочная «заливка площади» (U+2580..U+259F). */
private boolean[] mRunBlockFill;

/** DST_OUT-близнец: вырезает форму глифа из уже залитой ячейки. */
private static final PorterDuffXfermode DST_OUT_XFERMODE =
        new PorterDuffXfermode(PorterDuff.Mode.DST_OUT);
```

Разрыв рана (блочный ран не должен сливаться с соседним текстом):

```java
final boolean blockFill = codePoint >= 0x2580 && codePoint <= 0x259F;

if (blockFill != lastRunBlockFill || style != lastRunStyle || insideCursor != lastRunInsideCursor
        || insideSelection != lastRunInsideSelection
        || fontWidthMismatch != lastRunFontWidthMismatch || scaleChanged) { ... }
```

Отрисовка (`drawRunText`):

```java
final float textY = y - mFontLineSpacingAndAscent;
if (blockFill && mBackgroundAlpha < 255) {
    // 1) вырезаем форму глифа из ячейки (базовая заливка, фон, выделение, курсор)
    mTextPaint.setXfermode(DST_OUT_XFERMODE);
    canvas.drawTextRun(text, startCharIndex, runWidthChars, startCharIndex, runWidthChars,
                       left, textY, false, mTextPaint);
    mTextPaint.setXfermode(null);
    // 2) штампуем его обратно ровно с (foreColor, mBackgroundAlpha)
    final int translucentForeColor = (foreColor & 0x00FFFFFF) | (mBackgroundAlpha << 24);
    mTextPaint.setColor(translucentForeColor);
    mLastPaintForeColor = translucentForeColor;
}
canvas.drawTextRun(text, startCharIndex, runWidthChars, startCharIndex, runWidthChars,
                   left, textY, false, mTextPaint);
```

Внутри глифа результат `a·C + (1−a)·W` — идентично прямоугольнику pass A того же цвета; вне
глифа ячейка не тронута. Обе отрисовки идут под одной и той же матрицей, поэтому
масштабированный (font-width-mismatch) случай не затронут.

Сопутствующее: `mRunBlockFill` в `ensureRunCapacity()`, `runsMerge()` (`&& mRunBlockFill[a] ==
mRunBlockFill[b]`), `copyRun()`, новый параметр `addRun(..., boolean blockFill)` (хвостовой ран
передаёт `false`), и `blockFill` в сигнатуре `drawRunText(...)`.

## 7. Остаточная аномалия — ЗАКРЫТО в §12

На реальном экране opencode строка границы выглядит **не так, как контрольный ран**.

`after_reboot.png` (свежий запуск opencode, 1080×2400):

| y | mean | `#dark(<185)` | что это |
|---|---|---|---|
| 1359 | **184.5** | **563 / 988** | тёмная линия во всю ширину |
| 1360…1374 | 211.5 | **0** | «нормально» |
| 1375 | **186.0** | **484 / 988** | тёмная линия во всю ширину |
| 1376… | 218.5 | 0 | обычная строка |

То есть на месте сплошной полосы — **полая полоса высотой 16 px**: две тёмные линии на верхней и
нижней границе чернил, между ними пусто. Та же картина в `now.png` (`y = 987` и `1003`).

Дополнительно, внутри полосы видна **сетка**: на каждой границе ячейки (`x = 3 + 16k`) проходит
1 px **более светлая** линия, т.е. чернила занимают ~15 px из 16 и не замощают ячейку.

**Почему это не объясняется одной отрисовкой:** внутренность полосы всего на ~8 единиц темнее
соседних строк (211 против 219) ⇒ цвет чернил близок к цвету фона строки. А обе линии-ободка
темнее фона на ~35 единиц (184 против 219) ⇒ это **не** может быть результатом одной
alpha-композиции `▀`. Одно и то же значение `C` не даёт одновременно +8 в середине и −35 по краю.

Косвенно та же тема видна на логотипе: в `logocmp.png` (BASELINE `de4616ec` → FIXED `8bdcb09` →
HEAD/perf `7142df`) штрихи букв в последнем варианте разбиваются видимой сеткой на
прямоугольники размером с ячейку.

## 9. Гипотезы и следующие шаги

**H1. Цвет чернил границы opencode близок к цвету фона рамки.**
Тогда при `a = 0.8` заливка почти не отличается от фона и «выживают» только края.
Проверка: валидный truecolour-репро с `fg == bg` (сначала контрольная строка с заведомо
известным цветом, потом тест).

**H2. У `DST_OUT`-выреза и `SRC_OVER`-штампа разные следы.**
Чернила `▀` — глиф fallback-шрифта с advance 18 px, масштабированный в ячейку 16 px, поэтому
по горизонтали остаётся ~1 px зазора на ячейку (это и есть видимая сетка). Это объясняет сетку,
но **не** объясняет ободок темнее и чернил, и фона.

**H3. Замешана вторая отрисовка.**
Кандидаты: `CHARACTER_ATTRIBUTE_UNDERLINE` / `STRIKETHROUGH` (но ободки разнесены ровно на 16 px
= высота полублока, что не совпадает с разносом подчёркивания и зачёркивания при `fontsize=26`),
либо взаимодействие с прямоугольником фона строки.

**Что делать дальше:**

1. **Получить точный байтовый поток opencode для строки границы** (`script(1)` или лог pty) —
   чтобы знать реальные SGR-атрибуты, а не догадываться.
2. Построить truecolour-репро **с валидацией**: сначала контрольная строка с известным цветом,
   и только если она разобралась верно — доверять остальным.
3. Решить вопрос семантики: сейчас блок-глиф красится в `mBackgroundAlpha` (204), т.е. **так же
   непрозрачно, как фон**. Это согласовано с фоном, но означает, что тёмный `▀` всё равно
   читается как почти непрозрачная полоса — то есть исходная жалоба пользователя закрыта лишь
   частично. Альтернатива — использовать *прозрачность* (`255 − mBackgroundAlpha` = 51), если
   блок-глиф должен быть именно «фоновым», а не «как фон».
4. Убрать сетку: рисовать блочный ран через `canvas.clipRect` по ячейкам либо заливать ячейку
   прямоугольником (`drawRect`) вместо опоры на полублок из шрифта.

## 10. Грабли окружения (пригодятся в следующий раз)

* **IP устройства динамический.** После ребута `192.168.105.245` умер, новый адрес —
  из `adb mdns services` (`192.168.204.111:5555`). Не хардкодить.
* **`uiautomator dump` иногда отдаёт пустоту** (сначала попадается узел клавиатуры, а
  `content-desc` терминала содержит `&#10;`). Надёжно: `grep terminal_view_page` по сырому XML.
* **`screencap` raw = 16-байтовый заголовок** `<IIII>` (w, h, fmt, colorspace), дальше RGBA.
* **`input text` не понимает пробелы** — `%s`; перевод строки — `keyevent 66`.
* **Скрипты для `adb push` нормализовать в LF** (`\r\n` → `\n`), иначе `bash` падает.
* **Инъекция в терминал без `input`:** `su -c 'printf "…\n" > /proc/<pid>/fd/<pty-master-fd>'`;
  master'ы видно как `/dev/ptmx` в `ls -l /proc/<pid>/fd`.
* **git-аномалия окружения** (из `MEMORY.md`): `git commit` через Bash удаляет
  `.git/refs/heads/<branch>` — лечится записью loose-ref полным 40-символьным хешем.

## 12. Продолжение (2026-09-11, позже в тот же день)

§7 разобран в `docs/block-glyph-size-regression.md`: аномалия оказалась **композиционной**,
а не геометрической (правка не двигала глифы ни на пиксель), а §9.3/§9.4 закрыты:

* семантика выбрана в пользу «блочный глиф = фон» (§9.3), т.е. `mBackgroundAlpha`, как и было;
* сетка и ободок устранены **не** заливкой прямоугольниками (§9.4), а заменой пары
  `DST_OUT` + `SRC_OVER` на **одну** отрисовку в `PorterDuff.Mode.SRC_ATOP` — она линейна
  по покрытию глифа `m` и сохраняет альфу назначения, поэтому точна и на AA-крае, и в
  ~1 px перекрытии соседних блочных глифов;
* приёмочный тест: свёрнутый по фазе ячейки разброс профиля упал с ~4 единиц до 0.1
  (ниже одного 8-битного уровня), чернила не изменились. Детали и таблица — в §6.4
  документа `block-glyph-size-regression.md`.
