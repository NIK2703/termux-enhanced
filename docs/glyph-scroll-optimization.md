## 2. Что УЖЕ оптимально (не трогать)

Эти вещи сделаны правильно и являются частью инвариантов — перечисляю, чтобы в плане правок
не пришлось их заново обосновывать:

1. **Кольцевой буфер и O(1) скролл.** `scrollDownOneLine` не копирует строки для полного экрана —
   двигается только `mScreenFirstRow` (`TerminalBuffer.java:478`). Скролл «в буфере» бесплатный.
2. **Lazy-аллокация строк.** `mLines[i] == null` пока строка не записана; `getLineOrBlank()` для
   чтения из `onDraw` без аллокации (`:534`, `:547`).
3. **Dirty-строки.** Частичная перерисовка при точечных изменениях (`markRowDirty` +
   `invalidateRowRange` + clip-rect в рендере, `:269-277`). На «тихом» экране кадр стоит почти ноль.
4. **Схлопывание кадров вывода** через `Choreographer` (`TerminalSession.java:246`): парсинг
   делается на каждый чанк, перерисовка — не чаще одного раза на vsync.
5. **A1-memo в `findStartOfColumn`** (`TerminalRow.java:106-116`): снимает квадратичность
   заполнения строки при CJK/эмодзи. Проверено: сброс кэша стоит на всех путях со сдвигом
   индексов (`:263`, `:268`, `:288`, `:306`) и при попадании «внутрь» широкого символа (`:150`).
6. **Кэш ширин `WcWidth.BMP_WIDTH_CACHE`** и **кэш метрик `bmpMeasures`** (общий на
   (typeface, textSize)) — по одной таблице на 64 KiB / 256 KiB вместо `measureText` на символ.
7. **Двухпроходный рендер строки** (фоны пачками → текст) и группировка соседних одинаковых фонов
   в один `drawRect` (`TerminalRenderer.java:424-462`).
8. **Кэш состояния `Paint`** (`:133-137`, `:624-643`): сеттеры дергаются только при смене стиля.
9. **Физика fling в пикселях**, квантование только на выходе; tail-cut; перенос остатка
   `mScrollRemainder` между жестами. См. `android-like-terminal-scrolling.md`.
10. **Овердраг в глифовом пространстве** (`glyphYOffset()`), а не `translationY`: инвалидация и
    отрисовка считают одну и ту же `y` — иначе расхождение на величину оттяжки каждый кадр.

## 3. Центральный факт: скролл обязан стоить полный кадр

`TerminalBuffer.scrollDownOneLine()` вызывает `markAllDirty()` (`:469`). С этого момента
`repaintAfterUpdate()` выбирает полную перерисовку (`:965-975`) → `invalidate()` без rect →
`onDraw` → `render()` со всеми строками.

**Почему иначе нельзя в глифовой модели.** Скролл — это сдвиг `mScreenFirstRow` по кольцу.
Сами `TerminalRow` не перемещаются, меняется отображение «строка → y». Значит на экране
*каждая* строка оказалась на новой координате, и перерисовать надо все. Частичный dirty-rect здесь
применим только к полосе, куда «дорисовались» новые строки, а остальной экран всё равно должен быть
перевыведен на сдвинутых позициях.

Стоимость одного кадра (оценка для экрана 200×50, `rowHeight ≈ 30 px`):

| Этап | Объём | Оценка |
|---|---|---|
| Сканирование ячеек (getStyle + WcWidth + measure + ветвления) | 10 000 ячеек | 0,1–0,2 мс |
| Ранов на кадр | 50–500 (текст / цветной вывод) | — |
| `drawTextRun` | 50–500 вызовов | 0,4–2,5 мс |
| `drawRect` фона + курсор | 10–500 | 0,1–0,5 мс |
| **Итого полный кадр** | | **≈ 1–3 мс** |

Это укладывается в бюджет 16,6 мс, поэтому «в среднем» всё летает. Проблема проявляется там, где
полный кадр рисуется **каждый** vsync на фоне другой работы: `yes`, `cat` большого файла,
`npm install`, `tail -f`, а также на больших/ландшафтных экранах и со включённой прозрачностью
(дополнительный слой композитинга).

Отсюда единственная стратегия оптимизации: **делать полный кадр дешёвым**, потому что отменить
полный кадр на скролле в глифовой модели нельзя (вариант с блитом — см. §7, требует отдельного
спайка).

## 4. Находки и оптимизации

### A2. Быстрый путь строки (наибольший выигрыш при минимальном риске)

**Сейчас:** для каждой строки выполняется цикл по колонкам (`:348-398`), даже если строка —
сплошные пробелы дефолтным стилем (а на типовом шелле таких строк больше половины экрана, и
ровно они доминируют при скролле по истории).

**Предложение:** завести в `TerminalRow` два «липких» флага, поддерживаемых инкрементально:

```java
/** Стиль всех ячеек одинаков (до первого различия; сбрасывается в clear()). */
boolean mUniformStyle;      // + long mUniformStyleValue
/** В строке нет ни одного непробельного символа (липкий; сбрасывается в clear()). */
boolean mAllSpaces;
```

Оба — односторонние («липкие»): выставляются в `false` в `setChar()` и в `true` в `clear()`.
Это консервативно: ложное `false` стоит лишь чуть большего объёма работы, никогда — артефакта.
Поддержка стоит один `if` на `setChar`.

Тогда в `render()`:

```java
if (line.mAllSpaces && line.mUniformStyle && cursorX < 0 && !insideSelectionRange) {
    // цвет считается один раз на строку
    if (backColor == rawBgColor) continue;             // базовая заливка уже есть — ничего не рисуем
    mBgPaint.setColor(backColor);
    canvas.drawRect(0, top, columns * mFontWidth, bottom, mBgPaint);
    continue;                                          // ← вся строка за O(1)
}
```

Второй уровень того же пути — строка с однородным стилем и «простым» содержимым:
`!mHasNonOneWidthOrSurrogateChars` (флаг уже есть, но package-private → нужен публичный геттер,
рендер живёт в `com.termux.view`) плюс новый флаг «только ASCII» и однократно посчитанный в
конструкторе рендера `mAsciiMonospace` (все `bmpMeasures[0x20..0x7E]` равны `mFontWidth`).
В этом случае кодпоинт ↔ колонка взаимно однозначны, нет комбинирующих, нет расхождения ширины →
**строка превращается ровно в один ран и один `drawTextRun`**, а цикл по колонкам не нужен вообще.

Ожидаемый эффект: на экране шелла 40–70 % строк становятся O(1) вместо O(columns); на типовом
кадре — минус 40–60 % сканирования и минус заметная доля `drawTextRun`.

**Реализовано (без новых флагов).** «Липкие» флаги `mAllSpaces`/`mUniformStyle` требуют поддержки
в `setChar()` — а это самый горячий метод эмулятора, и цена `if` на каждый записанный символ
платится всегда, включая те кадры, где выигрыша нет. Вместо этого быстрый путь проверяет
`!hasNonOneWidthOrSurrogateChars()` (флаг уже поддерживается, добавлен публичный геттер — рендер
живёт в `com.termux.view`) и делает один линейный проход сразу по `mText[column]` и
`mStyle[column]`: если встречается непробел или другой стиль — строка отдаётся обычному пути.
Проход дешевле основного цикла ранов в разы (нет `WcWidth`, нет `measureCodePoint`, нет ветвлений
по курсору/выделению) и не требует никакого нового состояния.

Две ловушки, из-за которых быстрый путь нельзя делать безусловным:

1. **Подчёркивание и зачёркивание** — это текстовые декорации, `drawTextRun()` рисует их и поверх
   пробелов. Строка пробелов с атрибутом underline визуально не пустая, поэтому такой стиль
   отправляется в обычный путь (проверка `CHARACTER_ATTRIBUTE_UNDERLINE | STRIKETHROUGH`).
2. **Фон.** Пустая строка с нестандартным фоном всё равно должна быть закрашена — рисуется один
   `drawRect` на всю строку, с тем же SRC/SRC_OVER-выбором, что и в pass A.

### A3. Группировка ранов с «нестандартной» шириной (эмодзи, псевдографика)

**Сейчас:** условие разрыва рана (`:370`) включает `fontWidthMismatch || lastRunFontWidthMismatch`,
и комментарий прямо говорит: «ломаем на каждом несовпадающем кодпоинте, чтобы каждый глиф
масштабировался индивидуально, а не усреднялся». Следствие: строка из 100 эмодзи — это 100 ранов,
на каждый из которых приходится `canvas.save()` + `scale()` + `drawRect()` + `drawTextRun()` +
`canvas.restore()` (`:553-559`, `:575-585`, `:646`, `:649`). Экран `nerdfetch`/`broot`/`ls` в
каталоге с эмодзи — thousands of canvas-операций на кадр. Это самый тяжёлый реальный сценарий
после «просто много текста».

**Предложение:** ломать ран не на каждом несовпадающем символ накопление, а **при смене измеренной
ширины** (сравнение `Math.abs(w - runWidth) > epsilon`). Подряд идущие эмодзи почти всегда имеют
одинаковую измеренную ширину → весь их участок схлопывается в один ран с одним масштабом.
Ключевое свойство исходного решения **сохраняется**: внутри рана все глифы имеют одну и ту же
измеренную ширину, поэтому масштабирование по-прежнему точное — усреднения нет, обрезки нет.

```java
// вместо fontWidthMismatch || lastRunFontWidthMismatch
boolean widthChanged = fontWidthMismatch
        && Math.abs(measuredCodePointWidth - mRunMeasuredWidthOfLastCodePoint) > 0.01f;
```

Ожидаемый эффект: на эмодзи/боксах число ранов падает с O(число символов) до O(число различных
ширин), т.е. обычно до 1–2 на строку. Кратное снижение числа `save/scale/restore` и `drawTextRun`.

**Реализовано — сравнение коэффициентов, а не ширин.** Сравнивать сами измеренные ширины
(`|w − w_prev| > eps`) нельзя: глиф шириной 2 колонки и глиф шириной 1 колонка могут иметь близкие
абсолютные ширины при совершенно разном масштабе. Сравнивается **коэффициент**
`measuredWidth / (wcwidth · mFontWidth)`, и — важное решение — требуется его **точное (побитовое)
равенство float**, а не близость по эпсилоне.

Причина в том, как применяется масштаб: `drawTextRun` получает один `canvas.scale(...)` на весь
ран, вычисленный из суммарных величин, а позиции глифов внутри рана накапливаются. Если
коэффициенты различаются хотя бы на 0,5 %, ошибка накапливается вдоль рана и за 100 глифов
достигает заметной доли ячейки. При точном равенстве коэффициентов масштаб рана **в точности**
равен масштабу каждого глифа по отдельности — результат пиксельно идентичен старому
поведению «один ран на глиф». Всё, что не совпало точно, остаётся на старом пути.

Практически это покрывает как раз частые случаи: псевдографика, повторяющиеся эмодзи, брайль.
Цепочка из *разных* эмодзи с разными метриками по-прежнему даёт один ран на глиф — но она и
должна, иначе глифы поедут.

### A4. Переиспользование ранов между кадрами (сдвиг кэша при скролле)

Список ранов строки зависит от: содержимого строки, палитры, режима reverse-video, курсора,
выделения, метрик шрифта. **От `y` он не зависит.** А при скролле/fling содержимое строк не
меняется — меняется только позиция. Сейчас это игнорируется: каждый кадр всё пересчитывается.

**Предложение:** кэш ранов, индексированный **внешней строкой** (массив из `mRows` записей), с
валидацией по версии:

* `TerminalRow` получает `int mVersion`, инкрементируемый в `setChar`/`clear`;
* кэш хранит `rowIdentity + rowVersion` и результаты;
* **при скролле на k строк кэш сдвигается на k** (`System.arraycopy` по массиву из ~`mRows`
  ссылок — то же самое, что уже делает `blockCopyLinesDown`), и инвалидируются только k новых
  строк;
* дополнительные ключи валидации: версия палитры, `cursorRow` (инвалидация старой и новой строки
  курсора), состояние выделения, идентификатор рендера (шрифт/размер).

Для fling по истории это чистый выигрыш: **ни одна строка не пересчитывается**, платятся только
вызовы отрисовки. Для потока вывода — пересчитываются только новые строки.

Ожидаемый эффект: минус 30–50 % CPU кадра скролла/fling (всё сканирование, всё `measureText`,
всё `WcWidth`). Риск: средний — появляется состояние, которое надо аккуратно инвалидировать
(OSC-палитра, смена схемы, смена буфера, ресайз). Вводить после A2/A3 и под флагом.

### B1. `wideDisplayCharacterStartingAt` — квадратичность на CJK

`TerminalRow.setChar()`, медленная ветка, дважды вызывает `wideDisplayCharacterStartingAt()`
(`:203`, `:212`). Метод (`:159-171`) каждый раз сканирует строку с нуля — O(spaceUsed).
Для строки из 100 CJK-символов это 2 × O(100) на каждый `setChar`, т.е. **O(cols²) на строку**.
A1-memo помогает `findStartOfColumn`, но этот метод остался в стороне.

**Реализовано: возобновление сканирования с A1-memo.** Цикл остался циклом, но стартует не с нуля,
а с `(mCachedColumn, mCachedCharIndex)`, если запрашиваемая колонка не левее кэшированной:

```java
if (column >= mCachedColumn && mCachedColumn >= 0 && mCachedCharIndex >= 0 && mCachedCharIndex <= mSpaceUsed) {
    currentColumn = mCachedColumn;  currentCharIndex = mCachedCharIndex;
} else {
    currentColumn = 0;              currentCharIndex = 0;
}
while (currentCharIndex < mSpaceUsed) { /* тот же разбор, что и раньше */ }
```

**Что НЕ надо делать (проверено замером).** Естественная идея — выразить метод через уже
мемоизированный `findStartOfColumn`: «широкий символ — это когда колонка `c` и колонка `c + 1`
отображаются в один и тот же индекс», т.е. `findStartOfColumn(c) == findStartOfColumn(c + 1)`.
Логика верная, но замер показал **1615 мкс против 1344 мкс у оригинала — минус 20 %**.

Причина: запрос колонки, следующей за широким символом, попадает в ветку «inside a wide char»
(`TerminalRow.java:150`), которая **правильно** сбрасывает memo — пара `(column, index)` там не
является корректной «колонка → индекс её первого символа». Значит следующий же запрос
(а это `findStartOfColumn(columnToSet)` в том же `setChar`) сканирует строку с нуля, но уже
оплатив сверху два вызова с проверками и записью кэша. Асимптотика «O(1) амортизированно»
здесь не выполняется, потому что инвалидация кэша происходит ровно на том пути, который метод
использует.

**Замеры** (JVM, экран 200×50, лучший из 20 прогонов, временный бенч удалён после замера):

| Сценарий | Оригинал | Через `findStartOfColumn` | Возобновление с memo |
|---|---|---|---|
| Запись экрана 200×50 широким CJK | 1344 мкс | 1615 мкс | **1071 мкс** |
| 10 k смешанных записей (ASCII + 1-char wide + surrogate wide) | 26,5 мс | — | **21,9 мс** |

Корректность: 152 юнит-теста `terminal-emulator` (включая `TerminalRowTest` с
`testDoubleWidth*`, `testOverwritingDoubleDisplayWidth*`, `testFindStartOfColumnInsideWideChar`,
`testCrashATE145`, `testSurrogateCharsWithNormalDisplayWidth`) проходят.

### B2. Массовый путь для `resize()` / `blockCopy()` / `copyInterval()`

`resize()` (`:343-427`) при смене числа колонок пересобирает экран **посимвольно** через
`setChar` (`:404`). При лимите истории 2000 строк и 200 колонках это ~400 тыс. вызовов на поворот
экрана; при максимуме 50 000 строк (`TERMINAL_TRANSCRIPT_ROWS_MAX`) — до **10 млн**. То же самое
делают `blockCopy`→`copyInterval` при скролле региона (`:73-96`), плюс `copyInterval` при
`this == line` аллоцирует полную копию массива (`:78`).

**Предложение:** быстрый путь для случая «источник и приёмник не содержат широких/суррогатных/
комбинирующих символов» (проверяется существующим `mHasNonOneWidthOrSurrogateChars`):

```java
// текст: 1 char == 1 колонка → простое копирование
System.arraycopy(src.mText, srcX1, dst.mText, dstX1, len);
System.arraycopy(src.mStyle, srcX1, dst.mStyle, dstX1, len);
```

Для `resize()` добавить тот же путь на уровне строки: если старая строка «простая» и влезает
целиком — копировать массивы, а не переигрывать `setChar` по символу.

Эффект: поворот экрана / смена размера шрифта с большой историей — с сотен мс до десятков.

### C1. `clear()` заливает больше, чем нужно

`TerminalRow.clear()` делает `Arrays.fill(mText, ' ')` по **всей длине** массива, а она —
`1.5 × columns` и растёт на `columns` при каждом расширении (`:255`, `:279`). Читается только
`[0, mSpaceUsed)`. Вызывается на каждой строке вывода (новая строка внизу экрана).

```java
Arrays.fill(mText, 0, Math.max(mColumns, mSpaceUsed), ' ');   // вместо Arrays.fill(mText, ' ')
```

Экономия ~⅓ работы заливки на каждой строке скролла. Копеечная правка.

### C2. Прозрачность: два `Paint` вместо мутации xfermode

При `mBackgroundAlpha < 255` на каждый прямоугольник фона делается `setXfermode(SRC)` и
`setXfermode(null)` (`:455-459`, `:580-584`, `:601-605`) — два нативных вызова на закрашенную
ячейку. Достаточно завести два заранее настроенных `Paint`:

```java
private final Paint mBgPaintSrcOver = new Paint(Paint.Style.FILL);
private final Paint mBgPaintSrc;   // с xfermode SRC, выставленным один раз в конструкторе
```

и выбирать нужный по `mBackgroundAlpha`, не трогая xfermode в цикле.

**Сделано.** Добавлен `mBgSrcPaint` (SRC выставлен один раз в конструкторе); все четыре точки
заливки — базовая `drawRect` при частичной перерисовке, pass A, фон масштабированного рана,
курсор — выбирают `mBgPaint` или `mBgSrcPaint`. Семантика не меняется: как и раньше, SRC
применяется только при `mBackgroundAlpha < 255` и только к цвету с подставленной альфой.
Отдельно это мелкая правка, но она убирает два нативных вызова на каждый закрашенный
прямоугольник, а их на кадре — сотни.

### C3. Полоса инвалидации во всю ширину

`invalidateRowRange()` (`:1046`) инвалидирует `(0, top, getWidth(), bottom)`. Полоса включает
зону скроллбара, поэтому `drawScrollbar()` обязан вызываться на каждом частичном кадре (`:2511`,
там же комментарий). Можно сузить полосу до правой границы глифовой сетки, когда скроллбар не
активен (`getScrollbarRange() == 0`), — тогда частичный кадр вообще не трогает скроллбар.

### D1. `getWordAtLocation()` — квадратичный поиск границ завёрнутой строки

`:174-181` ищет начало и конец завёрнутой строки, вызывая `getSelectedText()` в цикле: каждый вызов
материализует всю строку в `StringBuilder`. Стоимость — O(длина²). Сейчас метод вызывается только
из `ScreenBufferTest`, но он публичный и представляет собой мину, если дойдёт до UI (двойной тап).
Правильная реализация — идти по `getLineWrap(row)` вверх/вниз без материализации текста.

## 5. Мелкие наблюдения без практического эффекта (для полноты)

* `addRun()` вызывает `ensureRunCapacity()` на каждый ран — это два сравнения, пренебрежимо.
* `mScrollRemainder` используется как общий аккумулятор drag/колеса — сделано верно, перенос
  остатка между жестами (`captureFlingRemainder`) убирает «залипание» на строку.
* `awakenScrollBars()` в `onScreenUpdated` (`:905`) — системные скроллбары отключены
  (`:694`), вызов — мёртвый код; удалить или не трогать.
* `mStyle` — `long[columns]` (8 байт на ячейку) из-за 24-битных цветов. На истории 2000×200 это
  ~3,2 МБ только стилей; на 50 000 строк — 80 МБ. Переход на `int[]` с side-table для
  truecolor-ячеек дал бы 2×, но это отдельный рефакторинг с широким радиусом поражения.

## 7. Что НЕ предлагается (и почему)

* **Субглифовый сдвиг.** Запрещён моделью рендера, ломает dirty-rect и резкость глифов —
  обосновано в `android-like-terminal-scrolling.md` §9.
* **Blit-скролл (сдвиг предыдущего кадра битмапом).** Единственный способ *отменить* полный кадр
  на скролле, но требует либо рендера в software-bitmap (потеря HWUI-текста), либо двухслойной
  схемы с hardware layer и `setTranslationY` — что прямо конфликтует с инвариантом
  «инвалидация и отрисовка считают одну `y`» (`TerminalView.java:1000-1013`). Возможный спайк,
  но начинать не с него: сначала надо измерить, какая доля кадра — сканирование, а какая —
  `drawTextRun`. Если после A2/A3/A4 кадр укладывается в 1–2 мс, blit не окупит сложности.
* **Своя физика скролла вместо `OverScroller`.** Уже системная, трогать не надо.
