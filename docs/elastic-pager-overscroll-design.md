# Проектирование упругого пере-перетаскивания пейджера терминалов

**Цель:** на крайней странице пейджера сессий горизонтальный драг за границу должен не
«упираться в стену», а оттягивать экран терминала за край с нарастающим сопротивлением и
пружинить обратно при отпускании.

**Область:** `app/src/main/java/com/termux/app/terminal/PagerOverscrollController.java` (новый),
`SessionPagerManager`, внутренний `RecyclerView` пейджера `ViewPager2`.

**Окружение:** `viewpager2 1.1.0`, разрешённый `recyclerview 1.3.1`, `minSdk 21`, `compileSdk 34`,
`targetSdk 28`. Все утверждения о поведении `RecyclerView` ниже проверены по байткоду
`recyclerview-1.3.1` (`javap -c`), а не по памяти.

---

## 0. Постановка задачи и наблюдаемое поведение

Сейчас на первой/последней странице горизонтальный драг полностью мёртв:
`LinearLayoutManager.scrollHorizontallyBy()` возвращает `0`, `RecyclerView` ничего не
прокручивает, страница стоит на месте. Нужно, чтобы она **смещалась** за палец и возвращалась.

Отдельно: страница должна смещаться **целиком**, открывая фон (обои) за ней — это и есть
«оттянуть экран от границы».

---

## 1. Варианты, которые отпали

| Вариант | Почему не годится |
|---|---|
| **A. Прокрутить сам `RecyclerView` за границы** | Нельзя: `RecyclerView` физически не может выйти за пределы контента. Это не `ScrollView` с `overScrollBy()`, смещение всегда в `[0, range]`. |
| **B. Перехват тача (`OnItemTouchListener` или контейнер вокруг пейджера)** | Работает, но ценой дублирования `mTouchSlop`, axis-lock и конечного автомата `DRAGGING`. Возвращая `true` из `onInterceptTouchEvent`, мы заставляем `RecyclerView` сделать `cancelTouch()` — пейджер выпадает из `SCROLL_STATE_DRAGGING`, и вся существующая логика (IME-гвард `setTerminalPageSwitchInProgress`, `mUserScrollInProgress`, скролл таб-стрипа) перестаёт вызываться на границе. Слишком много скрытых связей. |
| **C. `ViewPager2.PageTransformer`** | Вызывается только из `onScrolled`. На границе `onScrolled` не приходит вообще — трансформеру нечем управлять. |
| **D. Включить системный `OVER_SCROLL_ALWAYS` и отдать stretch платформе (Android 12+)** | Stretch растягивает **весь** `RecyclerView` (масштаб + сдвиг), а не отодвигает страницу от края; на API < 31 вместо него будет старый glow. Плюс он уже отключён сознательно: растяжение добавляет второй композитный проход поверх полупрозрачного терминала (см. комментарий, который был в `setup()`). |
| **E. `EdgeEffectFactory`-шпион (выбран)** | `RecyclerView` **уже** считает «пиксели драга за границу» — см. §2. Остаётся только перехватить этот канал. Никакого своего тач-парсинга, пейджер остаётся владельцем жеста. |

## 2. Как `RecyclerView` уже считает пере-перетаскивание

`RecyclerView` не выбрасывает невостребованный драг — он скармливает его `EdgeEffect`.
Цепочка (проверено по байткоду 1.3.1):

```
onTouchEvent(MOVE)
  → scrollByInternal(dx, dy, ev, TYPE_TOUCH)
      → mLayout.scrollHorizontallyBy(dx, …)      // consumedX — реально прокручено
      → unconsumedX = dx - consumedX             // ← это и есть «drag за границу»
      → if (getOverScrollMode() != OVER_SCROLL_NEVER && ev != null && !isFromSource(ev, MOUSE))
            pullGlows(x, unconsumedX, y, unconsumedY)
              → ensureLeftGlow() / ensureRightGlow()          // mEdgeEffectFactory.createEdgeEffect(...)
              → EdgeEffectCompat.onPullDistance(glow, |unconsumedX| / getWidth(), displacement)
```

Значит:

1. **Дельты приходят в пикселях**, нормализованных на ширину: `deltaPx = deltaDistance * width`.
   Мышам/стилусу этот путь недоступен (`SOURCE_MOUSE` отсекается) — для тача работает всегда.
2. **`OVER_SCROLL_NEVER` полностью вырубает канал** — именно поэтому старая строка
   `pagerRv.setOverScrollMode(OVER_SCROLL_NEVER)` обязательна к удалению: она отключала не только
   stretch, но и вообще всю доставку события.
3. Знак: `unconsumedX < 0` → левый край (палец тянет вправо, контент должен уехать **вправо**),
   `unconsumedX > 0` → правый край (контент уезжает **влево**). Оба края получают
   **положительный** `deltaDistance` при нарастании оттяжки — направление живёт в том,
   какой именно `EdgeEffect` вызвали.

Обратный путь (отпускание и флинг) тоже уже есть:

```
resetTouch() → releaseGlows()        → glow.onRelease()      // палец подняли
ViewFlinger.run():
   consumeFlingInHorizontalStretch(dx)                       // stretch-путь, отключён нулевой distance
   … если флинг ничего не прокрутил:
   absorbGlows(velocityX, velocityY) → shouldAbsorb(…) → glow.onAbsorb(|velocity|)
```

Из `absorbGlows()` важно одно: **`onAbsorb()` вызывается только если `glow.isFinished()` вернул
`true`**. Поэтому шпион обязан всегда отвечать `isFinished() = true`, иначе флинг в стенку
молча теряется.

## 3. Что такое «шпион» и почему он ещё и лечит старый баг

`SpyEdgeEffect` — это `EdgeEffect`, который:

* **никогда не вызывает `super.onPull()`** → внутренняя `mDistance` всегда `0`;
* `getDistance()` → `0`, `draw()` → `false`, `isFinished()` → `true`;
* все входящие дельты отдаёт контроллеру.

Побочный эффект: **штатная анимация края выключена навсегда и по-настоящему**, а не «выключателем
сверху». Все stretch-пути (`releaseHorizontalGlow`, `consumeFlingInStretch`, `shouldAbsorb`)
принимают решение по `EdgeEffectCompat.getDistance()` — он равен нулю, значит:

* нет растяжения на Android 12+ → **нет второго композитного прохода** → прозрачность терминала
  больше не «усыхает вдвое» на время анимации (ровно то, ради чего ставился `OVER_SCROLL_NEVER`);
* нет glow на старых API;
* `consumeFlingInStretch()` возвращает флинг нетронутым, поэтому `absorbGlows()` доезжает до нас.

То есть упругое смещение **заменяет** stretch, а не наслаивается на него.

## 4. Куда применять смещение

`translationX` **внутреннего `RecyclerView`** (не страницы, не `ViewPager2`):

* пейджер полноэкранный и клипует детей → страница уезжает за край, а полоса, которую она
  освободила, показывает фон активности/обои. Это ровно тот «отъезд» который нужен;
* одна анимируемая величина, не надо искать `ViewHolder` и следить за ресайклингом;
* `PagerSnapHelper`, `onPageScrolled`, `getCurrentItem()` живут в координатах скролла и **не
  видят** `translationX` — конфликтовать нечему;
* тач-тестирование учитывает трансформацию, поэтому обратной связи «смещение → новые координаты
  → ещё смещение» не возникает.

## 5. Кривая сопротивления

> Физика вынесена в **`ElasticOverdrag`** (`terminal-view`) и **общая с вертикальным скроллом
> терминала** (см. `elastic-terminal-overdrag-design.md` §4). Здесь только адаптер: он решает,
> куда девать смещение (`translationX` внутреннего RecyclerView), но не как оно считается.

От константы в dp отказались — всё считается от **ширины страницы** `W`:

```
M = 0.2 · W        предел оттягивания («20 % длины списка»)
L ≈ 2.244 · W      проход пальца, который этот предел достигает — вычислен, не выбран
```

```
f(x) = M · sin( (π/2) · x / L ),   0 ≤ x ≤ L,   далее M
f⁻¹(y) = (2L/π) · asin(y / M)      — нужна в §6
```

`L` выводится, а не назначается: `L = π·M / (2·BOUNDARY_SLOPE)` при `BOUNDARY_SLOPE = 0.14`
(втрое жёстче прежних 0.42; у iOS для того же 0.55; см. `elastic-terminal-overdrag-design.md`
§4.1). Два числа независимо не крутятся — иначе предел и отклик у границы расходятся, и
страница начинает отставать от пальца на две трети хода.

* `f(0) = 0`;
* `f'(0) = π·M/(2L) = 0.14` — у самой границы страница идёт за пальцем на 14 %, то есть
  резинка сопротивляется очень жёстко с первого пикселя; `f''(0) = 0` — старт жеста
  **точно линейный**, никакой ваты в первом миллиметре;
* `f(L) = M` и `f'(L) = 0` — предел **достигается** (в отличие от асимптоты гиперболы, у
  которой «максимум 20 % ширины» на практике означал бы «максимум ~12 %»), а поскольку
  в точке предела кривая уже горизонтальна, выхода на полку не видно: это не «стена», а
  естественное загрубение резинки.

Таблица в долях ширины (для страницы 1080 px — в скобках px):

| драг `x` | 3 % | 7.5 % | 15 % | 30 % | 50 % | 224 % = `L` |
|---|---|---|---|---|---|---|
| смещение `f(x)` | 0.4 % (5) | 1.0 % (11) | 2.1 % (22) | 4.1 % (45) | 6.8 % (74) | **20 % = M** (216) |

Типичный жест «потянул сантиметр» (~30 % ширины на телефоне это как раз ~1 см) даёт ~4 %
ширины видимого отъезда — за страницей видно обои, но тройное сопротивление требует вести
палец почти вдвое с лишним длиннее экрана, чтобы выбрать весь предел.

Побочный выигрыш: `W` **читается на каждый вызов**, а не кешируется от плотности в
конструкторе, поэтому поворот или split-screen сами перенастраивают физику.

## 6. Возврат перетаскивания (bleed) — самая неочевидная часть

`RecyclerView` ничего не знает про наше смещение. Поэтому стоит пальцу пойти **обратно**, он
сразу начинает честно скроллить — и страница поедет и скроллом, и остаточной оттяжкой одновременно
(вдвое быстрее пальца).

Лечение — `OnScrollListener.onScrolled(rv, dx, …)`: каждый потребленный пиксель скролла гасит
один пиксель оттяжки. **Знак `dx` не используется — только модуль:**

```
|t| = |translation| − |dx|;  t = sign(translation) · max(0, |t|)
translation = t;  raw = f⁻¹(|t|)
```

Так «потянул и вернул» и «потянул и флингнул внутрь» читаются как одно непрерывное движение:
энергия оттяжки перетекает в перелистывание.

> **Почему нельзя `translation − dx` (со знаком).** Это выглядит правильнее, но это была
> настоящая поломка. Кривая пружины (§7) перелетает границу: на интервале `t ≈ 0.17…0.5`
> интерполятор даёт долю > 1, то есть смещение **меняет знак** относительно породившей его
> оттяжки (`+56 → … → −8 → 0`). Если в этот момент начать реальный скролл, вычитание `dx`
> работало **в обратную сторону**: на каждом кадре `onScrolled` смещение уходило всё дальше, и один свайп
> к соседнему терминалу складывал в него всю ширину страницы (1000+ px). RecyclerView
> уезжал за пределы экрана, все страницы рисовались вне вьюпорта — **вывод терминалов
> пропадал полностью для всех сессий, лечилось только перезапуском приложения**
> (смещение жило в поле контроллера). «Только уменьшение по модулю» делает величину
> монотонно убывающей: bleed может только втягивать страницу, никогда не выталкивать.
>
> Второй уровень защиты — жёсткий кламп в `setTranslation()`: `|translation| ≤ MAX_PULL`.
> Смещение — временная аффектация, а не накапливаемое состояние; всё, что пишет его, идёт
> через один метод, так что один кламп закрывает все будущие пути.

**Особый случай — одна страница.** Тогда скроллиться некуда: возврат к границе приходит как
`unconsumedX` **противоположного** знака, то есть как оттяжка **другого** края. Поэтому в
`onEdgePull()` новая дельта сначала гасит накопленное другой стороной, и только остаток
накапливается на своей:

```
returned = min(otherRaw, delta);  otherRaw -= returned;  myRaw += delta - returned;
```

Это даёт непрерывность позиции при пересечении границы: `+30 → 0 → −10` в «сырых» пикселях
даёт `+14.7 → 0 → −7.4` в смещении, без скачка.

## 7. Отпускание и флинг в стенку

**Отпускание.** `onRelease()` → пружина из текущего смещения в `0` на `ValueAnimator`.
Интерполятор — `ElasticOverdrag.SPRING`, замкнутая форма **критически задемпфированного**
осциллятора (вторая производная, настоящая пружина, а не безье-кривая). Буквально тот же
объект, что у вертикального скролла терминала:

```
y(t) = (1 + ωt)·e^(−ωt)          переходная характеристика при ζ = 1
Y(t) = y(t) − y(1)·t             … с вычтенным остатком
value(t) = from · Y(t),    ω = 8.5,  длительность 140 ms
```

| момент | t | доля от `from` |
|---|---|---|
| старт | 0 | 100 % |
| пик скорости | ~0.12 (16 мс) | 74 % (= `2/e`, для ζ = 1 это константа) |
| 92 % пути | ~0.49 (69 мс) | ~8 % |
| 98 % пути | ~0.68 (95 мс) | ~2 % |
| конец анимации | 140 мс | **ровно 0** |

**Колебаний нет вовсе.** `Y'(t) = −ω²t·e^(−ωt) − y(1)` — оба слагаемых отрицательны на всём
`[0,1]`, то есть движение **монотонно** и границу не пересекает: ни одного перелёта, ни одного
второго качка. Прежний `ζ = 0.65` перелетал на 6.8 % амплитуды; при старом пределе 56 dp это
было ~4 px, а с новым пределом в 20 % страницы (216 px) стало бы уже ~15 px вздрагивания за
границу — плюс именно этот перелёт был причиной бага из §9.1 (смещение меняло знак, и bleed
начинал работать в обратную сторону).

Возврат при этом остаётся **упругим**: отпущенная из покоя страница сначала **разгоняется**
к границе и только потом осаживается — в отличие от ease-out, который быстрее всего в первом
кадре и потому читается как «уехала», а не «вернулась». Вычитание остатка `y(1)·t` убирает
последний щелчок: без него к `t=1` оставалось бы ~0.2 % (0.4 px на пределе в 216 px), которые
аниматору пришлось бы покрыть одним кадром.

Реализовано на `ValueAnimator`, **без новой зависимости** —
`androidx.dynamicanimation:SpringAnimation` дал бы ту же физику «из коробки», но тянет
за собой артефакт ради одного жеста.

**Флинг в стенку.** `onAbsorb(|velocity|)`: скорость переводится в отскок тем же
`ElasticOverdrag.impact()`, что и в терминале. Флинг — это не палец: он приходит **со
скоростью**, и резинка должна её погасить, поэтому здесь работает динамика, а не кривая хода
пальца (§5). Две вещи, которые в предыдущей версии модели были неверны:

* **Скорость входа — скорость импульса.** `ẏ(0) = v`: контент въезжает за границу на той же
  скорости, на которой до неё доехал. Флинг вдвое быстрее — вылет вдвое быстрее. Раньше
  импульс прогонялся через кривую хода пальца и входил со скоростью `BOUNDARY_SLOPE·v`
  (14 % от скорости удара) — ровно отсюда и получилась «анимация, ставшая втрое медленнее»
  после утроения сопротивления.
* **Дальность — дело жёсткости.** `y_peak = v/ω`: утроение сопротивления утроило жёсткость,
  поэтому вылет стал **втрое короче** (а не таким же длинным, как прежде) и втрое быстрее.
  В предыдущей версии амплитуда была привязана к доле предела, поэтому утроение
  сопротивления не меняло расстояние вовсе, а растягивало только время.

Резинка — маятник в пространстве смещения: `U(y) = A·(1 − cos κy)`, `κ = π/(2M)`,
`A = (ω/κ)²`, а точка разворота — в замкнутой форме: `y_peak = acos(1 − (v·κ/ω)²/2)/κ`,
обрезанная по `M`. На странице 1080 px (предел 216 px, `ω ≈ 60.7 рад/с`): флинг
2000 px/с ≈ 33 px смещения, 6000 px/с (предохранитель) ≈ 99 px. Сильный флинг визуально
«бьёт» страницу в ограничитель, а не растворяется в никуда; слабый — даёт пропорционально
мало, непрерывно от нуля. Подробный вывод — `elastic-terminal-overdrag-design.md` §7.2.

**Вылет играется во времени, а не телепортируется.** Раньше `onAbsorb` записывал вершину в
один кадр и анимировал только возврат — вылет читался мгновенным и не имел отношения к
скорости удара. Сейчас `onAbsorb` → `ElasticOverdrag.impact(v, …)` → `startImpact()`: маятник
интегрируется симплектическим Эйлером по 1 мс (`ω·dt ≈ 0.06`), последний сэмпл пришпиливается
к аналитической `y_peak`, а сэмплы проигрываются на `ValueAnimator` с **линейным**
интерполятором. Интегратор владеет *временем*, алгебра — *дальностью*. Длительность — четверть
периода маятника, `(π/2)/ω ≈ 26 мс`; в предыдущей версии модели на тот же вылет уходило
~460 мс, потому что счёт шёл в пространстве хода пальца, где эффективная жёсткость `∝ 1/L²`,
а `L` при утроении сопротивления утроился. По завершении `travelAt(1) = peak` передаётся в ту
же пружину возврата `ElasticOverdrag.SPRING`. Та же физика, что у терминала (см.
`elastic-terminal-overdrag-design.md` §7.5).

Прерывание пружины новым тачем: перед `cancel()` снимаются все слушатели (иначе `cancel()` сам
дозовёт `onAnimationEnd` и телепортирует страницу на границу), накопители пересидируются из
текущего смещения через `f⁻¹`.

## 8. Точки интеграции

```
SessionPagerManager.setup()
  └─ было:  pagerRv.setOverScrollMode(View.OVER_SCROLL_NEVER)     // удалено, см. §2.2
     стало: mOverscroll = PagerOverscrollController.install(mTerminalPager)

SessionPagerManager.destroy()
  └─ mOverscroll.destroy()      // снять пружину, чтобы она не пережила активность

PagerOverscrollController.<init>
  ├─ setOverScrollMode(OVER_SCROLL_ALWAYS)   // вернуть канал pullGlows/absorbGlows
  ├─ setEdgeEffectFactory(SpyFactory)        // шпион
  └─ addOnScrollListener(bleed)              // §6
```

`ViewPager2` не прокидывает `setOverScrollMode()` внутрь (проверено: в байткоде `ViewPager2`
нет ни одного вызова), поэтому переключать режим надо именно на внутреннем `RecyclerView` —
он достаётся как `mTerminalPager.getChildAt(0)` (уже используется в `getPagerRecyclerView()`).

## 9. Граничные случаи

* **Плейсхолдер «новая вкладка».** Это настоящая страница, поэтому справа от последней вкладки
  границы нет — драг честно листает на плейсхолдер, упругость не включается. Оттягивать можно
  уже с самого плейсхолдера (справа дальше некуда) — работает автоматически.
* **Одна сессия.** `updatePagerUserInputEnabled()` делает `setUserInputEnabled(count >= 2)`, так
  что с одной вкладкой драг не принимается вообще и упругости не будет. Если нужно и для одной —
  достаточно порога `>= 1`: раньше это включало бы системный stretch, но теперь он подавлен
  шпионом (§3). Не меняю автоматически: рядом живёт логика временного `setUserInputEnabled(false)`
  при коммите плейсхолдера (`SessionPagerManager`, ~строки 840–876).
* **Вертикальный скролл терминала.** `TerminalView.onScroll()` для вертикальной оси делает
  `requestDisallowInterceptTouchEvent(true)` — пейджер жеста не видит, упругости нет. Так и надо.
* **Мышь/стилус.** `pullGlows()` отсекает `SOURCE_MOUSE`, упругость только для тача.
* **Поворот/смена конфигурации.** Смещение живёт в `translationX` и не переживёт recreate —
  при `destroy()` пружина снимается, состояние не протекает.
* **Прозрачность/обои.** Никакой новый composite-проход не добавляется: `translationX` — это
  трансформация `RenderNode`, уже используемая системой, в отличие от stretch.

## 9.1 Отказ: «вывод всех сессий пропал, пейджер не листается, лечится только перезапуском»

**Симптом.** Оттянуть крайний экран → отпустить → **пока идёт пружина** быстро листнуть на
соседний терминал. После этого вывод терминалов пропадает сразу у всех сессий, пейджер
перестаёт реагировать на горизонтальный драг, вернуть можно только перезапуском приложения.

**Почему симптом именно такой.** Смещение пишется в `translationX` внутреннего RecyclerView
пейджера — а это **одна**view, в которой лежат **все** страницы. Значит любое «плохое» значение
смещения накрывает все сессии разом, и переживает смену вкладок (оно не часть состояния страницы).
Плохое значение здесь = не число (`Infinity`/`NaN`):

* `NaN` в `RenderNode`-трансформации → поддерево вообще не рисуется → **вывод пропал у всех**;
* `ViewGroup` при hit-testing инвертирует матрицу потомка; у матрицы с `NaN` обратной нет →
  координаты тача, переданные RecyclerView, становятся `NaN` → вся арифметика драга (`dx`,
  `scrollByInternal`) даёт `NaN` → **горизонтальное листание умирает**;
* сбросить это уже нечем: смещение — это не скролл, его никто больше не пересчитывает.

**Откуда взялось не число.** Две дыры, обе на пути «очень большое → бесконечность → NaN»:

1. `damp(x) = (C·M·x) / (C·x + M)`. При `x = +Infinity` это `Inf/Inf = NaN`; при просто огромном
   `x` числитель переполняется до `Infinity` первым — итог тот же.
2. В `Infinity` его превращали:
   * денормализация в шпионе — `deltaDistance * Math.max(1, getWidth())`. Фреймворк уже поделил
     на `getWidth()`; при нулевой ширине его собственное деление даёт `±Infinity`, а
     `Math.max(1, 0)` заменяет делитель на 1 и бесконечность доезжает до `damp()`;
   * неограниченный аккумулятор «сырого» хода пальца. `inverseDamp()` делит на `(MAX − damped)`,
     и у асимптоты отдаёт ~3·10⁵; аккумулятор никогда не сбрасывался вниз, так что при
     переполнении `float` получался `Infinity`.
3. А закреплял отказ `cancelSpring()`: он снимает слушателей **до** `cancel()` (иначе страница
   прыгает в границу посреди жеста), но именно `onAnimationEnd` был единственным местом, которое
   гарантированно пишет честный 0. Прерывание пружины — ровно то, что делает пользователь,
   листая соседнюю вкладку, — оставляло на view то значение, которое успела насчитать арифметика.

**Что сделано.** Три инварианта, которые выполняются на каждом входе, а не предполагаются:

| Инвариант | Реализация |
|---|---|
| Только конечные значения | `isFinite()` на входе в `onEdgePull`/`startSpring`; `setTranslation()` — единственная точка записи `translationX`, всё нечисловое превращает в 0 |
| Ограниченность | аккумулятор режется `clampRaw()` по `L` (= 0.571 ширины страницы); `damp()` никогда не превышает `M = 0.2·W` (`|sin| ≤ 1` и аргумент обрезан по `L`); `inverseDamp()` — замкнутая форма `asin`, её аргумент обрезан по 1, поэтому к полке не подойти бесконечно близко; скорость флинга — `Math.min(v, 6000)` |
| Никогда не сдвинут в покое | `ensureSettled()` на каждом `SCROLL_STATE_IDLE`: **отложенный** (post) сброс остатка, если пружины нет. Отложенный — потому что RecyclerView уходит в IDLE внутри `ACTION_UP` **до** `resetTouch() → releaseGlows()`, и синхронный сброс убивал бы пружину раньше, чем она стартует |

Дополнительно:

* шпион выходит при `getWidth() <= 0` — нечего денормализовывать, нечего и применять;
* `onAbsorb` теперь получает **направление края** (`mDirection`). Раньше сторона угадывалась по
  знаку текущего смещения, а оно в этот момент равно 0 и угадывалось всегда «влево» — то есть
  флинг в **последнюю** страницу отбрасывал экран не в ту сторону;
* `addOnAttachStateChangeListener` → `reset()` при отсоединении view от окна (пружина не должна
  писать в отсоединённый `RenderNode`);
* `destroy()` теперь снимает все слушатели, возвращает дефолтную `EdgeEffectFactory` и снова
  ставит `OVER_SCROLL_NEVER` — пейджер после себя оставляет точно таким, как до установки.

Худший исход при любой будущей ошибке в арифметике — **отсутствие анимации**, а не сломанный
пейджер: инвариант «в покое смещение всегда 0» гарантирует это независимо от причины.

## 10. Параметры

Всё, кроме предохранителя скорости, живёт в **`ElasticOverdrag`** и **общее с вертикальным
скроллом терминала**; в контроллере осталась только одна своя константа:

| Константа | Значение | Смысл |
|---|---|---|
| `MAX_FRACTION` | `0.2` | предел отъезда от ширины страницы — **собственно требование** |
| `BOUNDARY_SLOPE` | `0.14` | наклон у границы — единственная величина по вкусу; втрое жёстче прежних 0.42 (у iOS 0.55) |
| `SATURATION_FRACTION` | `≈ 2.244` | проход пальца, достигающий предела; вычислен как `MAX_FRACTION · π/(2·BOUNDARY_SLOPE)` |
| `INITIAL_SLOPE` | `0.14` | наклон в нуле; производное от двух предыдущих |
| `SPRING_DURATION_MS` | `140` | длительность возврата: втрое быстрее прежних 420 мс — резинка втрое жёстче, поэтому и разжимается втрое быстрее |
| `SPRING_OMEGA` | `8.5` | нормированная ω критически задемпфированного возврата (ζ = 1, перелёта нет вовсе); физическая `ω = SPRING_OMEGA·1000/SPRING_DURATION_MS ≈ 60.7 рад/с` — та же, на которой резинка останавливает флинг |
| `MAX_ABSORB_VELOCITY` | `6000` px/s | предохранитель скорости флинга (локальная константа) |

## 11. Чек-лист ручной проверки

1. 2+ вкладки, крайняя слева: тянуть вправо → экран уезжает вправо, открывая фон; сопротивление
   нарастает; отпустить → возврат с одним отскоком.
2. То же зеркально на последней вкладке.
3. Тянуть влево с первой вкладки → обычное листание, упругости нет (не должно).
4. Потянуть за границу и вернуть палец обратно, не отпуская → смещение плавно сходит в ноль и
   начинается нормальное листание, без рывка и двойной скорости.
5. Потянуть за границу и отпустить с быстрым флингом наружу → заметный «удар» в ограничитель.
6. Потянуть и флингнуть внутрь → оттяжка перетекает в перелистывание.
7. Вертикальный скролл истории на крайней вкладке → упругость пейджера не срабатывает.
8. Включить прозрачность фона/обои, повторить п.1 → прозрачность терминала не «усыхает» на время
   анимации (регресс, ради которого ставился `OVER_SCROLL_NEVER`).
9. Плейсхолдер «новая вкладка»: драг на него — обычное листание; с него дальше вправо — упругость.
10. Перейти в другую вкладку тапом во время пружины → никакого «залипания» смещения.
11. `adb shell am kill` / поворот экрана во время оттяжки → страница не остаётся сдвинутой.
