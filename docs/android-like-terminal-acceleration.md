# Ускорение прокрутки и суммирование импульсов: приведение терминала к модели AOSP

**Проект:** `D:\projects\termux-enhanced`
**База:** `docs/android-like-terminal-scrolling.md` (перевод оси fling в пиксели — уже сделан)
**Предыдущая точка:** коммит `0fab152e` + незакоммиченные правки px-оси fling.
**Вопрос:** как в системе устроено *ускорение* fling и *суммирование импульсов*, и почему в терминале
оно отличается.

### 1.1. Ключевой факт, который всё меняет

`VelocityTracker` использует **разные стратегии для разных осей**
(`DEFAULT_STRATEGY_BY_AXIS` в `VelocityTracker.cpp`):

```cpp
static const std::map<int32_t, VelocityTracker::Strategy> DEFAULT_STRATEGY_BY_AXIS =
        {{AMOTION_EVENT_AXIS_X,      VelocityTracker::Strategy::LSQ2},
         {AMOTION_EVENT_AXIS_Y,      VelocityTracker::Strategy::LSQ2},
         {AMOTION_EVENT_AXIS_SCROLL, VelocityTracker::Strategy::IMPULSE}};
```

- **Плоские оси (X/Y, палец)** → `LSQ2`. Здесь «накопление» = подгонка полинома по окну 100 мс.
  Никакого суммирования импульсов.
- **Дифференциальные оси (`AXIS_SCROLL`, колесо и precision-тачпад)** → `IMPULSE`. Вот где
  живёт буквальное *суммирование импульсов*.

То есть «как в системе» — это **две разные механики**, и путать их нельзя. В терминале первая
уже получена бесплатно от `GestureDetector`, вторая отсутствовала полностью.

## 2. Почему системе не нужно суммировать остаточный импульс

Распространённое заблуждение: «в системном списке повторный свайп по летящему тексту ускоряет
его, значит списки суммируют скорости». Они не суммируют — они **измеряют**.

`VelocityTracker` считает производную **абсолютной** позиции пальца в координатах экрана. Когда вы
ловите летящий список, ваш палец в момент касания уже движется вместе с контентом (иначе вы бы
промахнулись). Дальше:

- палец движется **с той же скоростью, что контент** → `v_изм = v_контента` → fling продолжает
  движение без рывка, текст «прилипает» к пальцу;
- палец движется **быстрее** → `v_изм > v_контента` → ускорение;
- палец движется **медленнее / навстречу** → торможение.

Всё это получается из одного числа — измеренной скорости пальца. Никакого состояния между
жестами не нужно, и AOSP его не хранит: на `ACTION_DOWN` список делает `abortAnimation()`, а
`GestureDetector` очищает `VelocityTracker`.

**Следствие для терминала.** Наша механика `captureCurrentFlingVelocity` + экспоненциальный распад
(`FLING_CAPTURE_TAU_MS = 150`) + `combineFlingVelocity` (`FLING_RESIDUAL_FACTOR = 0.6`) добавляла к
уже измеренной скорости пальца **ещё и скорость scroller'а**. Это *двойной учёт* одного и того же
движения: контент едет, палец едет вместе с ним, и оба вклада складываются. Результат — повторный
свайп систематически **перелетает** относительно любого системного списка.

### 2.1. Побочный баг: знак захваченной скорости

`OverScroller.getCurrVelocity()` возвращает **норму** скоростей по осям
(`hypot(vx, vy)`), то есть всегда `≥ 0`. Старый код делал:

```java
float scrollerVelocity = mScroller.getCurrVelocity();   // >= 0, знак потерян
mCapturedFlingVelocityY = -scrollerVelocity;            // всегда одного знака
```

Знак остаточной скорости был **всегда одним и тем же**, независимо от того, куда летел fling.
Практический эффект: повторный свайп **ускорялся только в одну сторону** и **гасился** в другую
(вместо ускорения получалось вычитание). Теперь знак берётся из `mFlingRawVelocity` — скорости,
с которой fling запускался.

## 3. AOSP IMPULSE: точный алгоритм

Из `frameworks/native/libs/input/VelocityTracker.cpp`.

Модель: сенсорная поверхность — физическое тело, палец совершает работу.

```
E   = 1/2 · m · v²
dW  = F · dx = m · (dv/dt) · dx = m · v · dv
W   = m · Σ ( v · dv )          →   v = sign(W) · sqrt(2 · |W|)
```

Псевдокод (для дифференциальной оси, `deltaValues = true`; массивы — **в обратном времени**,
индекс 0 = самый новый сэмпл):

```java
float calculateImpulseVelocity(long[] t, float[] x, int count) {
    if (count < 2) return 0;
    if (count == 2) {
        // x[0] — дельта самого нового события; (t[1]-t[0]) < 0, знаки сокращаются
        return -x[0] / (1e-9f * (t[1] - t[0]));
    }
    float work = 0;
    for (int i = count - 1; i > 0; i--) {          // от старейшей пары вперёд по времени
        if (t[i] == t[i - 1]) continue;
        float vprev = ke2v(work);                  // скорость в более старой точке
        float vcurr = -x[i - 1] / (1e-9f * (t[i] - t[i - 1]));
        work += (vcurr - vprev) * abs(vcurr);      // |v| — чтобы торможение вычитало энергию
        if (i == count - 1) work *= 0.5f;          // начальное условие: поверхность уже двигалась
    }
    return ke2v(work);
}
float ke2v(float work) { return (work < 0 ? -1 : 1) * sqrt(abs(work)) * 1.41421356237f; }
```

Две тонкости, которые легко потерять при портировании:

1. **`|vcurr|`, а не `vcurr`.** Без модуля торможение добавляло бы энергию вместо того, чтобы её
   отбирать, и смена направления давала бы бессмыслицу.
2. **Половина веса старейшего сегмента.** Это начальное условие «тело уже двигалось со скоростью
   `v₀`», кинетическая энергия которого `1/2·v₀²`. Именно оно делает алгоритм несмещённым:
   постоянный поток дельт возвращает ровно свою скорость (проверено тестом
   `constantStreamReturnsExactlyThatVelocity`).
3. **Скорость интервала берётся из *новейшего* конца.** Поэтому у N сэмплов только N−1 интервал, и
   дельта самого старого сэмпла в сумму не входит вообще (тест
   `theOldestDeltaIsDroppedBecauseAVelocityComesFromTheNewerEndpoint`).

Константы: `HISTORY_SIZE = 20`, `HORIZON = 100 мс`.

## 4. Что было не так в терминале, и что сделано

### 4.1. Кросс-жестовое суммирование выключено (дефолт = поведение системы)

`FLING_RESIDUAL_ENABLED = false` в `TerminalView`.

- `startFling` теперь берёт `velocityY` как есть (клампнув по модулю), без `combineFlingVelocity`.
- `interruptFlingForNewTouch` больше не захватывает остаточную скорость (если флаг выключен).
- Весь код захвата/распада/суммирования **сохранён** и по-прежнему работоспособен — достаточно
  переключить флаг, чтобы вернуть прежний «flywheel». Исправлен знак (см. §2.1).

### 4.2. Суммирование импульсов колеса — по AOSP IMPULSE

Новый класс `terminal-view/.../support/ScrollImpulseTracker.java` — порт
`calculateImpulseVelocity` (см. §3) с отклонениями, которые задокументированы в самом классе:

- время подаётся в миллисекундах (`MotionEvent.getEventTime()`), внутри хранится в наносекундах;
- сэмплы с одинаковым таймштампом **складываются**, а не перезаписываются: для дифференциальной
  оси перезапись означала бы потерю целого нотика колеса.

Применение в `onGenericMotionEvent`:

- сам тик по-прежнему прокручивается **сразу** (системно, без инерции) — px→строки через общий
  `mScrollRemainder`, чтобы дробные дельты тачпада не терялись;
- если включён `WHEEL_FLING_ENABLED`, тик дополнительно уходит в накопитель, и каждый тик
  перезапускает таймер `WHEEL_IMPULSE_SETTLE_MS = 100 мс` (= `HORIZON`);
- когда серия закончилась, **один раз** запускается fling со скоростью
  `impulseVelocity × getScaledVerticalScrollFactor()` px/с.

Почему именно так: раньше на каждый тик вызывался `accelerateFling` с фиксированным импульсом,
то есть fling **перезапускался на каждом нотике** — позиция сбрасывалась в `mTopRow`, сплайн
начинался заново, и движение получалось рваным. Импульсная модель снимает эту проблему по
определению: импульсы копятся внутри накопителя, наружу выходит один fling.

### 4.3. Позиция больше не теряет суб-строковый остаток между жестами

В системе позиция непрерывна и субпиксельна; у нас она квантуется, но остаток можно **переносить**:

- `mScrollRemainder` больше не обнуляется на `ACTION_UP`;
- при завершении fling (и по касанию, и по доезду) остаток px-оси передаётся в
  `mScrollRemainder` — новый метод `captureFlingRemainder()`;
- в режиме mouseTracking (`mFlingDeltaMode`) остаток не из чего взять — абсолютной позиции нет,
  перенос пропускается;
- обнуление осталось там, где меняется геометрия и остаток в пикселях теряет смысл:
  pinch-зум (меняется высота строки), смена сессии, `onCancel`, drag thumb'а скроллбара —
  всё это идёт через `stopFlingAndClear()`.

Итог: стыки drag→drag, drag→fling и fling→drag больше не «залипают» на величину до одной строки.

### 4.4. Мелочи

- Tail-cut теперь сравнивает `Math.abs(getCurrVelocity())` — чтобы порог не стал зависить от
  направления, если семантика `getCurrVelocity()` когда-нибудь изменится.
- Исправлены перепутанные знаки в (пока выключенном) edge-glow коде `onScroll`: `distanceY < 0`
  уводит **в историю** (к верхней кромке), `distanceY > 0` — к низу. Эта конвенция выведена из
  работающего upstream-пути drag/fling и теперь задокументирована в комментарии.
- Удалены более не используемые `velocityForFlingDistancePx()`, `SCROLL_FRICTION`,
  `DECELERATION_RATE`, `WHEEL_FLING_ROWS` — калибровка «импульс на тик» заменена честной
  скоростью из накопителя.
- `mMaxCombinedFlingVelocity` → `mMaxFlingVelocity` (никакого «combined» больше нет).
- Добавлен `onDetachedFromWindow()`: снимает отложенный колбэк импульса и гасит fling.

## 6. Что осталось несистемным (осознанно)

1. **Квантование в строки.** Рендер глифовый; субглифовый сдвиг запрещён требованием.
   Компенсируется точной физикой (скорость и торможение — системные) и переносом остатка.
2. **Tail-cut.** В системе нет (там непрерывные px), но при квантовании хвост fling рассыпается
   на видимые «тики». Потеря дистанции ≤ 2 строки.
3. **Жёсткий стоп у края** вместо `EdgeEffect`. Решение `0fab152e`, не откатывается;
   glow доступен за `EDGE_GLOW_ENABLED`.
4. **Инерция колеса** (`WHEEL_FLING_ENABLED`) — Chromebook-style, системного аналога нет.

- `isStale()` соответствует горизонту.

## 8. Ручная сверка на устройстве (POCO X5 Pro, LineageOS)

1. Один и тот же свайп в терминале и в системном списке (Настройки) — пролёт одинаковый.
2. **Повторный свайп по летящему тексту:** ускоряет, но **не перелетает** — раньше пролёт был
   заметно длиннее системного.
3. Коснуться летящего текста — мгновенный стоп, без докатки.
4. Медленный drag туда-обратно — нет «залипания» при смене направления (перенос остатка).
5. drag → fling → drag: позиция не отпрыгивает на строку.
6. `yes` во время fling — без джиттера; после остановки follow-text работает.
7. Колесо/тачпад: дробные дельты копятся; с `WHEEL_FLING_ENABLED=true` серия тиков даёт **один**
   плавный доезд, а не серию рывков по нотику.
